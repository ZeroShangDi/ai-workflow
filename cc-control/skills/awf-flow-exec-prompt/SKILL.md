# W-Prompt — 提示词生成引擎

为 awf-run 工作流的每个阶段生成符合用户风格的提示词。被 `/w-prompt` 命令调用，也可独立使用。

---

## 二、阶段生成规则

每个阶段分两步：**先分析上下文做决策，再按顺序组装**。以下规则确保 AI 看到 state.json 的数据后，知道该从字典中选哪条提示词。

---

### DEV — 开发阶段

**第一步：分析上下文，做决策**

| 判断条件 | 决策 | 从字典选 |
|----------|------|----------|
| task.deps 非空 | 需要先理解依赖任务的产出 | [进入状态]：「先阅读相关代码，告诉我你理解了什么」 |
| task 是从 DEBUG 回来的（--from DEBUG） | 自主推进，不需要逐步确认 | [设定模式]：「你自主推进，不用每个步骤都等确认」 |
| task.prompt 描述复杂、涉及多个文件 | 逐步推进，每步验证 | [设定模式]：「我们一步一步来，每完成一步等我确认」 |
| task.prompt 描述简单、改动明确 | 快速迭代 | [设定模式]：「我们快速迭代，每次只改一个小点」 |
| task.prompt 中提到具体文件名 | 收窄到文件级 | [锁定范围]：「只改这一个文件」 |
| task.prompt 提到模块/目录 | 收窄到模块级 | [锁定范围]：「只改当前模块，不要碰其他地方」 |
| task.prompt 中有"新模块""新功能""架构""跨文件""创建""新增" | complexity = complex | DEV 阶段链走全链条 + DOCS |
| task.prompt 中有"修复""bug""优化""重构""性能""调整" | complexity = medium | |
| task.prompt 中有"改配置""改文案""改默认值""单行""改常量""改注释" | complexity = simple | |
| task.prompt 中有"首期""简化""临时""快速" | 降低复杂度预期 | [控制深度]：「先做最简单的实现，跑通了再说」 |
| task.prompt 中有"基础设施""长期""架构" | 提示考虑扩展 | [控制深度]：「这是长期基础设施，要考虑后续的扩展」 |
| task.prompt 或 deps 中包含 Figma 链接 | 追加 UI 稿提示 | [UI 稿/Figma]：选 1 条 |
| 以上条件都不命中 | 使用默认组合 | [进入状态]：「先复述一遍需求」+ [锁定范围]：「改动越小越好」+ [控制深度]：「先把主流程跑通」 |

**第二步：按顺序组装**

```
1. [进入状态] → 1 条（决策结果）
2. [设定模式] → 1 条（决策结果，跳过则用默认）
3. [锁定范围] → 1 条（决策结果）
4. [控制深度] → 1 条（决策结果，跳过则用默认）
5. task.prompt 或 task.desc（核心任务描述，原样拼接）
6. 如有 Figma → [UI 稿] 1 条
7. 状态更新指令
```

**DEV 生成示例**（task 简单改动、无依赖、自主推进）：
```
先复述一遍需求，确保你理解的是我要的。
你自主推进，不用每个步骤都等我确认。
改动越小越好。

/ai-workflow:w-dev {task.prompt}

完成后更新状态。
```

---

### DEBUG — 调试阶段

**第一步：分析上下文，做决策**

| 判断条件 | 决策 | 从字典选 |
|----------|------|----------|
| --error 中包含"报错""crash""Error""500" | 定位崩溃点 | [排查定位]：「先不要修，先定位根因」+「检查最近的改动，二分法定位是哪个提交引入的」 |
| --error 中包含"不生效""没反应""没触发" | 走链路，找断点 | [排查定位]：「从数据流的角度把整个链路走一遍，标注每个环节的输入输出」 |
| --error 中包含"偶发""有时""不稳定" | 先确认复现条件 | [排查定位]：「先确认复现条件」+「对比正常情况和异常情况的日志差异」 |
| 控制台无输出、无打点触发 | 先加日志 | [排查定位]：「先加日志定位断在哪里」 |
| exec.result 中有已排除的方向 | 拼接已排除信息 | 直接从 exec.result 提取，追加到 prompt 中 |
| exec.files 有 1-2 个文件 | 收窄到具体文件 | [锁定范围]：「只改引起问题的代码」 |
| exec.files 有 3+ 个文件 | 防止修复扩散 | [锁定范围]：「只改引起问题的代码，不要顺手改其他东西」 |
| 以上条件都不命中 | 默认链路排查 | [排查定位]：「用排除法，逐个关掉可能的原因」 |

**第二步：按顺序组装**

```
1. [排查定位] → 2 条（决策结果）
2. [锁定范围] → 1 条（决策结果）
3. 错误上下文：{task.desc}，{fromPhase} 出错：{error.description}
4. 已排除（从 exec.result 提取，无则跳过）
5. 状态更新指令
```

**DEBUG 生成示例**（不生效类错误、单文件改动）：
```
从数据流的角度把整个链路走一遍，标注每个环节的输入输出。
用排除法，逐个关掉可能的原因，看哪个关掉后问题消失。
只改引起问题的代码。

{task.desc}，{fromPhase} 出错：{error.description}

定位根因并修复。修完后更新状态。
```

---

### REVIEW — 审查阶段

**第一步：分析上下文，做决策**

| 判断条件 | 决策 | 从字典选 |
|----------|------|----------|
| exec.files 有 5+ 个文件 | 全面审查，按维度 | [审查验证]：「审查所有改动，按正确性、边界、耦合、性能四个维度」 |
| exec.files 有 1-4 个文件 | 聚焦审查，假设有 bug | [审查验证]：「假设这个改动有 bug，最可能在哪里出问题」 |
| 任何情况 | 检查关联影响 | [审查验证]：「检查有没有影响到其他模块，不要只看改动本身的文件」 |
| task.wbsRef 指向 UI 相关模块 | 检查场景覆盖 | [审查验证]：追加「列出所有可能受影响的场景，逐个验证」 |

**第二步：按顺序组装**

```
1. [审查验证] → 2 条（决策结果，至少包含关联影响那条）
2. 审查范围：{exec.files}
3. 产出要求：文档（前缀 awf-review-）
4. 状态更新指令（通过 → TEST，不通过 → DEV）
```

---

### TEST — 测试阶段

**第一步：分析上下文，做决策**

| 判断条件 | 决策 | 从字典选 |
|----------|------|----------|
| 任何情况 | 场景化验证 | [审查验证]：「列出所有可能受影响的场景，逐个验证」 |
| 任何情况 | 验证点来源 | 从 task.desc 提取正常路径，从 exec.result 提取边界，从错误历史提取异常路径 |
| 任何情况 | 额外检查固定 | 控制台报错、打点数据是否正确、关联功能是否受影响 |
| TEST 结果发现缺陷 | 追加排查 | [排查定位]：选 1 条 |

**第二步：按顺序组装**

```
1. [审查验证] → 1 条
2. 测试范围：{exec.files}
3. 验证点（至少 3 条：正常路径、边界条件、异常路径）
4. 额外检查项
5. 状态更新指令（通过 → COMMIT，缺陷 → DEV）
```

---

### COMMIT — 提交阶段

无决策分支，所有条件固定。

**组装顺序**：

```
1. [提交] 自查：「自查一遍：有没有遗留的调试代码、注释掉的旧逻辑、写死的测试值」
2. [提交] 约束（全选）：
   - 只提交本次改动的文件
   - 不要 push
   - 用中文写 commit message
   - 不要带 AI 的账号信息
3. 提交范围：{exec.files}
4. 状态更新指令（标记任务 done）
```

---

### FINISH — 收尾阶段

**第一步：分析上下文，做决策**

| 判断条件 | 决策 | 从字典选 |
|----------|------|----------|
| 里程碑有 10+ 个 task | 全面总结 | [收尾]：「总结这次改了什么、为什么这么改、还有什么没做的」 |
| 里程碑有 <10 个 task | 简要总结 | [收尾]：「检查所有任务完成、文档同步、Issue 清点」 |
| 任何情况 | 固定检查项 | 遍历 plan.tasks 确认全部 done、对比 exec.files 和 docs/、扫描 .claude/issues/、lint + typecheck |

**第二步：按顺序组装**

```
1. [收尾] → 1 条（决策结果）
2. 固定检查项（全列）
3. 状态更新指令（标记里程碑 done）

还有未完成任务时：不进入 FINISH，输出未完成任务列表，回 DEV。
```

---

### DOCS — 文档更新阶段

**第一步：分析上下文，做决策**

| 判断条件 | 决策 | 说明 |
|----------|------|------|
| task.complexity === 'complex' | 触发 DOCS | 新模块/架构始终需要文档 |
| task 是 featureGroup 最后一个 | 触发 DOCS | 完整功能需要文档 |
| FINISH 阶段 | 固定检查 | 扫全量文档是否过期，未覆盖的执行为缺失 |
| 以上都不满足 | 不触发 | 不需要独立 DOCS 阶段 |

**第二步：按顺序组装**

```
1. [收尾] 文档相关：「更新相关文档，确保文档和代码同步」
2. 任务上下文：{task.desc} + 改动文件 {exec.files} + 执行结果 {exec.result}
3. 文档范围：docs/ 下与 task.wbsRef 对应的文件
4. 状态更新指令（标记文档已同步）
```

## 三、风格铁律

生成 prompt 时必须遵守以下 9 条规则，从用户 2039 条提示词蒸馏而来：

1. **场景 + 约束 + 参考** — 先说场景，再说限制，最后给参照物
2. **具体，不抽象** — 说文件路径不说"相关文件"，说组件名不说"对应模块"
3. **先列边界再动手** — 明确告诉 AI 哪些不能动
4. **一个 prompt 一个任务** — 不把多个独立需求塞进同一个 prompt
5. **互斥/对比显式标注** — "A 和 B 互斥"、"只有 X 应该 Y"
6. **调试类 prompt 带排除项** — 告诉 AI 已排除了什么、怀疑什么
7. **中文为主，技术名词保留英文** — "检查下 hover 时的 quickAskRatio 计算结果"
8. **不废话** — 去掉"请你帮我"、"麻烦你"，直接说事
9. **简洁不啰嗦（弱限制）** — 保留必要信息的前提下尽量短。只说做什么、边界在哪，怎么做到是模型的事。不把需求复述一遍，不去教模型已经会的东西。不强制，但生成完问自己：有没有可以删掉而不影响意思的句子？

## 四、上下文装配

生成 prompt 时从 `.awf/state.json` 读取以下上下文：

| 来源 | 字段 | 用途 |
|------|------|------|
| task | `prompt` | DEV 的核心任务指令 |
| task | `desc` | 所有阶段的描述锚点 |
| task | `exec.result` | DEBUG 了解改了什么、REVIEW 知道审什么 |
| task | `exec.files` | REVIEW/TEST/COMMIT 的范围 |
| task | `commits` | COMMIT 判断是否需要多次提交 |
| task | `deps` | DEV 提示注意依赖任务的产出 |
| task | `wbsRef` | 关联到 WBS 和需求文档 |
| plan | `wbs` | 理解整体上下文 |
| milestones | `status` | FINISH 判断进度 |

## 五、状态更新模板

每个生成的 prompt 末尾必须附加阶段对应的状态更新指令：

| 阶段 | 完成后更新 |
|------|-----------|
| DEV | `awf_task_status` → active, `awf_task_result` → 写入 exec.result + exec.files |
| REVIEW | 通过 → `awf_phase` → TEST; 不通过 → `awf_task_status` → active, `awf_phase` → DEV |
| TEST | 通过 → `awf_phase` → COMMIT; 缺陷 → `awf_task_status` → active, `awf_phase` → DEV |
| COMMIT | `awf_task_commit` → 写入 hash + message, `awf_task_status` → done |
| DEBUG | `awf_task_status` → active, `awf_task_result` → 更新 exec.result |
| FINISH | `awf_milestone_update` → done, `awf_phase` → FINISH |
| DOCS | `awf_task_result` → 更新 exec.result（标注文档已同步） |

## 六、特殊场景处理

### 多任务衔接
如果上一个 task 刚完成，在 DEV prompt 中追加：
```
上一个任务完成了，改动在 {exec.files}。当前任务依赖这些改动。
```

### DEBUG 回到 DEV
