# 开发原则

行为准则——写代码时怎么工作、怎么取舍。质量标准见 code-dev-quality，设计取舍见 code-dev-design。

## 核心准则

1. **先理解再动手** — 没理解清楚需求或代码上下文，不动代码
2. **极简优先** — 用最简单的方案解决问题，不提前抽象（YAGNI）
3. **外科手术式修改** — 只改必要的，不顺手重构无关代码
4. **目标驱动** — 每行代码都知道它在服务哪个验收标准

## 工作方式

- **小步前进，频繁验证** — 一个增量完成就验证一次，不攒一大坨再测
- **小步重构** — 重构是习惯不是项目：每次改动顺手把经过的代码变好（Boy Scout 原则），但要有测试兜底
- **失败要快** — 错误尽早暴露，不静默吞掉
- **提交纪律** — 原子提交、说明为什么（见 code-commit-gitflow）
- **AI 友好代码** — 代码要能被没有完整上下文的下一个读者（人或 AI）看懂：依赖显式传入（DI 优于全局状态）、类型/接口用足、显式优于巧妙

## 代码组织

- 相关代码放在一起（局部性原则，见 code-dev-design 代码组织节）
- 一个文件一个职责
- 不要创建"utils" 垃圾桶

## 命名

- 函数名说清做什么（动词 + 名词）——`fetchData`、`validateEmail`
- 变量名说清是什么（名词）；集合用复数 `users` 不是 `userList`
- 布尔值用 `is` / `has` / `should` 前缀
- 不用无意义的名字：`data`、`info`、`handler`、`manager`
- 缩写在业务域内用；单字母只在短循环内用

## 函数设计

- 一个函数只做一件事——需要"and/or"描述就拆
- 参数不超过 3 个，超过用对象
- 副作用和纯逻辑分离，副作用推到边界
- 复杂度阈值：圈复杂度 >10 提示要拆，嵌套深度 >3 用早退守卫

## 错误处理

- 边界处验证（用户输入、API 响应）
- 内部代码信任类型系统
- 错误信息说清：什么错了 + 为什么 + 怎么修
- 可预期失败返回错误值，不可预期异常抛错（见 code-dev-design 函数节）

## 一致性优先

- 同一件事只用一个写法（`get` vs `fetch` 二选一），全库统一
- 用 lint + formatter 强制执行，不靠人自觉
- 不确定的取舍问 code-dev-design / code-dev-cto
