# 代码简化

在不改变行为的前提下，减少不必要的复杂度。

## 核心原则

### 复杂度分两种，只简化可控的那种

| 复杂度 | 来源 | 是否可简化 |
|--------|------|-----------|
| 业务复杂度 | 规则、合规、边界情况 | 不可消除，但可放对位置 |
| 实现复杂度 | 过度抽象、绕弯、重复 | 可控，审查重点 |

目标不是消除所有复杂度，是把必要的复杂度放好、把不必要的减掉。

### 抽象的时机：Rule of Three

> 第一次直接做，第二次咬牙复制，第三次才抽象。— Don Roberts

一次出现直接实现；两次出现可暂缓、做时留意相似；三次及以上再提取抽象。**重复 3 次用具体实现，好过一个猜错的抽象。**

### 过度抽象是债：AHA / YAGNI

- **AHA（避免仓促抽象）** — 重复比错误的抽象便宜。错误抽象的征兆：为一个新场景不断加参数、共享代码里出现 if 分支按调用方分流、注释解释"这条路径给谁用"。修复：内联该抽象、重新复制、让正确模式浮现
- **YAGNI（你不会需要它）** — 不为假想需求写代码：不写未来才用的钩子、不写无调用方的接口（一个实现时不需要接口）、不建没有插件的插件架构、不留注释掉的代码

### 简单设计的四个规则（按优先级）

1. 通过所有测试
2. 表达意图（命名/结构让目的显而易见）
3. 无重复（知识单一表达）
4. 元素最少（删掉不为 1-3 服务的任何东西）

规则冲突时，前面的赢。

## 检查项

1. **Rule of Three** — 只出现一两次的模式不要抽象；反之，重复 3 次了还没抽象也是债
2. **过度工程化** — 为未来需求写的代码就是债务；抽象工厂给单一实现、泛型仓库给单一实体
3. **死代码** — 未被调用的函数、未使用的变量、注释掉的代码、无实际用处的配置
4. **if-else 链** — 可以用查表法（map）替换
5. **冗余状态** — 能推导的值不要存储（存储派生值是双份真相）
6. **过度配置** — 只有一个值的配置项不需要存在
7. **条件分流** — 共享代码里按调用方 if 分流 → 拆开或真正抽象
8. **聪明的代码** — 用位运算炫技、魔法条件，读者要推理半天 → 换成直白的实现

## 简化方法

- 能删的先删（死代码、注释掉的、未用参数）
- 能合并的再合并（重复逻辑 → 只到第三次）
- 简化后行为不变——简化必须有测试保障
- 简单的代码不需要注释来解释；需要解释的说明名字或结构有问题

## 简化前自问

- 这个抽象有 3+ 个真正相同的使用场景吗？（没有 → 内联）
- 我在解决今天的问题还是假想的未来？（未来 → 删）
- 不熟悉的人能一眼看懂吗？（不能 → 简化）
- 简化之后测试还过吗？（不过 → 需要测试补位，先补测试再简化）
