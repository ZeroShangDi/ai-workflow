# 文档体系

> 参考：Diátaxis 文档框架（四类文档）、Michael Nygard ADR 模板

## 文档分类

### 1. 需求文档（code-doc-base）

- 位置：`docs/features/<需求名>/`
- 内容：目标、边界、场景、验收标准
- 必选，每个需求必须有

### 2. 测试用例（code-doc-test）

- 位置：`docs/features/<需求名>/`
- 内容：基于需求文档的测试场景和用例（见 code-test-case）
- 必选，和需求文档同目录

### 3. 问题中心（code-doc-issues）

- 位置：`docs/issues/`
- 内容：阻塞问题、待决策事项、风险记录
- 状态：开放 / 进行中 / 已关闭

### 4. Bug 记录（code-doc-bugs）

- 位置：`docs/bugs/`
- 内容：缺陷描述、复现步骤、根因分析、修复方案
- 作用：踩坑记忆——同样的错误不犯第二次

### 5. 可复用资源（code-doc-reuse）

- 位置：`docs/reuse/`
- 内容：组件、模块、工具函数、代码片段索引
- 作用：减少重复造轮子

### 6. 决策记忆（code-doc-decision）

- 位置：`docs/discuss/`
- 内容：架构决策、方案对比、技术偏好、踩坑经验
- 格式：背景 → 选项 → 决策 → 理由

## 决策记录用 ADR 格式

重大技术决策按 ADR 写，git commit 说明"改了什么"，ADR 说明"为什么这么选"：

```markdown
# ADR-001: 选择 Zustand 作为全局状态库

状态：accepted   // proposed / accepted / deferred / superseded / withdrawn

## 背景（Context）
多页面共享用户会话状态，Context 方案导致频繁全量重渲染。
数据更新频率高、组件订阅粒度要求细。

## 决策（Decision）
采用 Zustand + 切片订阅。

## 后果（Consequences）
正向：组件只重渲染订阅的切片，无样板代码。
负向：团队需学习新库；调试依赖 devtools 插件。

## 备选方案（Alternatives）
Redux Toolkit（样板重）、Context（重渲染面大）——为何不选。
```

- 一条 ADR 只记一个决策，一旦 accepted 不可改——被推翻就写新 ADR 并 superseded 引用
- 决策用主动语态（"我们将采用 X"），背景写真实约束而非"我们需要数据库"
- **在实现该决策的 PR 里同步写 ADR**，不拖到"以后"

## 四类文档写作法（Diátaxis）

每一页文档先判断属于哪一类，**一页只做一类**，混写是文档混乱的最大来源：

| 类型 | 回答的问题 | 写法 |
|------|-----------|------|
| 教程 | 从零教我 | 步骤式、带讲解，读者照着做 |
| 指南 | 怎么做 X | 祈使句、编号步骤、给可复现命令 |
| 参考 | 细节是什么 | 中立、穷尽、可扫描（API 参数表、配置键） |
| 解释 | 为什么这样 | 讲理由和取舍，防反复争论 |

## 原则

- 文档与代码同仓库，同提交更新
- **过时文档比没文档更糟**——更新或删除
- 增量更新优先于全量重写
- 分类是为了查找快，不是为了分类多
- **新鲜度是硬指标**——文档声明了代码里不存在的东西，就是传播错误；CI 可在代码变更时提示关联文档是否更新
- 决策/解释类文档 AI 可起草，但涉及"代码里实际是什么"的参考/解释，必须对着代码核对，禁止虚构
- 每份文档有 owner；不同层级文档标准不同（团队内部文档不必达到对外标准）
- 写最坏时刻的文档——runbook 是凌晨三点值班人员打开的，要编号步骤 + 可粘贴命令 + 预期输出

## 反模式

- 页面堆砌教程+参考+解释混在一页
- 只堆自动生成的参考文档，缺教程和解释
- 例子未经测试——"照着做会失败"的文档不如没有
- 专业盲区——对熟悉系统的人省略"显然的步骤"，新读者卡死
