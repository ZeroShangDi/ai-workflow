# 架构审查

从任务目标和完整 diff 出发审查变更传播，不逐文件孤立打分，也不因文件多而直接否决。

读取任务的 `exec.architecture` 与 `.awf/context/architecture.md`（存在时），但以实际代码和依赖关系为准。依次判断：

1. 需求的主要变化轴是否由明确的权威边界承载。
2. 同一业务判断是否被复制到多个模块，尤其是散落的类型/场景分支。
3. UI、存储、传输等细节是否越权决定领域行为，或产生反向/循环依赖。
4. 新抽象是否来自真实变化轴；共享实现是否因调用方差异不断增加特例。
5. 应重构时是否只做了补丁堆叠；不应重构时是否扩大了无关影响面。
6. 同类需求再增加一个实例时，预计修改是否能集中在当前扩展点。
7. 测试是否验证稳定行为，并允许内部结构安全演进。

## 架构纪律（逐条取证）

除上述通用判断外，还要对照项目架构地图（`.awf/context/architecture.md`）中已确认的架构纪律核验。纪律正文由项目的架构地图承载，以下是三类必须落到证据上的检查项——只写「符合/不符合」不算结论，必须给出命令输出或代码位置。

### 1. 依赖单向

- 读架构地图的「依赖方向」，列出允许方向与明令禁止的反向依赖。
- 用实际导入关系核验方向，**不以注释、文档自述或模块名代替证据**：扫描被审范围的 `require(` / `import ... from`，按层归类每条跨层导入。
- 重点看：底层是否反向依赖上层实现；端口/契约层是否依赖具体实现；入口层是否绕过接口直取内部模块。
- 注意字面导入扫描的死角：`require(path.join(__dirname, …))`、运行时拼接的路径、字符串别名等**计算路径引用**同样是真实依赖边却搜不到。凡「零依赖 / 零导入」类结论，必须补扫这类形式后再下。
- 非 pass 判据：存在与地图相反方向的导入，或同一模块同时依赖上下游两侧。

### 2. 隔离

- 确认每个运行实例（run / 租户 / 会话）的数据都由实例标识寻址：状态、日志、决策记录、临时目录、外部会话名。
- 查模块级可变状态（顶层 `let` / 模块级容器），逐个判定它属于进程级还是实例级；**实例级数据放在模块级即为串号隐患**。
- 查跨实例共享的固定路径、固定端口、固定名称。
- 非 pass 判据：任一实例级数据落在与实例无关的固定位置，或存在绕过标识取用的路径。

### 3. 事件 schema 版本

- 找到事件/消息的信封定义，确认是否带有可判定的版本字段。
- 确认消费方（落盘、推送、前端、外部订阅者）能否据版本区分形状；无版本的形状变更即为破坏性变更。
- 非 pass 判据：新增或修改事件形状，却未提供版本或兼容读路径。

三条与通用 7 条并列计入 verdict。违反任一条时，`architecture.note` 必须写明**纪律名 + 证据位置 + 期望方向**；只写纪律名不算合格结论。

## Verdict

- `pass`：变化沿合理边界发生；局部权衡不会显著增加下一次变更成本。
- `changes_requested`：方向可修复，但存在决策散落、依赖越界、错误抽象或应收敛而未收敛。
- `fail`：核心边界选择错误，继续局部修补会扩大结构损害，需要重新设计或拆分。

非 pass 时，结论必须指出：变化轴、被破坏的边界、证据位置、期望的权威归属和修复方向。不要只写“可维护性差”或“文件太多”。

在门禁 RESULT 中同时返回结构化架构审查信息：

```json
{"architecture":{"changeAxis":"变化轴","boundary":"期望边界","path":"refactor-then-change|split","boundaryChanged":true,"note":"证据与修复方向"}}
```

若审查确认了新的长期模块职责、依赖规则或扩展方式，修复并复审通过后再更新架构地图；失败轮次不写入未验证的设计。
