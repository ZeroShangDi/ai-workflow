# SQLite 数据持久化设计说明

> **状态：独立持久化模块及 Server、Web、CLI 的主流程接入已实现；MCP 仍通过 Server 间接使用，不直接访问 SQLite。**本文记录数据模型、表字段、接口与改造边界。每台设备使用全局数据库 `~/.awf/awf.sqlite`，统一保存该设备上多个项目的数据；建表 SQL 和版本迁移脚本放在代码目录 `server/persistence/schema/`。项目工作目录内的日志正文、审查报告和大型产物仍留在各自的 `.awf/` 文件夹。历史文件导入和跨设备同步尚未实现。

> **边界原则：**Server 是持久化访问边界；Web、CLI、MCP 通过 Server 的应用接口使用数据库，不直接依赖 SQLite repository 或 SQL。

## 1. 设计目标

- SQLite 不需要单独部署数据库服务；本实现使用 Node 内置 `node:sqlite`，不增加 npm 依赖。项目当前检测到 Node 24.14；该版本仍会报告 API 实验性警告，Node 24.15 起官方将 API 标为 Release Candidate。
- 需求是 plan 和 run 共用的持久化对象。plan、run 是归属该需求的工作流会话。
- run 中断后继续时保留同一个会话 ID，只新增一次执行尝试；日志目录也保持不变。
- 数据关系用外键和关联表表达；JSON 字段只用于扩展数据，不用 JSON 数组保存任务 ID、WBS ID 等关系。
- 写入用事务。状态投影更新和对应事件应在同一事务提交；用修订号作乐观并发令牌。
- 这一阶段数据库模块与业务应用解耦。所有 SQL、迁移、事务、连接配置和行映射都集中在持久化模块。

## 3. 实体关系与标识设计

```text
逻辑项目
├── 本机环境 / 项目目录（checkout）
├── 项目架构 WBS（一棵项目级结构树）
├── 产品 Issue / 待办
└── 需求
    ├── Plan 工作流会话
    ├── Run 工作流会话
    │   └── 执行尝试 1、2、3……（重启不换会话）
    ├── 任务 ── 任务依赖 / 执行记录 / commit 记录
    ├── 决策 ── 多对多关联任务
    ├── Bug ── 关联发现、修复、验证任务
    └── 需求修订、决策事件、运行日志文件

产品 Issue 可转为需求，但保留原 Issue ID 和转换历史。
```

### 3.1 当前关键 ID 盘点

| 概念 | 当前代码状态 | 设计处理 |
|---|---|---|
| `projectRoot` | `CC_PROJECT` 或 `cwd` 得到的本机路径，用于路由和定位 `.awf/` | 只代表本机 checkout 路径，不能作为跨设备项目 ID。 |
| `project_id` | 当前无稳定的一等身份字段 | 生成 UUID，存到可随 Git checkout 携带的 `.awf/project.json`。 |
| `runId` / `sid` | host `submitRun` 接受调用方 ID，缺省会用固定值 `default`；CLI 可传 `--run-id`；代码另有 `generateRunId` 等工具，但身份未统一 | 数据模型使用统一内部 `workflow_session_id`。新 run 创建时生成稳定 UUID/ULID。 |
| `runStamp` | 根据版本及秒级时间戳派生，用于日志/决策文件名；可能冲突 | 只作为旧 ID、导入别名或展示标签，不再作为主键/外键。 |
| Claude/DSH conversation ID | Claude hook 的 `session_id`、DSH 的 `sessionId` | 作为 provider 命名空间下的可空外部 ID 关联，不能替代 AWF 工作流会话 ID。 |
| message ID | 当前所检视的 Server/CLI/Web 路径中没有统一持久化的 message ID | 内部领域事件使用自己的 `event_id`。外部 message ID 仅在适配器真实提供且需要去重时记录。 |
| decision ID | 当前有 `decision_id`，事件写入按 runStamp 分文件 | 保留为可稳定映射的内部决策 ID，决策归属需求/会话，并可通过关联表连接多个任务。 |
| task ID | 如 `T1`，通常只在当前 state 文档内有效 | 用数据库内部 `task_id` 作稳定 ID；`task_key`（如 `T1`）在需求内唯一。 |
| 事件序号 | run host 使用内存序号和环形缓冲，进程重启会重置 | 持久化领域事件 ID 和聚合内序号；实时推送游标与持久序号分开。 |

盘点所依据的代码包括 `server/shared/run-id.cjs`、`server/shared/run-context.cjs`、`server/shared/project-paths.cjs`、`server/run/host.cjs`、`server/features/decision/store.cjs`、`server/web/api/hook.cjs` 及 CLI run/session 启动路径。以上是当前状况，不代表目标契约。

### 3.2 ID 规则

- `project_id`：逻辑项目 UUID，首次创建后稳定。不能由目录、`projectRoot` 或 Git remote 推导为唯一身份。
- `environment_id`：每台设备/安装实例一个 ID，不采集硬件指纹。
- `checkout_id`：某环境下某个项目实际目录的记录；目录移动只更新 checkout 路径，不改变项目 ID。
- `requirement_id`、`workflow_session_id`、`attempt_id`、`task_id`、`decision_id`、`bug_id`、`issue_id`、`event_id`：内部生成的不透明稳定 ID。
- provider conversation/message ID：可能为空，必须连同 provider 保存，不能取代内部 ID。
- 旧 `sid`、`runStamp`、`T1` 等经 `legacy_ids` 映射迁移，不继续复用为全局主键。

### 3.3 两台电脑上的同一项目

建议把小型 `.awf/project.json` 清单随项目仓库保存，其中记录稳定的 `project_id` 和 manifest 版本。每台设备有自己的 `environment_id`；全局数据库 `~/.awf/awf.sqlite` 同时管理该设备上的多个项目及其 checkout 路径。数据库不在项目仓库中，因此 Git checkout 不会复制本机数据库，也不会自动同步业务记录。

SQLite 文件放 Git 的确能支持单写者顺序交接，例如一台机器完成后关闭数据库、checkpoint、提交并 push，另一台 pull 后继续。但 SQLite 是二进制文件，Git 无法合并两台机器并行写出的表行；WAL 模式还涉及 `-wal`/`-shm` 文件和 checkpoint。因此建议默认不跟踪数据库文件。若未来选择 Git 顺序交接，需要明确单写者约束、备份和冲突恢复流程。

### 3.4 数据库文件和 SQL 源文件放在哪里

- **数据库运行文件：**放在用户级 `~/.awf/awf.sqlite`。一个设备上的所有项目共用本地数据库，`project_id` 区分逻辑项目，`project_checkouts` 记录该设备上各项目的目录。数据库不在项目仓库中，不会随 Git 复制；备份和权限也集中管理。
- **SQL schema/migration 源文件：**放在程序代码目录 `server/persistence/schema/` 并纳入版本管理。它们描述数据库如何创建/升级，不是数据库实例数据。
- **不建议项目根目录或项目下 `sql/` 目录存数据库文件：**数据库是本机生成的二进制运行数据；`sql/` 更适合放迁移 SQL 源码。把数据库放进仓库会遇到并行编辑无法合并、误提交以及 SQLite sidecar 管理问题。
- `~/.awf/awf.sqlite` 不放进 Git。不要直接复制运行中的数据库文件；备份走 SQLite backup API。

Git remote URL 可用作“可能是同一项目”的提示，但不适合作为 canonical ID：项目可能没有 remote、有多个 remote、改名、镜像、fork 或私有别名。稳定 ID 写入 manifest；remote 对比用于辅助提示，ID 不一致时由用户确认关联。

这套身份设计只为未来多设备同步留位置，**不会自动实现数据接力**。要同步需求和会话，未来还需选择中心服务或导入/导出机制，并定义并发冲突策略。多个 SQLite 文件本身不会自动合并。

#### 两个 SQLite 文件能否合并

可以把一份数据库中的行导入另一份数据库，但不能把两个 `.sqlite` 文件字节级拼接后得到一个正确数据库，也不能指望 SQLite 自动判断冲突该听哪边。`ATTACH DATABASE` 可以在同一连接里访问另一个数据库文件，真正的合并仍要由应用按表读取、插入/更新、处理外键和重复主键。官方 `sqldiff` 工具用于比较数据库差异，不负责业务冲突决策。

SQLite Session Extension 可以针对**相同 schema 且起始数据兼容**的数据库生成 changeset，再把变更应用到另一端；仍可能出现主键、唯一约束、外键或同一字段并发修改冲突，应用必须选择中止、忽略还是覆盖。它不是无条件的“自动合并”，且未来采用前还需确认 Node 驱动是否提供所需 API。

对本设计而言，追加式 `decision_events`、`domain_events` 等可以在稳定事件 ID、来源环境 ID 和去重规则下尝试合并；同一 `requirement`、`task` 或 `issue` 同时在两台设备修改时，必须有业务冲突规则。若未来要求无感多设备协作，中心同步服务通常比直接互相合并整个 SQLite 文件更容易控制一致性。

## 4. 数据表与字段

类型使用 SQLite `TEXT`、`INTEGER`。`PK` 表示主键，`FK` 表示外键，`NULL` 表示可空。ID 和时间默认由持久化 API 生成（UUID/ULID、UTC ISO-8601）；没有给出 SQL 默认值的必填项由 API 提供。JSON 以经过校验的 JSON 文本保存。相同类型和默认值的字段可合并列出，但每个字段名仍对应独立列。

### 4.20 约束与索引原则

- `UNIQUE(requirement_id, task_key)`、`UNIQUE(workflow_session_id, attempt_no)` 等保证局部唯一性；关联表使用复合主键。
- 外键约束跨实体关系；删除有依赖者的任务要拒绝。涉及学习历史的数据原则上归档/软删除，不级联丢失。
- 任务依赖环、状态机转换、WBS 父子环由同事务内的持久化校验拒绝；单纯 `CHECK` 无法表达跨行 DAG。
- 常用索引：任务按需求/状态/顺序；会话按需求/类型/创建时间；决策和事件按需求/会话/时间；Issue 按项目/状态/优先级。
- 时间统一 UTC ISO-8601。修订号不是时间戳，作为可靠乐观并发版本。
- 全局数据库由本机多个进程/项目共用；写事务应短小，配置 `busy_timeout`，避免长事务占住 SQLite 的单写者锁。

## 5. 前后端交互与持久化模块边界

第一阶段只实现下列持久化模块，不让 CLI、MCP、HTTP handler 或业务能力直接写 SQL：

```text
server/persistence/
  index.cjs                 # 唯一公共导出入口
  api/                      # 对外方法、跨表编排与事务边界
  database.cjs              # open/close、连接配置、事务
  schema/                   # 版本化 SQL migration
  repositories/             # 内部表读写，按数据模块分组，不对外导出
  errors.cjs                # 稳定错误码
```

模块依赖边界：只能依赖 Node 内置模块和自身文件；不引用 `server/shared`、`server/runtime`、CLI、插件、HTTP handler 或业务领域模块。公共 API 只接收基础类型/普通对象并返回普通对象。所有消费者以后都只引用 `server/persistence/index.cjs`；内部文件不作为公共 API。

调用方直接使用数据模块方法；不持有连接，也不逐次开关数据库。模块第一次初始化后在当前 Node 进程中复用一个连接，进程退出时由运行时回收；长驻服务可在优雅关闭时调用一次 `shutdownPersistence()`。数据库路径只需在应用启动时配置一次，也可以不显式初始化而使用默认路径。

```js
const persistence = require('./server/persistence/index.cjs');

// 可选：应用启动时指定数据库路径。省略则首次调用时使用 ~/.awf/awf.sqlite。
persistence.initializePersistence({ filePath: '/path/to/awf.sqlite' });

const result = persistence.projects.create({ name: 'my-project' });
if (!result.ok) throw new Error(result.error.message);

const created = persistence.requirements.createWithPlan({
  requirement: { projectId: result.data.id, title: '示例需求', requestText: '...' },
  plan: { title: '需求规划' },
});
if (!created.ok) throw new Error(created.error.message);

// 长驻服务退出时调用一次；CLI 短进程通常无需显式调用。
persistence.shutdownPersistence();
```

所有方法使用统一 `{ ok: true, data }` / `{ ok: false, error }` 结果；数据库约束错误、输入校验错误和存储错误由公共 API 边界转换为稳定错误码。跨表操作在 API 层的同一事务中编排；内部 Repository 失败会触发整体回滚。底层连接、SQL 和 Repository 不对外导出。

## 7. SQLite 技术选型

“无依赖”指 SQLite 不需额外数据库服务，不必然代表 Node 应用不用驱动。项目目前没有 SQLite 运行时依赖。

1. **已采用：Node 内置 `node:sqlite`。**当前检测到 Node 24.14，不增加 npm 运行时依赖，并使用同步事务；Node 24.14 仍显示实验性警告，官方从 v24.15 起将 SQLite API 标为 Release Candidate。需要在后续确定并统一项目支持的最低 Node 版本。[Node.js SQLite 文档](https://nodejs.org/api/sqlite.html) [Node.js 版本状态](https://nodejs.org/en/about/previous-releases)
2. 同步原生驱动：事务直观、性能好，但有平台预编译包和安装打包成本。
3. 纯 JS/WASM：避免原生编译，但需确认持久 VFS、文件锁、WAL 和文件系统兼容；不能假设内存版可安全写共享文件。

建议领域调用方只依赖自有 Repository API，不让驱动 API 泄漏到模块外。若最低 Node 版本不能提高，则需另选支持范围明确的驱动。

## 9. 事务、备份和运维原则

- PRAGMA：启用外键、WAL、合理 `busy_timeout`，并校验 `user_version`。迁移用 `BEGIN IMMEDIATE` 防止并发迁移。
- 同步驱动下事务回调不得 `await`；嵌套事务复用当前事务。异步驱动必须保证同连接隔离。
- 写当前状态及其事件必须原子提交；使用幂等键去重 hook 重试。失败事务不得留下半成品。
- 在线备份用 SQLite backup API。WAL 模式不能只复制主 `.sqlite`；否则在维护锁下 checkpoint 并关闭连接，再一并复制相关 sidecar 文件。
- `PRAGMA integrity_check` 由诊断接口运行，不必每次启动全库扫描。模块公开备份/完整性检查能力；CLI 命令以后另行接入。
- 不将 transcript、报告正文和大文件作为 BLOB 放入数据库，必要时登记相对路径、大小、摘要。
- 业务数据删除优先归档/软删除；禁止因级联误删用于流程优化的历史记录。

## 11. 独立模块验收标准（未来实现）

- 空库可创建；重复运行 migration 不破坏已存数据。
- 每张表、字段均有文档定义并能通过唯一公共导出 API 使用；调用方不需要引用内部文件。
