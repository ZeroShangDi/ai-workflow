# 能力测评方案设计

> 目标：对比三种模式的任务完成质量，量化 ai-workflow 的增量价值

---

## 1. 背景

ai-workflow 的定位是"给 AI 加上持久记忆、工作流编排和自主推进能力"。核心假设是：引入工作流编排后，AI 在复杂多步骤任务上的表现显著优于裸调用。

本方案设计对比实验，通过统一的任务集、统一的评测指标，量化三种模式的能力差异，回答：

- **cc-control 比纯模型好多少？**（插件 + MCP 的增量价值）
- **awf run 比 cc-control 好多少？**（工作流编排的增量价值）
- **在什么类型的任务上差距最大？**（能力边界探测）

---

## 2. 三种对比模式

| 模式 | 环境 | 执行方式 | 代表场景 |
|------|------|---------|---------|
| **M1 纯模型** | 裸 `claude -p` | 一次性 prompt，无上下文保持 | 用户直接问 Claude |
| **M2 cc-control** | 加载 plugin + 3 个 MCP server | 交互式对话，可手动使用 slash commands | 用户在 CC 中手动推进 |
| **M3 awf run** | M2 + `awf run` 自主执行 | 自动遍历 tasks，阶段驱动，无需人工 | 完全自主工作流 |

**控制变量**：三种模式使用相同的 task prompt 和相同的验收标准。

## 3. 测评指标体系

### 3.1 指标概览（5 维度 × 3-4 指标）

```
                    ┌─ 任务完成率 (TC)
        ┌─ 完成度 ──┤
        │           └─ 验收标准通过率 (AC)
        │
        │           ┌─ Lint 通过率 (LP)
        ├─ 质量 ────┤
        │           ├─ 测试通过率 (TP)
        │           └─ Commit 规范性 (CM)
        │
        │           ┌─ 总耗时 (ET)
测评 ──┼─ 效率 ────┤
        │           ├─ Token 消耗 (TK)
        │           └─ 产出/消耗比 (OE)
        │
        │           ┌─ 人工介入次数 (HI)
        ├─ 自主性 ──┤
        │           └─ 卡住/死循环次数 (ST)
        │
        │           ┌─ 圈复杂度 (CC)
        └─ 可维护性 ─┤
                    ├─ 代码重复率 (DR)
                    └─ 文件组织合理性 (FO)
```

### 3.2 指标定义

#### 完成度（权重 30%）

| ID | 指标 | 定义 | 数据来源 | 采集难度 |
|----|------|------|---------|---------|
| TC | 任务完成率 | done tasks / total tasks | state.json | 容易 |
| AC | 验收标准通过率 | 实际通过的 AC / 计划 AC 总数 | state.json + 人工复核 | 中等 |

**评分**：
- TC: `(done / total) × 100`
- AC: 人工逐条检查，通过数 / 总数 × 100

#### 质量（权重 25%）

| ID | 指标 | 定义 | 数据来源 | 采集难度 |
|----|------|------|---------|---------|
| LP | Lint 通过率 | `npm run lint` 0 错误的 task 占比 | CI/lint 输出 | 容易 |
| TP | 测试通过率 | 生成代码对应测试通过的比例 | vitest 输出 | 容易 |
| CM | Commit 规范性 | Conventional Commits 格式占比 | git log | 容易 |

**评分**：
- LP: 首次 lint 通过的 task 数 / 总 task 数 × 100
- TP: 通过的测试数 / 总测试数 × 100
- CM: Conventional Commits 消息数 / 总 commit 数 × 100

#### 效率（权重 20%）

| ID | 指标 | 定义 | 数据来源 | 采集难度 |
|----|------|------|---------|---------|
| ET | 总耗时 | 从开始到结束的 wall-clock 时间（分钟） | 计时器 | 容易 |
| TK | Token 消耗 | input + output tokens 总量 | Claude API usage | 困难（需 API 层） |
| OE | 产出效率 | 有效代码行数 / 总耗时 | git diff --stat | 容易 |

**评分**：
- ET: 与 baseline（首次 M1 运行）的比值，`min(100, baseline / actual × 100)`
- TK: 同上（token 消耗越低越好）
- OE: `产出行数 / 耗时(分钟)`，归一化到 0-100

> **TK 指标说明**：Token 消耗在 Phase 1 中无法精确采集（需 Claude Code 暴露 usage 数据）。Phase 1 使用估算值（基于输出字符数 × 0.3），Phase 2 接入 API 层精确采集。

#### 自主性（权重 15%）

| ID | 指标 | 定义 | 数据来源 | 采集难度 |
|----|------|------|---------|---------|
| HI | 人工介入次数 | 需要用户输入/选择的次数 | `.claude/issues/` + 决策记录 | 容易 |
| ST | 卡住/死循环次数 | 同一 task 重复执行 ≥3 次 | state.json history[] | 容易 |

**评分**：
- HI: `max(0, 100 - HI × 20)`（每次人工介入扣 20 分，最低 0）
- ST: 无卡住 = 100，每次卡住扣 25 分

#### 可维护性（权重 10%）

| ID | 指标 | 定义 | 数据来源 | 采集难度 |
|----|------|------|---------|---------|
| CC | 圈复杂度 | 函数平均圈复杂度 | eslint complexity rule | 中等 |
| DR | 代码重复率 | 重复代码行 / 总代码行 | jscpd 或手动 | 中等 |
| FO | 文件组织 | 文件结构是否合理（目录层级、命名） | 人工评审 | 困难（需人工） |

**评分**：
- CC: `max(0, 100 - (avgCC - 10) × 10)`（目标 ≤10）
- DR: `max(0, 100 - DR × 100)`（重复率越低越好）
- FO: 人工评分 0-100（目录结构、模块划分、命名规范）

### 3.3 综合评分公式

```
S = CW×30 + QW×25 + EW×20 + AW×15 + MW×10

CW = TC×0.6 + AC×0.4          (完成度)
QW = LP×0.4 + TP×0.4 + CM×0.2  (质量)
EW = ET×0.4 + TK×0.2 + OE×0.4  (效率)
AW = HI×0.6 + ST×0.4           (自主性)
MW = CC×0.4 + DR×0.3 + FO×0.3  (可维护性)
```

## 4. 对比实验设计

### 4.1 测试任务集

分三个难度等级，每组 ≥5 个任务：

#### Tier 1: 简单（单一功能，1-2 个文件）

| # | 任务 | 预期产出 |
|---|------|---------|
| T1-1 | 实现一个 `debounce` 工具函数 | 1 个 .js 文件 + 测试 |
| T1-2 | 实现一个 `formatDate` 日期格式化函数（支持多种格式） | 1 个 .js 文件 + 测试 |
| T1-3 | 实现一个简单的 HTTP JSON mock server（单文件） | 1 个 .js 文件 |
| T1-4 | 写一个 Markdown 链接检查脚本 | 1 个 .js 文件 + 测试 |
| T1-5 | 实现 `deepClone` 函数（处理循环引用） | 1 个 .js 文件 + 测试 |

#### Tier 2: 中等（多文件模块，3-8 个文件）

| # | 任务 | 预期产出 |
|---|------|---------|
| T2-1 | 实现一个 Todo CLI 应用（add/list/done/delete） | 3-5 个 .js 文件 |
| T2-2 | 实现一个简单的 key-value 存储库（支持 TTL） | 3-4 个 .js 文件 + 测试 |
| T2-3 | 实现一个 CSV→JSON 转换器（支持流式处理） | 2-3 个 .js 文件 + 测试 |
| T2-4 | 写一个静态博客生成器（Markdown→HTML） | 4-6 个 .js 文件 |
| T2-5 | 实现一个简单的任务队列（支持并发控制） | 3-4 个 .js 文件 + 测试 |

#### Tier 3: 复杂（多模块联动，8+ 个文件）

| # | 任务 | 预期产出 |
|---|------|---------|
| T3-1 | 实现一个 Express REST API（CRUD + 认证中间件 + 参数校验） | 8-12 个文件 |
| T3-2 | 实现一个 WebSocket 聊天室（含前端页面） | 6-10 个文件 |
| T3-3 | 实现一个简单的 CI 流水线模拟器（解析 .yml、执行 steps、报告） | 10-15 个文件 |
| T3-4 | 写一个数据库迁移工具（up/down/status、支持 SQLite） | 8-12 个文件 |
| T3-5 | 实现一个插件系统（动态加载、生命周期 hooks、隔离执行） | 10-15 个文件 |

### 4.2 实验流程

```
对每个 Tier 的每个任务：
  1. 准备干净的工作目录（空 git repo）
  2. 写入统一的 task prompt 到 task.md
  3. 用三种模式各执行一次：
     M1: claude -p "$(cat task.md)" > output.txt
     M2: 交互式 claude --plugin-dir ... + 告知"请完成任务，可用 /awf-run"
     M3: awf plan "$(cat task.md)" + awf run
  4. 采集各项指标
  5. 记录结果到 results.json
```

### 4.3 控制措施

- **相同 prompt**：三种模式使用完全相同的任务描述
- **相同环境**：相同 Node 版本、相同的默认配置
- **时间上限**：每个任务最多 30 分钟（Tier1）、60 分钟（Tier2）、120 分钟（Tier3），超时记为未完成
- **每条任务独立运行**：清理临时目录，避免上下文污染
- **人工复核**：所有任务的完成度由同一人按统一标准评判

### 4.4 实验矩阵

```
            T1-1  T1-2  T1-3  T1-4  T1-5  │  T2-1  ...  T3-5
M1 (纯模型)   ✓     ✓     ✓     ✓     ✓    │   ✓    ...   ✓
M2 (CC)      ✓     ✓     ✓     ✓     ✓    │   ✓    ...   ✓
M3 (awf)     ✓     ✓     ✓     ✓     ✓    │   ✓    ...   ✓
──────────────────────────────────────────┼─────────────────
总计：3 模式 × 15 任务 = 45 次实验
```

## 5. 评分模型

### 5.1 权重配置

| 维度 | 权重 | 理由 |
|------|------|------|
| 完成度 | 30% | 核心目标：能不能完成任务 |
| 质量 | 25% | 产出的代码能不能用 |
| 效率 | 20% | 时间和资源成本 |
| 自主性 | 15% | 工作流编排的核心价值 |
| 可维护性 | 10% | 长期价值，当前阶段权重较低 |

### 5.2 归一化方法

每个指标得分先计算原始值，再归一化到 0-100：

| 归一化方式 | 适用指标 | 示例 |
|-----------|---------|------|
| 直接比例 | TC, AC, LP, TP, CM | TC = 5/6 = 83.3 |
| 基准比值 | ET, TK | 以 M1 的值为基准，`100 × 基准/实际` |
| 阈值扣分 | HI, ST, CC | 超过阈值线性扣分 |
| 人工评分 | FO | 1-5 级评分 × 20 |

## 6. 实现难度评估

### 6.1 可自动化采集（Phase 1 即可实现）

| 指标 | 采集方式 | 置信度 |
|------|---------|--------|
| TC 任务完成率 | 解析 state.json `tasks[].status` | 高 |
| LP Lint 通过率 | `eslint --format json` 解析输出 | 高 |
| TP 测试通过率 | `vitest run --reporter json` 解析输出 | 高 |
| CM Commit 规范性 | `git log --format=%s` + 正则匹配 Conventional Commits | 高 |
| ET 总耗时 | 脚本计时 `time` / `Date.now()` 差值 | 高 |
| OE 产出效率 | `git diff --stat` + ET 计算 | 高 |
| HI 人工介入 | `.claude/issues/` 文件计数 + state.json 决策记录 | 中 |
| ST 卡住次数 | state.json `history[]` 中连续重复 phase 检测 | 中 |
| CC 圈复杂度 | `eslint` complexity rule 输出解析 | 中 |
| DR 代码重复率 | `jscpd` 或手动 diff 对比 | 中 |

### 6.2 需人工评判（Phase 1 采集中标注"需人工"）

| 指标 | 人工评判方式 | 原因 |
|------|-------------|------|
| AC 验收标准 | 逐条检查是否真正满足 | 语义判断，无法自动化 |
| FO 文件组织 | 1-5 分人工评分 | 无公认的自动化度量标准 |

### 6.3 需额外基础设施（Phase 2+）

| 能力 | 依赖 | 难度 |
|------|------|------|
| TK Token 消耗 | Claude API usage 字段暴露 | 等上游支持 |
| 批量实验编排 | runner 脚本 + 结果数据库 | 中等 |
| 历史趋势追踪 | 时序数据库 + 可视化 | 较高 |

### 6.4 分期实现路线

```
Phase 1（当前）：基础对比实验
  ├── 完成度 + 质量 + 效率（不含 TK）+ 自主性
  ├── 手动执行 45 次实验，结果录入 results.json
  ├── 纯 HTML 报告渲染
  └── 产出第一版对比结论

Phase 2（下个迭代）：自动化采集
  ├── 采集脚本 runner.js 批量执行 + 计时
  ├── 接入 lint/vitest/git 数据自动提取
  ├── 自动生成 results.json → HTML 报告
  └── Token 消耗（如果 API 层已暴露）

Phase 3（远期）：持续测评平台
  ├── 历史数据库 + 趋势图
  ├── CI 集成（发版前自动跑核心指标）
  └── 任务集扩展（社区贡献 test fixtures）
```

## 7. 预期结论模板

完成实验后，预期产出以下关键发现：

1. **M1 vs M2 差异**：加载 plugin + MCP 后，AI 可以使用 `awf-state` MCP tools 操作 state.json，任务完成率预计提升 10-20%（主要在复杂任务上）。

2. **M2 vs M3 差异**：`awf run` 的自主推进能力在 Tier 2+ 任务上差异显著。M3 消除了人工判断"下一步做什么"的认知负担，自主性指标预计提升 30-50%。

3. **能力边界**：M3 在 Tier 3 复杂任务上的优势最大（阶段驱动拆分复杂度），但在 Tier 1 简单任务上 overhead 可能反而增加耗时。

4. **ROI 拐点**：当任务需要 ≥3 个步骤时，M3 的增量价值超过其 overhead 成本。
