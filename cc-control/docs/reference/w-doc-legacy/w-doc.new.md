# w-doc

功能文档管理。覆盖功能文档、测试用例、开发日志、Bug 记录、决策记忆五类，支持**模块级 / 功能级**两种粒度，自动判断新建或增量更新。

## 关联 Skill

- **code-doc** — 文档体系规范（分类、ADR、Diátaxis 四类写作法）

## 参数

`$ARGUMENTS` — 模块名称 或 `模块/功能ID` 格式。

- 模块级：`/w-doc run` → `docs/features/run.md` + `docs/features/run.test.md`
- 功能级：`/w-doc run/req-003` → `docs/features/run/req-003.md` + `req-003.test.md` + `req-003.log.md`

可选 flag：`--force` 强制从零重写。

## 文档类型

| 类型 | 目录 | 说明 |
|------|------|------|
| 功能文档 | `docs/features/<name>.md` | 扁平存放，与测试用例同级同前缀 |
| 测试用例 | `docs/features/<name>.test.md` | 与功能文档同目录 |
| 开发日志 | `docs/logs/` | 功能级变更记录、关键决策、已知问题 |
| Bug 记录 | `docs/bugs/` | 缺陷、根因、修复方案 |
| 决策记忆 | `docs/discuss/` | 架构决策、方案对比、偏好记录 |

> 注：原分类中的「问题记录 `docs/issues/`」「可复用资源 `docs/reuse/`」已移除——问题上报走 `.claude/issues/`（AI 上报人工决策），`docs/reuse/` 从未建立。如后续需要可再加回。

## 路由逻辑

1. 解析 `$ARGUMENTS`：
   - 含 `/` → 功能级，解析出 `<module>/<req-id>`
   - 不含 `/` → 模块级
2. 检查目标文件是否存在
3. **不存在** → 走新建流程
4. **已存在 且无 `--force`** → 走增量更新流程
5. **已存在 且有 `--force`** → 走新建流程（覆盖）

## 模块级文档

面向整个模块的完整功能面：

- `docs/features/<module>.md` — 功能文档
- `docs/features/<module>.test.md` — 测试用例

模板与功能级一致（见下）。

## 功能级文档（三件套）

一个功能 = 一个逻辑集中的任务（对应 WBS 的一个叶子节点）。

### 文件命名约定

```
docs/features/<module>/
├── <req-id>.md          # 功能文档
├── <req-id>.test.md     # 测试用例
└── <req-id>.log.md      # 开发日志
```

### 1. 功能文档（`<req-id>.md`）

代码驱动参考风格（对齐实际 `docs/features/*.md`）：

```markdown
# [功能名] — 功能文档

> 对应 WBS：[节点编号]
> 源码：src/xxx

## 功能描述
[该功能做什么，1-3 句；含边界条件和异常情况]

## 执行流程
[流程图或步骤列表，标注关键决策点]

## 核心常量 / 配置
| 常量 | 值 | 说明 |
|------|-----|------|

## 函数清单
| 函数 | 说明 | 位置 |
|------|------|------|

## 接口 / 依赖
| 模块 | 用途 |
|------|------|

## 验收标准
- [ ] 标准 1
- [ ] 标准 2
```

### 2. 测试用例（`<req-id>.test.md`）

对齐实际 `docs/features/*.test.md` 格式：

```markdown
# [功能名] — 测试用例

> 对应功能文档：docs/features/<module>/<req-id>.md
> 源码：src/xxx
> 测试文件：tests/...

## 测试场景总览
| # | 场景 | 类别 |
|---|------|------|

## 详细测试用例

### TC1: [场景名]
**前置条件**：[精确初始状态]
**执行**：[具体调用]
**断言**：
- [精确结果]
- ...

## Mock 策略
| 依赖 | Mock 方式 | 说明 |
|------|-----------|------|
```

> 721 渐进式（70% 单元 / 20% 集成 / 10% E2E）作为测试设计参考，见 code-test-case；默认只留用例文档不写测试代码，逻辑过复杂或回归频繁时再补代码。

### 3. 开发日志（`<req-id>.log.md`）

```markdown
# [功能名] — 开发日志

> 记录核心变更和关键决策，不记录临时调试信息。

## 变更记录

| 日期 | 变更类型 | 描述 | 关联 commit |
|------|---------|------|------------|
| ... | feat/fix/refactor | ... | ... |

## 关键决策

1. [决策] — [原因] — [权衡]
2. ...

## 已知问题

- [问题描述] — [影响] — [计划]
```

## 文档撰写通用原则

1. **代码驱动**：所有描述必须基于实际代码分析，禁止虚构
2. **中文优先**：正文用中文，代码标识符保留英文
3. **表格优先**：结构化信息优先使用表格
4. **关注 Why**：记录设计决策和权衡
5. **精确引用**：文件路径 + 函数名
6. **增量优先**：文档与代码同提交更新，过时即改；增量更新优先于全量重写
