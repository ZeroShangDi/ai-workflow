# 任务粒度体系 Q&A 记录

> 2026-07-23，为制定 `flow-rule-task` skill 进行的需求讨论。
> 起因：讨论 eval 工具的 WBS 拆分时，发现需要先对齐"怎么拆任务"的方法论。

## 第 1 轮：eval 工具形态确认

**Q: 测评工具的形态是什么？是嵌入 awf CLI 的命令（如 awf eval），还是独立的 CLI 工具，或是 Web Dashboard？**

A: 独立 CLI + HTML 报告

**Q: 测评数据怎么收集？是在 awf run 执行过程中实时采集，还是 run 结束后从 state.json + 日志文件事后分析？**

A: 需要先确定采集维度，然后确认事后采集能否达到要求，如果不能达到要求则需要开发一套 SDK，然后实时采集，插入 SDK 暴露的方法，采集点采集，同样也是需要保留一定的高内聚低耦合。

**Q: 测评模式是单次评分还是基准测试套件？**

A: 先实现单次评分，后续做基准测试套件，渐进式实现。

---

## 第 2 轮：测评目的与定位

**Q: 测评的核心目的是什么？这决定了维度的权重分配。**

A: 能力边界探测、版本迭代对比、质量门禁。主要目的是为了比较不同版本 AWF 执行的效果，确保每次修改是正向的，能力边界探测也是这个目的，查缺补漏不断优化。次要目的是质量门禁确保流程能够正常运行不会断掉即可。可以拆分为两块实现，一块是效果调优，一块是流程运行的顺畅和稳定。

**Q: HTML 报告的主要受众是谁？**

A: 开发者/我自己

**Q: 这个工具放在项目结构的哪个位置？是 cc-control 内部的一个子模块，还是独立的顶层项目？**

A: 应该是放在 cc-control 内独立模块，但是放在 awf-eval 是否合理需要考量，他应该不属于 mcp 把？另外测试命令应该放在 cc-control 内的 script 中，作为开发期的命令，不向真实生产环境中暴露。

---

## 第 3 轮：目录结构与维度

**Q: 测评工具在 cc-control 内的目录结构如何设计？**

A: 测试和测评相关的逻辑统一放在 cc-control 下的 tests 目录下，至于目录下怎么划分，由你自行决定。

**Q: 效果调优和流程稳定性，是同一命令输出两份报告，还是两个独立命令？**

A: 同一命令，两份报告

**Q: 效果调优最核心的评分维度有哪些？（可多选，用于设计权重体系）**

A: 你的第一个为结果分析，第二个为过程分析，第三个算运行分析，这些理论上都需要，还可能需要比如 token 消耗统计，单个任务的对话轮次，是否存在死循环，是否卡住，提示词的生成的正确性，完全自主运行的累计时间，等等，我考虑的也不是很全面，关于维度需要单独多轮沟通，一次问题解决不了。

## 第 4 轮：eval 工具具体拆分决策

**Q: collector（采集器）包含 state 解析、git 提取、文件扫描三个子能力。它们是同一轮对话就能串行做完的程度，还是每个子能力需要独立的探索-实现-验证循环？**

A: 拆为 3 个独立 task [P]

**Q: scorer（评分引擎）包含 3 个 layer 评分器 + 1 个聚合器。Layer 评分器的逻辑是高度同构的（都是查表/线性插值），还是一个 layer 一个特殊逻辑？**

A: 2 个 task：评分器 + 聚合器

**Q: reporter（报告生成）包含终端输出、HTML 报告、Canvas 图表三个部分。图表（雷达图/条形图）是最大的工作量，这部分和 HTML 报告是分开做的还是同一轮搞定？**

A: 3 个 task：终端 + HTML + 图表 [P]

## 第 5 轮：Config/CLI/Health 拆分

**Q: config.js（阈值/权重/基准值配置）是单独一个 task 还是融入 scorer 一起做？它独立是因为权重配置需要在 scorer 之前被评审确认吗？**

A: 独立 task

**Q: cli.js（score + health 子命令）只是简单的 Commander 路由 + 模块组装。它算一个 task，还是 score/health 各自算一个？**

A: 1 个 task：CLI 入口

**Q: health.js（健康检查）依赖 state 解析能力（collector），但逻辑独立。它和 collector 能并行吗？还是等 collector 做完再做？**

A: 暂时不考虑串并行问题。

## 第 6 轮：泛化场景 — 测试拆分体系

**Q:「给已有的 REST API 服务加上 Redis 缓存层」，涉及：路由拦截判断是否命中缓存、序列化/反序列化策略、缓存失效策略（TTL + 主动失效）、配置管理（连接池/超时）。怎么拆？**

A: 渐进拆：先 MVP 一个 task，后续迭代补完整

**Q:「做一个 Markdown 预览编辑器」，实时分屏预览、语法高亮、导出 PDF、主题切换。怎么拆？**

A: 我不知道编辑器本身怎么实现，这其实是一个比较复杂的问题，如果说你现在已经有了一定的基础只是在之前编辑器的基础上叠加功能，那应该拆为四个功能，功能下再根据实现方案和实现步骤，复杂程度再向下拆分子任务，就分屏预览而言你可能要先逐个适配不同语法，然后再处理一些特殊场景之类的，需要渐进式的拆分。语法高亮这种可能或许比较简单，或者有现成的方案，可能拆的就比较少一点，但是它和预览以及主题切换都有关联，那可能还需要提前拆分出一个任务来制定好规则，所有的拆分都需要先考虑好实现方案，实现步骤，每个步骤的工作量才好想怎么拆分。

**Q:「做一个 WebSocket 实时通知系统」，服务端推送 + 客户端订阅 + 离线消息队列 + 已读/未读状态管理 + 通知聚合去重。怎么拆？**

A: 每个功能各自实现，复杂的继续向下拆分，不复杂的直接实现，最后一个任务整合联调。

## 第 7 轮：大型/复杂场景

**Q:「MySQL 迁 PostgreSQL」，200 张表，涉及 ORM 方言差异、存储过程重写、序列/自增差异、时间类型差异、事务隔离级别差异。不太确定有多少隐藏的兼容性问题。怎么拆？**

A: 先探索，确定差异，摸清影响点，确定迁移方案，特别是差异问题的兼容处理大致方案，这就有可能是多个任务，取决于有多少差异，然后要摸清楚表结构，确定关联关系，从独立的表开始逐个迁移验证，然后才是有关联的表，从底层表开始逐个迁移，有明确的先后顺序，遇到有需要处理差异或者其他处理的地方，需要单独拆出来任务先写迁移的工具，就比如事件类型差异，遇到复杂的表或者数据量大的表甚至要再拆分，一次完不成就拆两次，这还只是实现的过程，这个过程中你可能还要考虑断掉的问题，出错之后的问题排查，怎么核验数据的正确性，怎么检查有没有缺失遗漏，会不会有重复导入的数据，一些字段变更之后的影响范围，后续前端可能需要做的兼容处理等等，以及最终整合之后全量回归检查的任务。这是不小的工作量，也不是一次能说清楚的。

**Q:「集成微信支付 + 支付宝」，下单、支付回调、退款、对账、签名验签。现有订单系统已经有支付抽象层，但还没接入过真实渠道。怎么拆？**

A: 先调研，做设计，搭框架，渐进补全，对接业务，差缺补漏，多重测试等

**Q:「做一个跨平台 Button 组件」，要支持 React/Vue/Web Component 三种输出。样式主题可配、size 变体、loading 状态。怎么拆？**

A: 先考虑实现方案，代码组织方式，那些可以通用，那些需要各自实现，那些需要先定义好，这就要好几轮，再把架子搭建起来，然后逐个填充内容，每种框架需要各自实现的不同语法各自一个任务，通用的样式，方法按难度各自拆分，需要的功能，逐个往上加。主题 token 定义，样式配置，通用样式实现，如果有的话单独某个端的样式补充，如果一开始不知道那些通用，那些不通用的话还能用笨办法，先分别三个任务写三个组件，然后补充功能，接着抽离其中相同逻辑，重构。同样，这个也只是实现代码，后面还有你的组件打包，组件预览，组件功能测试但应该不包含在这个需求中，具体要看提问者的意思。之所以一上来就先考虑或者先实现再重构的目的都是为了后续的可维护性，可扩展性，等等代码质量问题，所有的功能都不是能跑就行，他需要能持续的跑，能不断地优化。

## 第 8 轮：特殊场景（紧急 / 算法 / 纯调研）

**Q:「线上支付回调成功率突然从 99.7% 掉到 87%」，用户投诉在增长。不清楚是代码 bug、第三方故障、还是数据库问题。怎么拆？这次有紧迫性约束。**

A: 先定位原因，从不同的角度考虑，比如是不是代码修改导致的，还是之前遗漏的 bug，第三方故障或者数据库问题，总之先排查，但要快速的排查，能排查到大致方向就根据方向采取不同的解决方案，比如如果是代码修改导致的，由于支付的重要性，那么回归版本或许是最好的选择，先回滚，本地继续深查根源以及对应的解决方案，如果是第三方故障，那要立刻联系第三方商讨解决方案，并且看是否有对应的备用方案临时解决当下问题，总之，能快速解决就快速解决，不能快速解决就立马准备备用方案，连备用方案也没有先公告，安抚，并仅快排查修复，修复先定方向，在查根因，最后想解决方案，解决之后还要做复盘。

**Q:「实现一个表达式解析器」，支持四则运算、变量绑定、函数调用、类型检查。这和业务系统开发拆分逻辑有区别吗？还是同一套方法？**

A: 渐进拆：理解验证 → 基本实现 → 边界/性能

**Q:「调研团队应该选 React 还是 Vue 3 作为新项目技术栈」，不写代码，只产出决策建议文档。这种纯调研型的工作怎么拆？**

A: 先知己，明确团队内技术储备，现有资产，招聘难度，时间与质量要求，要做什么项目，可能会有什么功能，再知彼，罗列框架区别，生态完善与项目契合度，框架优缺点。自身一个，项目拆解一个，框架对比一个，生态项目契合一个，长期演化成本一个，再综合评估一个。后续有问题再细化。有两条核心，不是要最好的，而是要最合适的，要综合成本最低，风险最小的。考虑一切选择类的问题之前，最重要的是先搞懂自己要什么。这就是为什么有人说，当你犹豫不决时就抛硬币，不是因为硬币能帮你解决问题，而是在你抛向空中的时候，你就知道自己选那个了。

## 关键节点：用户主动阐述

> "核心的判断点在自上而下的判断其在那个档位，从这个档位开始向下进行拆分，拆分的过程中要看具体的实现复杂度，复杂的问题要单独拆出来，各自独立的东西要拆出来，可以先各自独立最后组装的要拆分独立任务和组装任务。向下拆分的过程中觉得没必要拆了就可以停，不是一定要拆到最下层的，定义多层的目的是为了在面对复杂问题的时候降低整体的难度，拆不是目的，怎么能更好的实现才是目的。"
>
> "原子级虽然定义，但几乎不被使用，你说的改一个端点这种直接被定义为一个任务。最小拆分就是任务。任务的拆分主要取决于功能的复杂程度，功能不复杂的情况下一个功能也可以做为一个任务，同样的一个需求也是。"

## AI 归纳的体系总结

（此部分为 AI 基于上述 Q&A 提取，作为 `flow-rule-task` skill 的核心内容）

**一句话**：不了解实现方案就不能拆。拆分的质量取决于对实现步骤和工作量的认知深度。

**通用流程**：理解/探索 → 方案/规则 → 分治实现 → 组装/整合 → 验证/复盘

**五个核心锚点**：

| 锚点 | 含义 |
|------|------|
| 独立可验证 | 做完不需要等别的就能确认正确性 — 核心标准 |
| 复杂就拆 | 遇到复杂的部分单独拎出来，简单的不拆 |
| 同构合并 | 逻辑一样的用一个 task，不人为拆分 |
| 关联前置 | 多模块有耦合时先拆"定规则"的 task |
| 组装是 task | 各自做完后，整合联调本身是一个 task |

**非实现类 task 也是正经 task**：调研、方案、工具脚本、组装联调、验证回归、问题排查、运维保障、复盘总结。
