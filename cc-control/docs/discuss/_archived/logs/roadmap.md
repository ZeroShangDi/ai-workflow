# awf 路线图

> 当前状态 → 下一步 → 远期。优先级从上到下。

---

## 零、已具备的骨架

Run 闭环的**流程骨架**已经完整：CLI 读取 state → 启动 tmux-http → 创建 session → 遍历 task → 四阶段链 → FINISH。12 命令 + 9 skill 定义了方法论基本面。阶段间通过 one-shot 重组 prompt 重置上下文。Hook 系统感知 session 状态。

**问题：骨架能转，但里面不可见，产出不可信。**

## 一、Run 闭环——让骨架可信

### 1.1 状态管理工具化

**唯一不能靠提示词解决的事。**

AI 通过工具读写 state，不直接碰 JSON 文件。防止格式损坏、字段丢失、状态冲突。变更可追溯。

```
工具接口：
  state.get()           → 返回当前完整 state
  state.update({...})   → 合并更新，校验 schema
  state.taskStatus(id)  → 查单个 task 状态
  state.transition(id, from, to) → 受控状态流转
```

### 1.2 反跑偏机制

提示词层面实现，不需要额外基础设施。

每次阶段开始时注入：
- 当前 task 目标
- 上一阶段完成情况
- 下一阶段预期产出
- 自检触发条件（轮次阈值、产出不确定性）

要求 AI 在回复结尾附带状态摘要（结构化，可被 capture 解析）。

### 1.3 阶段简化规则

在状态机和提示词模板中定义：

| 条件 | 跳过 |
|------|------|
| 纯配置/文案变更 | REVIEW |
| 非 UI 变更 | TEST（UI 快照类测试） |
| 单文件小改动（<50 行） | 合并 REVIEW + TEST |
| 测试文件变更 | REVIEW（仅检查测试合理性） |

提示词模板根据条件动态组装，不给 AI 自己做决定的空间。

### 1.4 上下文管理策略

定义在提示词中，AI 自行判断并主动触发：

| 信号 | 动作 |
|------|------|
| 对话超过 N 轮 | 主动 `/compact` |
| 阶段切换 | 重组 prompt，不保留历史 |
| 连续 3 轮无实际产出 | 重新聚焦，检查是否跑偏 |
| 触及未知领域 | 升级为 issue，不强行推进 |
| 检测到重复修改同一块代码 | 暂停，总结根因，重新规划 |

### 1.5 最小文档生成链路

每次 RUN 必须产出的最小集合，格式在提示词中约束：

| 文档 | 内容 | 触发时机 |
|------|------|---------|
| `dev.log.md` | 每个 task 做了什么、改了哪些文件、遇到的问题 | 每个 task 完成时追加 |
| `issues/` | 需要人工决策的问题，含 2+ 方案选项 | 触发升级时 |
| `bugs/` | 发现的 bug，含复现步骤 | 触发 bug 时 |
| `decisions/` | AI 做过的重要选择及原因 | 提示词判断为重要决策时 |

后续扩展：产品文档、需求文档、测试用例文档、对话日志、运行日志、待办、技术债。

### 1.6 异常恢复路径

中断（手动停止、崩溃、超时）后从 state.json 恢复时：

- 当前 task 标记 `interrupted`
- 下一轮启动时 AI 先自检：该 task 的文件变更 → 评估完成度 → 决定续做还是重做
- 提示词引导 AI 先 git diff 看残留，再决定策略

### 1.7 Claude Code 输出捕获方案

当前只能通过 Hook 知道"session 空闲了"，但不知道 AI 输出了什么。

评估方向：
- tmux `capture-pane` 定期抓取（轮询，有延迟）
- Hook 注入脚本，每次 `Stop` 时自动 capture（更精准）
- 未来依赖 Claude Code 自身的输出回调 API（如果开放）

目的是让 checkpoint 探针、文档生成、质量判断有原材料。

## 二、Plan 方法论体系

把专业人的决策经验固化为结构化思考框架，注入 plan 阶段提示词。

### 2.1 技术维度思考框架

```
□ 技术选型：为什么选这个？替代方案是什么？取舍是什么？
□ 技术方案：数据流、组件树、状态管理、错误处理
□ 范围定义：做什么 / 不做什么 / 做到什么程度算完成
□ 功能定义：用户能做什么 / 系统应该输出什么
□ 功能拆分：哪些独立、哪些依赖、哪些可并行
□ 推进策略：先做核心链路还是先铺骨架
```

### 2.2 代码质量维度

```
□ 可读性：命名、函数长度、注释策略
□ 可复用性：是否有抽取机会、是否过度抽象
□ 可维护性：修改成本预估、模块耦合度
□ 健壮性：边界条件、错误处理、空值防护
□ 性能：关键路径识别、是否需要懒加载/缓存
□ 规范：符合项目已有的 code-standards
```

### 2.3 UI 设计维度

```
□ UI 框架选择
□ 风格定义（扁平/拟物/渐变/阴影策略）
□ Design Token（颜色、间距、字号、圆角体系）
□ 是否换肤
□ 是否多语言
□ 响应式策略
```

### 2.4 Plan 产出物

```
□ 需求文档（用户视角，功能描述，验收标准）
□ 原型/线框图（when UI）
□ WBS（交付物导向分解，标依赖和可并行标记）
□ Task 列表（线性顺序，每个 task 有明确完成条件）
□ 技术方案（架构图、数据模型、关键决策）
□ 风险清单（技术风险、时间风险、质量风险）
```

## 三、优化方向（Run 闭环稳定后）

### 3.1 阶段间结构化状态传递

阶段切换时，不传完整对话历史，只传结构化 JSON snapshot：
- 当前 task ID + 目标
- 已完成的关键步骤
- 已知的坑和遗留问题
- 下一步预期产出

### 3.2 Skill Router（按阶段裁剪）

根据当前阶段只加载相关 skill，减少 system prompt 体积：
```
PLAN   → design-standards, awf-spec
DEV    → code-standards, code-patterns, git-flow
REVIEW → code-standards, quality-standards
TEST   → testdoc, quality-standards
COMMIT → git-flow, version-management
FINISH → quality-standards, version-management
```

### 3.3 阶段内静默探针 + Checkpoint

tmux-http 轮次计数，每 N 轮注入一个问题问"当前目标是什么？做到哪了？"AI 的回复被 capture 后判断质量，不达标则触发 compact 或重新聚焦。

### 3.4 场景模型路由

| 场景 | 模型 | 理由 |
|------|------|------|
| one-shot 提示词生成 | Haiku | 文本组装，不需要强推理 |
| DEV 编码 | Opus/Sonnet | 核心产出，值得花 |
| REVIEW 筛查 | Haiku → Sonnet | 第一轮 Haiku 筛，可疑的交给 Sonnet 深查 |
| 探针判断 | Haiku | 只判断回复质量 |

### 3.5 多 Agent 并行

前提条件：
- 单 Agent 闭环已经稳定
- 并行 tasks 之间**无任何关联**
- 调度 Agent 做分配，不参与执行
- 每个并行 Agent 在独立 worktree + branch 工作
- 完成后通过统一的 review gate 合并

### 3.6 测试文件 Hash 防作弊

在每个 task 前后对测试文件做 hash。如果 Agent 修改了测试来让不完整的实现通过，可检测。在 REVIEW/TEST 阶段引入。

### 3.7 回归门禁

task 开始前保存 HEAD 快照。task 完成后跑全量测试。绿色变红色 → 自动 revert + 产出 bug 报告。

### 3.8 自调度机制

让 Agent 在等待外部条件时主动挂起并定时唤醒。可在 tmux-http 层面实现定时注入："X 分钟后继续检查"。

### 3.9 防幻觉 Skill

输出自我检查、置信度分级、禁止的表述模式（如编造 API、虚构错误信息）。

## 四、测评体系

**这是保证迭代不倒退的锚。**

一组标准化测试项目，每个项目包含：
- 需求描述
- 预期产出物清单
- 评分维度（功能完成度、代码质量、文档完整性、是否跑偏）
- 评分标准（每项 1-5 分）

每次改完方法论或提示词，跑一遍测评集对比分数。

测试项目应从简单到复杂分 tier：
```
Tier 1: 单文件工具函数（纯逻辑，无 UI）
Tier 2: 单组件/单页面（有 UI，有状态）
Tier 3: 多模块功能（有路由，有数据流）
Tier 4: 完整项目（从零到可交付）
```

### 真实沙盒运行方案

- 每个测评项目在独立沙盒环境运行
- 沙盒提供：干净的 git repo + 开发环境 + 预装依赖
- 运行后产出：代码 + 文档 + 日志 + 测评分数
- 对比不同版本 awf 在相同测评项目上的表现
