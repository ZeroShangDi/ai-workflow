# 方法论提示词体系

> 我定义的一套 AI 协作提示词。每一条可以直接复制粘贴使用。

---

## 进入状态

让 AI 在开始工作前建立正确的认知：

```
先阅读相关代码，告诉我你理解了什么，我确认对不对
```

```
先复述一遍我的需求，确保你理解的是我要的
```

```
告诉我你打算怎么做，不用太细，说思路就行
```

---

## 设定模式

每次协作开始时选定一种模式，整段对话都按这个模式走：

```
我们先讨论清楚再动手，这次不写代码
```

```
我们快速迭代，每次只改一个小点，改完我验证
```

```
你自主推进，不用每个步骤都等我确认，遇到不确定的再问我
```

```
这次只做探索和分析，不做任何改动
```

```
我们一步一步来，每完成一步等我确认再继续
```

---

## 锁定范围

AI 最容易犯的错就是改多了。用这些把范围钉死：

```
只改这一个文件
```

```
只改这一个函数，其他地方不要碰
```

```
保持现有接口不变，只改内部实现
```

```
不要引入任何新的依赖
```

```
改动越小越好，用最少的代码解决这个问题
```

---

## 控制深度

AI 容易过度设计和过度工程化。用这些控制深度：

```
先做最简单的实现，跑通了再考虑优化
```

```
这是临时方案，不需要考虑扩展性
```

```
这是长期基础设施，要考虑未来三年的扩展
```

```
不需要处理所有边界情况，先把主流程跑通
```

---

## 切换阶段

工作流中从一个阶段进入下一个阶段的信号：

```
方案没问题，开始写代码
```

```
可以提交了
```

```
先停一下，我们重新审视方向对不对
```

```
这一阶段完成了，总结一下然后进入下一阶段
```

```
这个问题先跳过，记录下来后面统一处理
```

---

## 排查定位

AI 排查问题时容易瞎猜。把方法定死：

```
先不要修，先定位根因
```

```
用排除法，逐个关掉可能的原因，看哪个关掉后问题消失
```

```
从数据流的角度把整个链路画出来，标注每个环节的输入输出
```

```
对比正常情况和异常情况的日志差异
```

```
检查最近的改动，二分法定位是哪个提交引入的问题
```

---

## 审查验证

```
假设这个改动有 bug，最可能在哪里出问题
```

```
检查有没有影响到其他模块，不要只看改动本身的文件
```

```
列出所有可能受影响的场景，逐个验证
```

```
只看不改，把发现的问题列出来，我自己判断修哪些
```

---

## 纠偏

AI 跑偏时最短的路径拉回来：

```
方向不对，换一个思路
```

```
太复杂了，给一个更简单的方案
```

```
你这样改会影响其他地方，要改就只改当前模块
```

```
不要自作主张加我没有要求的东西
```

```
回到核心问题，不要发散
```

---

## 回退

```
刚才的改动全部撤掉，重新开始
```

```
那个方向放弃，换一个方向重新分析
```

```
忽略前面的讨论，我们聚焦到这一个点上
```

---

## 提交

```
可以提交了，只提交本次改动
```

```
把改动拆成几个独立的提交，每个只做一件事
```

```
自查一遍：有没有遗留的调试代码、注释掉的旧逻辑、写死的测试值
```

---

## 收尾

```
总结这次改了什么、为什么这么改、还有什么没做的
```

```
把排查过程和结论记录下来，下次遇到类似问题可以直接参考
```

```
更新相关文档，确保文档和代码同步
```

---

## 决策

```
给我两个方案，一个激进的、一个保守的，说说各自的代价
```

```
如果时间只有一半，你会砍掉哪些
```

```
这个问题的最大风险是什么，有没有办法提前验证
```

```
不写代码有没有其他办法能达到同样的效果
```

---

## 上下文

```
当前对话太长了，总结关键结论然后我们重开
```

```
这个话题先存档，切换到另一个问题
```
