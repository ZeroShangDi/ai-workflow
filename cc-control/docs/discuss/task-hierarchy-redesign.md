# 任务层级体系重构讨论

> 2026-07-31，对 `flow-rule-task` 中任务层级体系的重构讨论。
> 起因：现有层级将时空维度混排，需要拆分为空间轴 + 时间轴双轴体系。

## 背景

现有 `flow-rule-task/SKILL.zh-CN.md` 定义的层级链条：

```
生态级 → 系统级 → 里程碑级 → 项目级 → 模块/需求级 → 功能级 → 任务级 → (动作级) → (原子级)
```

问题：**里程碑级和需求级属于时间维度，其余属于空间维度，混排在一起造成理解和使用上的混乱。**

---

## 第 1 轮：时空分离

### 结论

- **空间轴**：生态 → 系统 → 项目 → 模块 → 功能 → 任务（从大到小拆分，一棵会进化的树）
- **时间轴**：里程碑 → 需求（从远到近推进，一个不断追加的数组）

### 存储策略

- **空间轴**：永远只有一棵树（当前态），节点可标 `since: v0.2`、`status: stable/deprecated`。历史版本靠 git 回溯，不在数据里存 N 份快照。
- **时间轴**：一个不断 append 的数组，每个元素是里程碑 → 需求列表，需求里带 `affectedNodes` 指向空间节点。只增不改。

### 更新时机

| 事件 | 空间轴 | 时间轴 |
|------|--------|--------|
| 首次 init/plan | 生成 | 追加首个里程碑 |
| 规划结束 | 审视更新 | — |
| 新里程碑规划 | 审视（可选更新） | 追加新里程碑 |
| 执行中新发现 | 不更新，收集到 notes | 不变 |
| 执行结束 | 批量更新（新模块/重构） | — |
| 需求完成 | 不变 | 标记 done |

---

## 第 2 轮：T1-T9 空间层级 + DFS 后序遍历

### 层级定义

T1 为最小层级，自下而上。叶子节点可以停在任意层级，不需要硬拆到 T4。

| 标识 | 层级 | 门禁（示例） |
|------|------|-------------|
| T1 | — | 预留 |
| T2 | 原子级 | 不独立存在 |
| T3 | 动作级 | 不独立存在 |
| T4 | 任务级 | 核心执行单元 |
| T5 | 功能级 | 功能验收 + UI 审查 |
| T6 | 模块级 | 模块测试 + 代码审查 |
| T7 | 项目级 | 全量回归 + 安全审查 |
| T8 | 系统级 | 集成测试 + 架构审查 |
| T9 | 生态级 | — |

- T1-T3 只存在于概念中，不出现于任务清单。
- T4 是实践中最小使用单位。
- 项目可选择启用哪些层级，不需要的不启。

### DFS 后序遍历生成任务清单

```pseudo
visit(node):
  for child in node.children:
    if child.status != "skip":
      visit(child)
  if node.level >= T4:          // T4+ 生成可执行条目
    tasks.push(node)
  if node.level > T4:           // T5+ 子节点完成后触发门禁
    tasks.push(gate(node))
```

skip 状态场景：
- 模块标记为"本期不改动" → 整棵子树跳过
- 功能标记为"第三方提供" → 跳过但门禁保留（验证集成）

### 拆分用哪棵树，展示用哪棵树

- **拆分用空间轴**：需求来了 → 问"碰哪些空间节点" → 从那个节点往下拆到任务级。
- **展示用时间轴驱动 + 空间轴填充**：时间轴提供骨架（里程碑、需求），空间轴填充内容（哪些模块、多少任务）。不存在"用哪棵树展示"，展示永远是投影——同一份数据，不同视角：

| 视图 | X 轴 | Y 轴 | 用途 |
|------|------|------|------|
| 路线图 | 时间（里程碑） | 空间（模块） | 版本规划 |
| 系统全景 | 空间树 | — | 架构总览 |
| 执行面板 | 任务列表（时间切片） | 依赖链 | awf run |

## 第 3 轮：门禁体系

### 空间门禁（层级门禁）

配置在空间层级上，DFS 后序遍历时自然触发：子节点全部完成后，父节点执行对应门禁。

### 时间门禁

```
里程碑 v0.1
├ 需求A: done → 触发 需求门禁（需求验收 + 文档更新）
├ 需求B: done → 触发 需求门禁
└ 全部需求 done → 触发 里程碑门禁（全量测试 + version bump + 合并主分支 + changelog）
```

### 门禁配置化

门禁规则不硬编码，通过 `.awf/gates.yaml` 配置：

```yaml
levels:
  T5:  # 功能级
    gates:
      - review: { type: code, required: true }
      - review: { type: ui, required: false }
      - test: { scope: feature, coverage: 70 }
  T6:  # 模块级
    gates:
      - test: { scope: impacted, coverage: 70 }
      - review: { type: code, required: true }
  T7:  # 项目级
    gates:
      - test: { scope: full_regression, required: true }
      - review: { type: security, required: true }

time:
  requirement:
    gates:
      - verify: { type: acceptance }
      - doc: { type: update }
  milestone:
    gates:
      - test: { type: full_regression }
      - version: { type: bump }
      - merge: { target: main }
      - changelog: { generate: true }

default_skip_reasons: [third_party, not_this_milestone, already_done]
```

门禁模板一套，但测试 `scope` 参数按层级自动适配：
- T5 → 功能相关测试
- T6 → 模块内受影响功能的测试
- T7 → 全量回归

## 第 4 轮：待解决问题

### 跨模块依赖

**问题**：树结构天然是包含关系（父子），但真实任务常有跨模块依赖（A 模块的任务等 B 模块的接口）。DFS 后序遍历只能解决"子节点都做完了再组装"这类依赖，横向依赖无法表达。

**讨论方向**（未定论）：接口契约模式——横向依赖限制为依赖 T5+ 的接口节点，不依赖 T4 具体任务。依赖的是"接口就绪"而非"模块完成"。被依赖节点优先调度，依赖未满足的任务进入 waiting。

### 大模块测试用例

**问题**：大模块 T6 门禁要求跑模块测试，但如果模块有 20 个功能，一个 T4 任务只改了其中 3 个，全跑不合理。

**讨论方向**（未定论）：通过门禁 `scope` 分级缓解——T5 功能级 / T6 影响范围级 / T7 全量回归，不全压在模块门禁上。

### 一次性拆分多版本自主运行

**结论**：不建议超过一个里程碑。

原因：
1. v0.1 执行结果会改变空间树，基于当前树拆的 v0.2 可能失效
2. 需求会变，v0.1 做完后 v0.2 的优先级和内容可能有调整
3. 门禁失败会级联——v0.1 某个模块门禁不通过，v0.2 基于它的任务全卡住

例外：架构极度稳定 + 需求完全确定 + 版本间无耦合时可尝试。

---

## 方案风险

| 风险 | 说明 | 缓解方向 |
|------|------|---------|
| 树无法表达横向依赖 | DFS 后序假设纯层级，但真实任务有跨模块依赖 | 接口契约 + deps 字段补充 |
| 门禁在层级上太刚性 | 大模块和小模块走同一套门禁 | 支持 override，子节点可继承/覆盖父级配置 |
| 规划→执行结束才更新树 | 中间发现的新模块、新依赖无处记录 | 加 `notes` 字段收集发现，执行结束后批量更新 |
| T1-T9 是否够用 | 有些项目不需要这么细 | 项目选择启用哪些层级 |
