## 二、核心工作模式

### 2.1 决策框架：「先讨论、后动手」

这是你最显著的决策模式。典型句式：

```
"下面先只是讨论，先不动代码"
"不要着急，很多问题，最后我需要你出原型文档的时候你再出，我们现在只是讨论"
"先不着急，这个问题不大，先说这几个命令的问题"
"先不着急，我们先将 w-系列的命令任务做一个流程图"
```

**模式特征**：
1. 抛出问题时明确划定边界 —— 哪些现在讨论、哪些延后
2. 要求 AI 产出结构化思考（流程图、文档、方案优劣对比）再进入执行
3. 讨论过程中逐点推进，不跳跃（"不着急进入第二个问题"）

**统计**：344 条长提示词中，约 25% 包含"讨论/梳理/方案/你觉得/推荐"等决策信号

### 2.2 迭代风格：「持续纠偏、渐进明确」

你的纠错/反馈类提示词有清晰的层次：

**L1 - 方向纠偏**（49次以「不/不对/不是/不行」开头）：
```
"不对，好好想想，好好看看这12个提交的内容"
"不是，为什么会需要改这么多，不是只改一下uploadAttachment就行吗？"
"不对，你修改的不对，我又试了一次，还是一样的结果。"
```

**L2 - 细节校准**：
```
"样式完全不对，你再看下UI稿"
"不是替换，而是新增"
"不要在代码中出现svg代码。"
```

**L3 - 方法引导**（AI 走错路时主动提供替代方案）：
```
"有什么难办的，开关打不了增加个回调参数啊，当然用事件也行...不要想着配置驱动，配置太脆弱了"
"A显然不是一个特别好的方案，B似乎有一定可行性...我考虑使用 Hook 配置来实现，可能吗？"
```

**关键技巧**：纠偏时你不是只说"不对"，而是会给出具体原因和替代方向，让 AI 能立即修正。

### 2.3 需求表达：「场景 + 约束 + 参考」

你的需求描述有一个清晰的公式：

```
[具体场景] + [约束条件] + [参考物/参照系]
```

**实例**：
```
"关于工具栏的位置，现在还是有问题，问题在于工具栏在hover的时候增加了关闭按钮，
以及点击下拉菜单的时候会有改写和总结这些都导致所有的元素没有显示全，需要修复一下，
另外还有一种情况，就是当页面上不止有一个滑词工具的时候，
比如豆包的滑词工具在出现的时候会导致我们的滑词工具位置发生变化
我们期望的是不发生变化，这个看一下能不能解决"
```

**公式拆解**：
- 场景：hover 工具栏 + 关闭按钮
- 约束：所有元素显示全、位置不变化
- 参考：豆包的滑词工具（竞品对比）

**这种写法让 AI 能准确理解上下文，减少来回确认**。

## 三、AI 交互技巧

### 3.1 当 AI 走偏时：三段式纠偏法

1. **否定 + 指出偏差点**：「不对，你现在改的是什么？怎么感觉动到之前刚改动的逻辑了？」
2. **给出原因**：「不是，为什么你默认配置的格式和 mock 数据的格式都不一样？」
3. **提供正确路径**：「开关打不了增加个回调参数啊...不要想着配置驱动，配置太脆弱了」

### 3.2 当 AI 产出不确定时：并行对比法

```
"不如你先每种都生成一下。我先看看结果。"
```

**技巧**：不确定哪个方向好时，让 AI 同时产出多个版本再做选择，比逐一试错高效得多。

### 3.3 当 AI 过度设计时：约束收窄法

```
"不需要使用计划模式，太重了"
"对了，你也不是说非要零依赖，如果能大大降低你的开发复杂度也可以使用的。"
"我们首期为了简化需求，将多路并行的实现延后，因此和多路相关的字段我们定义，但注释掉。"
```

### 3.4 当 AI 纠缠于细节时：核心优先法

```
"是不是越扯越远了...确定错误和需求有没有关系，核心是先解决弹窗的问题，提示，提示，提示，先把风控弹窗提示的所有链路检查三遍"
```

**技巧**：用"核心是"、"先解决"等关键词把 AI 拉回主线。特征：重复强调关键词（"提示，提示，提示"）。

### 3.5 分步推进模式

```
"先完成该项目执行一个命令后将配置以插件的形式注入到 claude code 的功能。"
"只做这一步，完成后等待下一步指令。"
```

**技巧**：复杂任务拆成单步指令，每步验证后再继续，避免 AI 一次改动过多难以排查。

## 四、架构决策模式

### 4.1 模块化原则：「高内聚、低耦合、对外只开放接口」

```
"tmux-http 能否拆分为多个 Tools 或 MCP server，因为从一开始我就希望
这里的模块化更清晰一些，谁该负责什么，高内聚低耦合，对外只开放接口"
```

### 4.2 技术选型偏好：务实 > 炫技

| 偏好 | 实例 |
|------|------|
| 插拔式设计 | "以 Plugin 为主身份，但也可以保留 CLI，既可以通过 npm 安装，也可以通过 claude 安装" |
| 避免配置驱动 | "不要想着配置驱动，配置太脆弱了，如果结构变更或增加功能，配置可能就不够了" |
| 组件传参优于全局状态 | "我们是通过组件传参来实现的" |
| 先简化再扩展 | "首期为了简化需求，将多路并行的实现延后，字段先定义但注释掉" |

### 4.3 需求管理：范围意识强

```
"挂件相关功能未完成的点你可以记录下，但挂件本身不是我开发，所以不需要跟我说，
气泡，设置页以及云控才是我这期的需求，它们的遗漏才是我需要处理的"
```

**技巧**：明确区分「我的需求」和「别人的需求」，不被 AI 的扩展建议带偏。

### 4.4 版本管理哲学

```
"大版本的切换中间要进行一次端到端的全面测试...中版本进行一次集成测试...
小版本内部执行好单元测试就行"
```

## 五、Figma 设计稿驱动开发模式

你是 Figma MCP 的重度用户。Figma 相关提示词有 91+ 条。

**典型句式**：
```
"Implement this design from Figma. @<figma-url> 参考项目中的 <组件名>，在它下面写一个..."
```

**工作流**：
1. 给 Figma URL + 参考组件 + 差异说明（"多了一个描述，少了一个图片"）
2. 明确样式转换规则（"以 @ 开头接英文字母的 less 变量"）
3. 审查时对比 UI 稿逐个 check

**技巧**：你的 Figma prompt 效率很高 —— 一次给出多个 node-id、差异描述、参考组件，AI 能一次做对大部分。

## 八、产品思维

### 8.1 用户视角优先
```
"启动似乎不够友好吧？我还要开多个窗口，执行各自不同的命令，太过繁杂，
我希望的使用效果是：用户通过 pnpm install awf-cli, awf init 之后，
每次只需要 awf run 即可"
```

### 8.2 长期愿景驱动
```
"Claude code 本身就是一个很能干的工程师...我不希望只是给它加技能，
我希望的是开发一个东西，它能借助 AI 自主完成更加复杂的任务"
```

### 8.3 务实的迭代节奏
- 首期简化、先跑通、再完善
- 功能做减法，不做加法
- 通过"测试 → 发现问题 → 修复 → 审查 → 文档"形成闭环

## 九、可复用的提示词框架

### 框架 1：需求提出
```
[场景描述] + [期望效果] + [约束条件] + [参照物]

示例：
"在图片hover之后的按钮后面增加一个关闭icon，点击之后也出关闭弹窗的样式，
同时注意弹窗中功能的抽象，参数的定义，使组件可以适配滑词和图片两个场景，
包括后续可能的扩展。"
```

### 框架 2：Bug 排查
```
[现象] + [排除项] + [怀疑方向] + [验证要求]

示例：
"点击之后页面无变化，控制台没有输出，没有打点，没有触发debugger，
完全无反应...有没有可能是因为点击空白区域收起关闭菜单的逻辑导致？
但是这个关闭逻辑好像是后加的吧？"
```

### 框架 3：架构讨论
```
[抛出问题] + [已有方案及优劣] + [你的倾向] + [讨论边界]

示例：
"当前目录结构合适吗？A 方案显然不太好，B 方案有一定可行性但...
我考虑使用 Hook 配置来实现，可能吗？先讨论不动代码。"
```

### 框架 4：AI 纠偏
```
[否定当前方向] + [指出具体偏差] + [提供正确路径/替代方案]

示例：
"有什么难办的，开关打不了增加个回调参数啊...不要想着配置驱动，
配置太脆弱了...我们是通过组件传参来实现的。"
```
