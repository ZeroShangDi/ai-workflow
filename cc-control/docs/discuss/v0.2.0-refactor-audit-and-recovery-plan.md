人工前置模式会为受影响闭包安装 execution hold；单 agent 和批量调度都必须先原子占用任务再执行，因而 proposal 与派发竞态不会越过人工门槛。第一版限制每项目仅一个开放 proposal，并在审批锁内重新读取 proposal，避免并发审批和多个 hold 造成伪冲突。decision 接线完成后的自动化验证为 98 个测试文件、911/911；lint、架构门禁和完整 build（含 Web 与 pack dry-run）均通过，原有 4 项 `T1-113` 架构豁免未增加。

但上述结果不再作为“功能完成”判据：必须新增真实 server + 真实 MCP 的边界 case，以及真 tmux + 真 Claude 的运行中动态插入/人工批准 case；两者均需定向通过并纳入 `test:real -- --case all` 全量通过，留下证据文件后才能改为完成。

高风险调整的 decision 接线已完成自动化层：proposal 会建立正式 `decision_requested(status=awaiting_human)`，普通 proposal approve/reject 不能绕过；人工通过 `/awf/decisions/<decisionId>/resolve` 给出 approve/reject 后，系统应用或拒绝 proposal，并追加 `decision_completed(status=reviewed, source=human)`。若应用后完成记录写入中断，同 outcome 重试只补记、不重复应用。该结论仍受上述真实测试门槛约束。

### 1.4 原始架构目标发生的变形

#### A. 真正的 per-run sid 被替换成 projectRoot

当前实现不再按 sid 分区磁盘数据，CLI 也明确不向 server 注入 `CC_SID`。这解决了跨项目冲突的一部分，但没有完成原始目标：

- 同一个项目并行两个 run 仍没有可靠身份边界。
- 普通 Claude 会话与 awf 运行会话仍可能互相影响。
- `projectRoot`、run id、CC session id、tmux session 混用了不同层级的身份。

#### B. server 拆分被降级成“不得继续膨胀”

当前 `src/server/server.cjs` 仍有 1491 行，而架构规则允许最多 1600 行。这只能阻止继续明显膨胀，不能证明原始的 handlers/bootstrap/config 等结构拆分已经完成；只剩 109 行余量也说明这不是稳定终态。

#### C. state schema 单一来源没有落地

早期建立的抽象最终因为没有生产引用而被删除。这次删除本身是正确的，但也证明之前相关任务属于“创建了文件或骨架”，而不是“架构已经接线”。

#### D. 最终门禁排在真正架构实现之前

当前依赖关系大致是：

```text
T3-010 ─┐
T3-011 ─┼─> T4-001 ─> T1-113 ─> 未来才创建 A/D 架构任务
T1-120 ─┘
```

所谓最终门禁可以先完成，然后才开始创建原始范围内尚未完成的架构任务。这是规划语义断裂，不是普通的任务遗漏。

后续控制请求返回找不到 session，`T3-011` 留在 active，运行没有正常 settle。`8fa0740` 已经定位这个问题，但只是文档提交，没有修复代码或状态。

### 2.3 动态任务依赖为何断裂

当前调度器的核心逻辑是从任务数组开头开始找第一个 pending 且依赖已经完成的任务。

当 gate 失败后，修复任务被追加到队尾：

```text
原来：
T3-010 -> T3-011

动态添加后：
T3-010 -> T3-010-F1（但 F1 在队尾）

调度结果：
T3-010 被阻塞
T3-011 仍 ready，于是越过 T3-010 继续运行
```

当前已有四组这种“后置添加的前置依赖”：

- `T3-009 → T3-009-F2`

### 3.5 P3：修复导致本次失控的流程机制

#### P3-1 动态任务图必须支持原子变更

增加正式操作：

- `requeue(task)`；
- `supersede(old, replacement)`；
- `insertPrerequisite(task, prerequisite)`；
- state version/CAS；
- active task mutation 保护；
- 自动拓扑排序和环检测。

当 gate 创建修复任务时，应自动得到“修复任务 → 原 gate 重新检查 → 后续 gate”，而不是把修复任务追加到队尾。

#### P3-2 done 状态必须经过结果验证

禁止仅凭文件已创建、导出存在、单元测试通过、“后续再接线”写在结果里，或为了释放依赖而临时标记 done。

对架构任务至少验证：存在生产引用、旧路径被删除或禁止使用、负向架构测试通过、对应用户行为真实执行过。

#### P3-3 active task 增加租约

至少记录 attempt id、worker/server id、startedAt、heartbeatAt、leaseExpiresAt 和 finish reason。server 死亡后，系统应能判断任务是 stale，而不是永久 active。

#### P3-4 修复测试工具的破坏性行为

- 禁止使用广泛的 `pkill -f`；
- 测试进程必须记录精确 pid；
- 测试 server 使用随机端口和独立进程组；
- 测试结束只能清理自己创建的进程；
- 为清理器本身增加元测试。

#### P3-5 合并真实运行测试资产

`tests/eval` 和 `tests/regression` 应合并为单一资产模型，避免重复场景、两套 harness、一套更新另一套过期，以及统计数字互相冲突。
