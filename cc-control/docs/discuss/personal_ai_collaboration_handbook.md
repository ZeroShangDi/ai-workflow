# 第二部分：最高效的 10 个交互模式

## 模式 1：讨论-动手分离法 ⭐⭐⭐⭐⭐

**你的做法**：先抛问题让 AI 思考，明确说"先不动代码"，讨论出结论后再执行。

**优化版**：
```
"我们先讨论 [话题]，不动代码。
 你需要产出：[方案对比 / 流程图 / 目录结构建议]。
 讨论完后我会告诉你下一步做什么。"
```

**为什么高效**：避免 AI 在方向不明确时就开始写代码，减少大量回滚。

---

## 模式 2：逐点推进法 ⭐⭐⭐⭐⭐

**你的做法**：多话题时明确说"不着急进入第二个问题"，一个一个解决。

**优化版**：
```
"我们有 3 个问题要处理：
 1. [问题 A]
 2. [问题 B]
 3. [问题 C]
 先处理问题 1，2 和 3 不要蔓延到当前改动中。"
```

**为什么高效**：给 AI 全局视图但只允许操作局部，防止改动溢出。

---

## 模式 3：竞品参照法 ⭐⭐⭐⭐

**你的做法**：不确定方向时引用竞品行为作为参照系。

**优化版**：
```
"参考 [竞品] 的 [功能] 是怎么做的：[具体描述]。
 我们要达到的效果是 [差异说明]。
 你觉得怎么做最合适？"
```

**为什么高效**：给了 AI 一个具体的 mental model，比抽象描述准确得多。

---

## 模式 4：并行试错法 ⭐⭐⭐⭐

**你的做法**：不确定哪种实现好时，让 AI 每种都生成一版。

**优化版**：
```
"我不确定用方案 A 还是方案 B。你先每种写一版，
 只写核心逻辑不用完整实现，让我对比看看效果。"
```

**为什么高效**：一次对比 > 多次试错。但要注意控制每版的代价（"只写核心逻辑"）。

---

## 模式 5：约束收窄法 ⭐⭐⭐⭐

**你的做法**：AI 过度设计时主动放宽非必要约束。

**优化版**：
```
"这个可以简化：
 - [约束 X] 首期不需要，我们可以先 [简化的做法]
 - [约束 Y] 不是硬性的，如果增加很多复杂度可以不做
 核心只保证 [最关键的 1-2 点]。"
```

**为什么高效**：AI 默认会往完备的方向做，你主动砍需求反而提高质量。

---

## 模式 6：范围锚定法 ⭐⭐⭐⭐

**你的做法**：明确区分"我的需求"和"别人的需求"。

**优化版**：
```
"本期我只关注 [A 模块]、[B 模块]、[C 模块]。
 [D 模块] 的问题可以记录但不需要处理，它不是我负责的。
 不要被牵引到 D 的问题上。"
```

**为什么高效**：防止 AI 发现相关问题后自动扩展范围，导致一次改动过大。

---

## 模式 7：三段式纠偏法 ⭐⭐⭐⭐⭐

**你的做法**：否定方向 → 指出原因 → 提供替代方案。

**优化版**：
```
"这个方向不对。
 问题在于：[具体偏差]。
 正确的做法：[替代方案]，因为 [原因]。
 你重新做一遍，只改 [范围]。"
```

**为什么高效**：AI 从纠偏中能学到你的偏好，后续类似场景犯错概率降低。

---

## 模式 8：分步指令法 ⭐⭐⭐⭐⭐

**你的做法**：复杂任务拆成单步，每步验证后说"继续"推进。

**优化版**：
```
"这个大任务分 3 步：
 Step 1：[做什么] → 完成后告诉我，我验证
 Step 2：[做什么] → 在 Step 1 确认正确后执行
 Step 3：[做什么] → 在 Step 2 确认正确后执行
 现在只做 Step 1。"
```

**为什么高效**：每一步的结果可以独立验证，出错只回滚一步。

---

## 模式 9：上下文重置法 ⭐⭐⭐

**你的做法**：频繁 `/clear` 避免上下文污染。（44 次，使用最多的命令）

**优化版**：
```
在以下场景必须 /clear：
1. 连续对话超过 10 轮
2. 话题从一个模块完全切换到另一个模块
3. 大量粘贴错误日志后
4. 多次纠偏后 AI 还在犯同样的错（说明上下文中的错误信息在干扰）

在以下场景不需要 /clear：
1. 同一个 Bug 的持续排查（需要保留上下文）
2. 同一个功能的逐步实现
```

**为什么需要优化**：有时过度清理会丢失有价值的上下文。区分"该清"和"该留"。

---

## 模式 10：链路检查法 ⭐⭐⭐⭐

**你的做法**：遇到复杂问题时"检查全部链路三遍"。

**优化版**：
```
"检查 [功能] 的完整链路：
 1. 入口：[从哪里触发]
 2. 流转：[经过哪些判断/过滤]
 3. 出口：[最终走到哪里]
 4. 异常路径：[哪些情况下会短路/跳过]

 对每个节点，检查：
 - 是否被执行到？
 - 执行时的数据是否正确？
 - 有没有被其他逻辑拦截？

 产出：[链路文档] + [问题节点标注]"
```

**为什么高效**：把模糊的"检查一下"变成结构化的链路审计。

# 第三部分：低效模式诊断与改进

## 低效模式 1：模糊指令导致的反复确认

**数据**：33% 的提示词在 20 字以内，其中一部分是极简指令如"继续"、"执行"，但也有一部分是上下文不足导致的来回确认。

**实例**：
```
你："为什么不对？"
AI：[猜测原因]
你："不是这个"
AI：[换个猜测]
你："也不是，是 xxx"
```

**改进**：即使在短提示词中，也附上最少量的上下文锚点。
```
❌ "为什么不对？"
✅ "为什么不对？(我说的是第三次提交的 tag 不对)"
```

**规则**：10 字以下的提示词，追加一个括号说明具体指的什么。

---

## 低效模式 2：纠偏时情绪化表达稀释了有效信息

**数据**：49 次以「不/不对」开头的纠偏中，有一部分是先表达了情绪再给具体信息。

**实例**：
```
"靠，太坑了，原来是因为浏览器开了翻译才导致下标不能转换的"  
→ 有效信息："浏览器翻译导致 DOM 结构变化，影响了下标组件"
```

**改进**：把"结论/原因"放在第一位。
```
✅ "根因找到了：浏览器翻译插件修改了 DOM，导致下标组件失效。
    这是偶然发现的，控制台一直没有报错所以排查了很久。"
```

---

## 低效模式 3：多需求混合导致 AI 执行不完整

**数据**：17% 的提示词超过 100 字，其中一部分同时包含 3+ 个需求。

**实例**：
```
"第一，我直接安装应该是和之前的冲突了，还需要把之前删除。
 第二，Readme 文件可以更新了。
 第三，CLAUDE 文件也可以更新...
 最后，好像没有 .gitignore 文件吧？"
```

**改进**：这种一次性提多个需求是高效的，但需要编号 + 每个需求后留验证点。
```
✅ "同时处理 4 件事：
 1. 清理旧安装 → 验证：npm list 不再有旧包
 2. README 更新 → 验证：新用户能按 README 跑起来
 3. CLAUDE.md 合并 → 验证：cc-control 的 CLAUDE 包含了旧的必要内容
 4. 加 .gitignore → 验证：node_modules 不会被 track
 每完成一项告诉我，不要全部做完一起说。"
```

---

## 低效模式 4：排查时跳跃方向导致 AI 上下文混乱

**数据**：有一些 session 中，排查方向发生了 3+ 次跳跃（A 可能 → B 可能 → C 可能）。

**改进**：排查前先列出所有可能，排优先级，逐个排除。
```
"对于 [问题]，可能的原因有：
 1. [原因 A] (概率最高，因为 xxx）→ 先排查
 2. [原因 B] (概率中等）
 3. [原因 C] (概率低，除非 xxx）
 先按 1→2→3 的顺序排查，每排除一个告诉我结果。"
```

---

## 低效模式 5：缺少验证步骤导致"修好了但没完全修好"

**数据**：部分 session 中同一个 Bug 的讨论超过 3-5 轮，说明修复不够彻底。

**改进**：每次修复后主动要求 AI 给出验证方案。
```
"修复后，请你：
 1. 检查是否还有其他调用点存在同样的问题
 2. 列出需要我验证的测试步骤
 3. 标注可能受影响的关联模块"
```

# 第四部分：Skill 模板

将你最常用的工作流固化为 Skill：

```markdown
---
name: my-workflow
description: 我的标准开发工作流 — 需求→讨论→实现→审查→提交
---

## 触发条件
当我说"开始工作流"或处理新需求时自动应用。

## 工作流阶段

### Phase 1: 理解（只读，不动代码）
1. 阅读相关的现有代码
2. 理解当前实现和数据结构
3. 如果有 Figma 链接，调用 Figma MCP 获取设计稿
4. 输出：理解摘要 + 关键发现
5. **等待我确认后再进入 Phase 2**

### Phase 2: 方案（讨论，不动代码）
1. 提出 2-3 个可选方案
2. 每个方案标注：改动范围、风险、复杂度
3. 给出推荐方案和理由
4. 输出：方案对比表
5. **等待我选择方案后再进入 Phase 3**

### Phase 3: 实现
1. 按选定方案实现
2. 每次只改必要的文件，不顺手重构不相关的代码
3. 如果发现有额外需要改的，先问我
4. 完成后自查：
   - 有没有遗漏的边界情况？
   - 有没有影响其他模块？
   - 有没有遗留的调试代码？

### Phase 4: 审查
1. 检查改动是否完全满足需求
2. 检查是否有类似的代码可以复用而不是重复
3. 检查错误处理是否完整
4. 输出：审查结果 + 风险点

### Phase 5: 验证
1. 列出具体的验证步骤
2. 给出测试的边界条件
3. 标注可能受影响的关联功能

### Phase 6: 提交（我控制时机）
1. 生成 commit message（中文，描述改动内容）
2. **不自动 commit，不自动 push**
3. 等待我发出提交指令

## 铁律
- ❌ 绝不自动 push
- ❌ 绝不添加 "Co-Authored-By: Claude"
- ❌ 绝不在 Phase 2 确认前写代码
- ✅ commit message 用中文
- ✅ 每个 Phase 结束等待确认
```

# 第五部分：提示词自检清单

每次发提示词之前，快速过一遍：

## 必检项（缺了大概率要多轮才能补全）

- [ ] **AI 知道我要改哪个文件吗？**（给了路径或明确的组件名）
- [ ] **AI 知道不能改哪些吗？**（明确了修改边界）
- [ ] **我给了足够的上下文吗？**（错误日志、截图、Figma 链接、参考组件）
- [ ] **这是一个需求还是多个需求？**（多个需求时编号了没有）
- [ ] **我需要先讨论还是直接动手？**（明确告诉了 AI）

## 场景专项

### 提需求时追加：
- [ ] 有参照物吗？（竞品怎么做 / 现有哪个组件可以参考）
- [ ] 约束清晰吗？（技术栈限制、兼容要求、文件范围）
- [ ] 优先级明确吗？（哪些必须这期做，哪些可以延后）

### 报 Bug 时追加：
- [ ] 复现路径写清楚了吗？（不是只说"坏了"）
- [ ] 已排除的可能性标注了吗？（帮 AI 缩小排查范围）
- [ ] 控制台/网络/打点信息附上了吗？
- [ ] 环境信息给了吗？（浏览器版本、加载方式）

### 纠偏时追加：
- [ ] 说了哪里不对 + 为什么不对吗？（不只说"不对"）
- [ ] 给了替代方向吗？（AI 知道往哪改）
- [ ] 重申了边界吗？（哪些还是不让动的）

### 讨论架构时追加：
- [ ] 问题描述清楚了？（当前有什么困境）
- [ ] 方案对比了吗？（哪怕只是口头列举）
- [ ] 讨论了边界吗？（哪些这次不讨论、延后）

### Figma 对接时追加：
- [ ] 给了完整 URL（含 node-id）吗？
- [ ] 指定了参考组件吗？
- [ ] 差异说清楚了吗？（和参考组件哪里一样、哪里不同）
- [ ] 样式转换规则声明了吗？（变量名规则、字体规则等）

### 提交代码时追加：
- [ ] 检查过改动范围吗？（没多改不相关的东西）
- [ ] commit message 写好了吗？（中文、描述改动内容）
- [ ] 没有包含 Claude 的署名吗？

## 上下文健康检查（每 10 轮对话一次）

- [ ] 当前对话是否还在同一个话题上？
- [ ] AI 是否开始犯重复的错误？（→ 需要 `/clear`）
- [ ] AI 是否开始"忘记"早期的约束？（→ 需要重新声明）
- [ ] 话题是否已经完全切换了？（→ 需要 `/clear`）

# 附录：一句话速查

| 场景 | 一句话模板 |
|------|-----------|
| 新功能 | "在 [位置] 实现 [功能]，参考 [组件]，注意 [约束]" |
| 改功能 | "把 [A] 改成 [B]，因为 [原因]，不要动 [C]" |
| 报 Bug | "[现象]，已排除 [X/Y/Z]，怀疑是 [假设]，环境 [信息]" |
| 纠偏 | "不对，[偏差]，应该是 [正确方向]，只改 [范围]" |
| 讨论 | "先不动代码，讨论 [话题]，产出 [格式]，不涉及 [延后话题]" |
| 排查 | "检查 [功能] 的链路，从 [入口] 到 [出口]，重点看 [节点]" |
| Figma | "Implement @[URL]，参考 [组件]，差异是 [描述]，规则是 [规则]" |
| 审查 | "审查 [范围]，重点看 [维度1/2/3]，产出 [文档]" |
| 提交 | "可以提交了，只提交 [范围]，用中文 message" |
| 继续 | "继续，下一步" |
| 清理 | "/clear，新话题：[话题]" |
