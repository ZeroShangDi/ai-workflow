| 项 | 内容 |

1. **run 剩余任务里最后四个正是门禁** —— `T3-009` 模块门禁、`T3-010` 文档门禁、

## 三、决策二：护栏 —— 确保新任务不重蹈覆辙

用户明确要求：「一定要确保新的任务不会再出现各种问题」。**不做成"多写几句提醒"，做成机器能拦住的。**

把 `scripts/check-architecture.mjs` 从**取证工具**（现状：退出码恒 0，只出证据）升级为
**会失败的结构门禁**。它现在已能扫真实 `import/require` 边，加不变量即可：

| 不变量 | 拦住的是 |
|---|---|
| `src/` 下零生产引用模块（入口 / 静态资源 / 测试夹具走白名单） | N-2 那一类「建了没人用」 |
| 依赖方向越界（`ALLOWED` 集合已存在） | 分层被绕过 |
| 结构断言：`server.cjs` 行数上限、`src/server/` 不得出现 `.html/.css` | 目标结构回退 |
| 接线任务的验收必须含**引用关系证据** | 「由后续任务执行」式空引用 |

**效果**：每条新任务的 acceptance 都写成 `npm run check:arch 通过` —— **可判定，且推不掉**。
这与 `.awf/issues/002` 的修法一致（「建成」型验收永远推得出去；「零引用」型验收推不掉）。

## 五、任务分解与插入位置（2026-09-11 定稿）

### 5.1 位置设计：靠 deps 表达，不靠数组位置

`findNextTask` = 「数组里第一个 **deps 全满足**的 pending」。位置只影响展示序与并列先后，
**依赖关系必须靠 deps 表达** —— 否则会出两类事故，都真实发生过：

- **空引用**：`T3-011` 的 deps 指向已撤回的 `T1-107` → 永远不可就绪（本文件 §一 排查起点）。
- **抢先跑**：新任务设 `deps=[]` 且**只挂进 `T3-009.deps`** 时，T3-009 被阻塞 →
  扫描继续往后 → `T3-011`（全量真机回归门禁）成为第一个就绪者**抢先跑掉**，
  验收一个还没做的树；新任务随后才跑，**跑完无任何门禁覆盖**（= 重演 issue 002）。
- **自造环**（本次实际踩到并修复）：把**桥接任务 `T1-113`**（deps=`[T1-106]`）一并挂进门禁 deps，
  立刻形成 `T3-011 → T1-113 → T1-106 → T4-001 → T3-011` 的环，全链死锁。
  教训：**挂进某任务 deps 前，先确认那条边不会把下游接回上游**。
  凡动 deps，必须跑全图环检测 + 悬空检测（见 §5.2 规则 3）。

### 5.2 落到图上的三条规则

1. 新任务**同时挂进 `T3-009.deps` 与 `T3-011.deps`** —— 两道门禁都覆盖，且堵死上面的抢先。
2. 桥接任务 `T1-113` 的 deps **指向 `T4-001`**（全链最后一道门禁）—— 保证它在 run 真正收尾之后才被拾取。
   原指向 `T1-106`，2026-09-11 更正为 `T4-001`：`T1-106` 已被用户裁定暂缓，挂在它后面会让责任不可达（见 §四 更正）。
3. 插完用 store 做一次**稳定拓扑重排**（按任务编号），让展示序与依赖序一致。

### 5.3.1 T1-119 落地记录（撤销 T1-094 的「旧页保留」处置）

T1-094 当时的处置是「删除 `ui.html`，**保留** `dashboard/decisions/diagnostics.html` 与 `theme.css/common.js`
作为未构建时的观测页」。T1-119 明确**撤销**该处置：这 5 个文件已删除，`/`、`/diagnostics`、`/decisions`、

- **缺产物不静默**：产物缺失时页面路径返回 **503 + 明确告警**（提示运行 `npm run build`，并给出期望路径），
  同时往 server 日志写一行 `[web] 前端产物缺失` —— 不给空白页、也不静默 404。
- `static.cjs` 的 `defaultAliases()`（无扩展名路径 → 某个 legacy html）一并删除：别名表改由调用方显式给出。
- `check-architecture` 新增结构断言 `server-no-static-assets`：`src/server/` 不得出现 `.html/.css`
  —— 拦住「又往 src/server 里塞页面」的回退。

### 5.4 验收的反重蹈机制（关键）

- **引用关系型验收**：每条任务的 acceptance 必须可判定，形如
  「`grep` 确认零直接 require」「`npm run check:arch --strict` 通过」，
  **禁止**「由后续任务执行」「待接入」这类指向集合的表述。
- **自清豁免表**：`check-architecture` 的 `EXEMPTIONS` 每条必须带 `reason` + `responsible`（责任任务 id）；
  `T1-115`/`T1-117` 的验收 = `--strict` 通过（豁免表为空）。
  这样「待办」从注释变成**会让门禁变红的数据**。
