# 任务拆分器设计（v0.1 草案）

> 2026-08-06 · 承接 [`task-hierarchy-redesign.md`](task-hierarchy-redesign.md)（空间轴/时间轴分离、T1-T9 层级、DFS 后序生成任务、门禁体系）。本稿是任务拆分器整体设计的核心记录，后续以此为准修订。

## 1. 目标

将自然语言需求，经过「对齐 → 范围锁定 → 定级 → 契约 → 拆分 → 派生任务/门禁 → 校验」，产出可直接交给 awf run 执行的 `state.json`。

拆分器的**唯一产物是 state.json**（含 WBS 树 + tasks 列表），中间一切产物（需求文档、契约清单、context）都是过程态。

## 2. 流水线骨架

```
需求描述
  │
  ▼
S0  输入归一化       产出：结构化需求（目标/边界/场景/验收）
  │
  ▼
S1  需求对齐 Q&A     产出：需求文档 —— 范围 100% 锁定（技术细节可 60-70%，范围不行）
  │
  ▼
S2  范围锁定 ⭐      产出：范围声明 {inScope, outOfScope, assumptions, openQuestions=∅}
  │
  ▼
S3  定级             产出：级别（空间层级定位）→ 决定叶子深度 + 门禁
  │
  ▼
S4  结构设计 ⭐      产出：契约清单（跨模块接口/数据模型/共享资源）→ type:contract 节点，最先拆最先做
  │
  ▼
S5  拆分 WBS（DFS）  产出：WBS 树 —— 一条分支拆到底，每分支落盘 checkpoint
  │
  ▼
S6  派生 tasks+门禁  产出：tasks —— 叶子→任务，按层(BFS)平铺，门禁按级别插入
  │
  ▼
S7  校验 + 交付      产出：state.json（schema + 引用 + 一致性 三重校验）
```

**两个关键新增**：S2 范围锁定（可追溯闸是它的落地机制）、S4 契约先行（返工隔离）。

## 3. 核心机制

| 机制 | 一句话 | 解决的硬问题 |
|------|--------|-------------|
| 契约先行 | 阶段间传递类型化产物（有 schema），不传自然语言 | 契约问题、返工 |
| 分层推进 + 中间落盘 | 不在一个上下文里拆完，逐层/逐分支落盘，可中断可恢复 | 上下文过重、已拆的要改 |
| 工具约束 + 校验闸 | 产物只能经工具写入，每阶段出口过校验才能推进 | AI 不按流程走、交付校验 |

## 4. 定级模型（空间层级）

**双轴**：空间轴（怎么拆）+ 时间轴（怎么排期）。任务拆分以**空间轴**为主。

空间层级链：

```
生态 ── 系统 ── 项目 ── 模块 ── 功能 ── 任务(特殊) ── 原子
                        ↑实际范围                    ↑
                  最多系统级、常见项目级以下      几乎不用
```

- **功能 = 默认任务单位**：一个功能 = 一个任务
- 功能复杂 → 向下拆出子任务（**任务级**）
- 功能/模块简单 → 直接收成**模块级任务**，不强拆
- 叶子在「模块级 ~ 任务级」之间浮动，按任务量决定（粒度经济，不追最小）
- **定级 = 在层级链上定位需求 → 决定叶子深度 → 门禁随之确定**

## 5. WBS 模型

节点类型：

| type | 含义 | 角色 |
|------|------|------|
| container | 内部节点，继续拆 | 结构 |
| leaf | 叶子，成为任务 | 任务 |
| contract | 契约节点（接口/数据模型/共享资源） | 任务 + 边界 |
| gate | 门禁节点 | 门禁任务 |

规则：
- **拆分 DFS**：一条分支拆到底再拆下一条。上下文只装一条分支，每拆完一条分支落盘 checkpoint。
- **合成 BFS**：从树按层平铺任务列表 → 同一交付物的叶子相邻、gate 排在它管的叶子之后。
- **只有叶子是任务**；contract、gate 节点也是任务（都要按规则生成 prompt）。
- **叶子停止判据**：能写出具体的、可独立验证的 `done` 条件且不引用子部件 → 停。写不出具体 done → 内部还有可拆的契约/子交付物 → 继续拆。

## 6. 门禁模型

**门禁始终与级别有关**，从树结构 + 级别派生，非手插。

| 级别 | 门禁 |
|------|------|
| 功能级 | **审查** —— 功能拆成多任务时，审查挂功能级父节点，管全部子任务；功能=单任务时，任务后追加审查任务 |
| 模块级 | **测试**（程度见 §7） |
| 项目级 | **端到端测试** —— 是否加，询问用户 |

- gate 的 `deps` = 它管的全部叶子/子交付物 → 执行顺序天然保证"先做，后审/测"。
- 项目级 E2E 是否纳入，由用户确认。

## 7. 测试模型

两族 + 可选：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A 用例审查式** | AI 生成测试用例 → 对着代码链路审查有无问题 | 快、不写测试代码、快速发现问题 | 费 token、有遗漏 |
| **B 代码测试式** | 单元 / 集成 / E2E，写测试代码跑命令 | 结果可靠、不易遗漏 | 需先写测试、变动时要维护测试逻辑 |
| **C 性能/压力** | 压力、性能测试 | 针对性强 | 按需，不常用 |

**未决**：A/B 如何按级别分配（模块级测试用 A 还是 B？）、覆盖率、B 的程度组合。用户明确"测试的程度怎么设计需要考虑"。

## 8. 范围锁定

Q&A 后产出范围声明：

```
范围声明 = {
  inScope:       [{交付物, 验收线}]   ← 每个是"交付物+验收"，不是功能名
  outOfScope:    [显式不做的清单]
  assumptions:   [隐含前提，不锁会漂移]
  openQuestions: []                    ← 必须为空才能进拆分
}
```

三道闸：
1. **冻结闸**：范围声明用户确认后冻结，变更走正式流程。
2. **可追溯闸**（校验器强制）：WBS 每个节点必须追溯到一条 `inScope` 或 `contract`，追溯不到 → 拒绝创建。越界需求在工具层建不进 WBS。
3. **越界即提问闸**：拆分中发现范围外功能，AI 不得自行纳入 → 记入 `out-of-scope-detected`，问用户（纳入 or 排除）。

范围变更流程：改范围声明 → 用户确认 → 受影响子树标 `stale` → 重拆。每步落盘可回滚。

## 9. 上下文管理

- **分层拆分**：L1/L2 一个会话 → L3 每模块一个会话（可并行）→ 叶子按需。
- **懒拆分**：不是所有叶子都在规划期拆出；任务执行期发现可再拆时动态拆。规划期只保证"可执行的骨架"。
- **探索知识落盘**：每层拆分读到的代码理解写 `context.md`，下一层直接读，不重复探索。

## 10. 变更传播

- **版本化 WBS**：重大变更前快照，可回滚。
- **变更传播**：改上层 → 子树标 `stale` → 只重拆受影响子树，差分更新，不全量重拆。
- **契约缓冲**：S4 把跨模块边界定死在契约里，变更大多发生在契约内部，返工被隔离在子树内。

## 11. 流程合规（保证 AI 按流程走）

不靠 prompt 提醒，靠结构：
1. **写入通道唯一**：产物只能经拆分器工具写入（`create_wbs_node` / `create_task` / `advance_stage`），AI 无法直接改文件。
2. **阶段状态机**：拆分器有 `stage` 状态，当前阶段校验通过才能 `advance_stage`。
3. **出口校验**：每阶段一个 schema 校验器，产物不合法进不了下一阶段。

## 12. 交付校验

交付前三重校验：
1. **Schema**：字段完整、类型对、复杂度/status 合法。
2. **引用完整性**：`deps` 引用存在、无环、无孤立；`wbsRef` 指向存在节点；每个 WBS 节点被至少一个 task 覆盖。
3. **一致性**：需求验收标准在 WBS/tasks 有落点；要求的门禁类型都被插入。

校验规则从第 1 阶段开始累积（每阶段出口用同一套），不是最后一刻才写。

## 13. 未决事项

| # | 事项 | 说明 |
|---|------|------|
| 1 | **测试程度分配** | A/B 按级别怎么分、覆盖率、B 的程度组合（模块级到底测多深） |
| 2 | **跨模块依赖** | 横向依赖（A 模块任务等 B 模块接口）如何表达——承接旧文档「接口契约」方向，S4 契约先行是它的落地 |
| 3 | **大模块测试范围** | 模块 20 个功能只改 3 个，全跑不合理——门禁 scope 分级（功能级/影响范围级/全量回归） |
| 4 | **门禁配置化** | 承接旧文档 `.awf/gates.yaml` 方案，还是并入 skill 规则 |
| 5 | **任务 ID / 编号规则** | deps、wbsRef 的引用方案 |
| 6 | **多里程碑** | 是否支持一次规划拆多个里程碑（旧文档结论：不建议超一个） |
| 7 | **S3 契约先行的触发** | 初步定为 M 级必做、S 级跳过（旧文档「接口契约只依赖 T5+ 节点」可参照） |

## 14. 与现有实现的差异（后续落地参考）

| 现状 | 设计目标 |
|------|---------|
| w-plan 一次性拆完，无 checkpoint | 分层 + 中间落盘，可中断恢复 |
| WBS 节点 `{id,name,desc,acceptance,deps}` | + `level` / `done` / `ref` / `type`(container/leaf/contract/gate) |
| 复杂度按关键词推断 simple/medium/complex | 空间层级定位（模块~任务），门禁由级别派生 |
| 阶段链硬编码在复杂度里 | 门禁 = 级别的函数，可配置 |
| 无范围锁定 | S2 范围声明 + 可追溯闸 |
| 无契约先行 | S4 契约清单，type:contract 节点 |
| task.prompt 拼接无规则 | 按 WBS 节点字段（desc/done/ref）拼，规则成文 |
