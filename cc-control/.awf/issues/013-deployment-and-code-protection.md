# 部署形态与代码保护

**一句话**：产品将来要支持「本地部署 + 一定程度的代码保护」，并为「部分或全部云端（SaaS）」留路；
要求不高，**现在不做**，先登记方向与那条必须守住的架构线。

## 一、目标形态（用户 2026-09-13 表述）

1. **本地部署**，做到"前三档"保护即可（不追求绝对防复制）：
   - 代码混淆（javascript-obfuscator）
   - V8 字节码（bytenode）
   - 打包成二进制（Bun compile / Node SEA / pkg）
2. **有能力时做云端**：或整体 SaaS，或**只把 server 放云端**（部分云端）。
3. 要求不高 —— 只要能挡住"顺手复制去卖"这个量级。

## 二、必须守住的架构线（比保护手段更重要）

**核心逻辑必须在 `server/` 内、且只经 HTTP/WS 暴露。**

这是形态切换的前提：
- 走 **SaaS / 部分云端** → 把 `server/` 收到云上，用户拿 `web/`（或桌面壳）；
- 走 **本地部署** → `server/` + `web/` 一起打包。

只要这条线守住，形态切换是**部署方式**的改动，不用重写。**一旦逻辑漏到 `web/` 或 `src/cli/` 里，云端这条路就断了**（用户手里必须有那部分代码才能跑）。

> 这条线正是 2026-09-12 目录重构时定的：`server/` 与 `web/` 平级、能力在 `server/features/`、
> `adapters/` 收口 cc 接入。见 `docs/discuss/server-layering-plan.md`。

## 三、已知的硬限制（诚实记下，避免将来误判）

1. **插件形态必然下发源码**：`plugin/` 下的 MCP server（`.cjs`）、命令、技能必须是**文本**，Claude Code 读的是源码而非字节码。
   → 走插件形态时，**`plugin/` 这一层保护不了**，与 server 无关。
2. **JS 在客户端无法真正防提取**：上述三档都是"提高门槛"，不是"杜绝"。混淆可被还原、字节码可被 dump、二进制可被解包。
3. **本地部署与防复制天然互斥**：真正有效的保护是"代码不落地"（SaaS）。选本地部署 = 接受源码可见，靠 **License + 在线激活 + 服务条款**做商业约束。

## 四、将来真做时的大致顺序（不承诺）

1. 先确认**产品形态**（本地 / 部分云端 / SaaS）—— 这是产品决策，决定后面全部；
2. 若本地：`server/` + `web/` 打包（二进制或 SEA）+ 混淆，配 License 校验；
3. 若部分云端：`server/` 上云，本地只留 `web/` 或桌面壳；
4. 激活/授权链路（在线校验、设备绑定）在 2/3 之后。

## 五、当前决议

- **只登记，不做任何实现**；
- **但要守住第二节那条线**：核心逻辑进 `server/`，只经 HTTP/WS 出；
- 与 `011`（隔离模式删除、真机回归在 run 之外跑）同属"部署/运行形态"话题族，将来可合并评审。
