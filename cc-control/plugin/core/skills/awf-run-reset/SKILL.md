# 反复失败时的重开

当多次修复无法收敛时，回撤当前 task 的改动，复盘后再重新探索实现。不是撤销代码，是重新评估方向和方案。

## 调用时机（AI 判断）

满足任一即考虑调用：

- 同一 task 连续多次失败，且每次修复产生新问题
- 多次修复无进展（修复不改变失败结果）
- 执行方向与预期持续偏离

调用权在 AI 或调用方命令——本 skill 不自行判定"是否该重开"，只负责**判定如何回撤** + **执行回撤** + **触发复盘**。

## 前置判定：如何回撤

| 场景 | 动作 |
|------|------|
| **run 阶段**（`.awf/state.json` mode 为 `run`，自治执行中） | 自动执行回撤，无需人工确认 |
| **非 run 阶段**（人在操作，手动调用） | **先向用户确认**再执行回撤 |

## 回撤执行

### 撤销范围

- **只撤销当前 task 相关修改**：以 `exec.files` + `git status` 对照，精确还原本次 task 产生的文件变更
- **保留无关未提交变动**：更早之前未提交、与当前 task 无关的改动一律不动
- 禁止 `git reset --hard` / `git checkout .` 全量清空
- 若某文件同时含 task 相关与无关的未提交改动 → 该文件不做全量还原，改为人工确认

### 重置任务状态

- `task.status` 回 `pending`
- 清空 `exec.result` / `exec.files`（通过 awf-state MCP tools）

## 复盘阶段（引用）

回撤后**先总结复盘，再重新探索实现**。不要立即动手。

1. **复盘** → 按系统化调试流程执行（不再依赖 superpowers 插件技能）：
   - 清晰描述之前修改的问题是什么
   - 盘算已用过哪些方法、哪些方法尚未尝试
   - 判断最可能的原因是什么
   - 按「根因调查 → 模式分析 → 假设检验」的步骤收敛到根因
2. **重新探索实现** → 按头脑风暴式发散收敛流程执行：
   - 基于复盘结论重新评估需求和方案
   - 更新执行提示词（awf-plan-prompt 产物）
   - 获得认可后再以新方向实现

## 原则

- 重开不是失败，是发现之前的理解不够——用新理解重新出发
- 回撤是手段，复盘才是目的：回撤后必须完成复盘，否则循环会重演
