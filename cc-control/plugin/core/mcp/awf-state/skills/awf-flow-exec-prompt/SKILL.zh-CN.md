# 提示词生成引擎

为 awf-run 的每个阶段生成提示词。核心思路：先用决策表选提示词，再按顺序组装。

---

## 一、提示词字典

按场景分类，标注适用阶段。生成时按决策表从字典选取。

### 进入状态（DEV 开头）

- 先阅读相关代码，告诉我你理解了什么，我确认对不对
- 先复述一遍需求，确保你理解的是我要的
- 告诉我你打算怎么做，不用太细，说思路就行

### 设定模式（DEV、PLAN）

- 我们先讨论清楚再动手，这次不写代码
- 我们快速迭代，每次只改一个小点，改完我验证
- 你自主推进，不用每个步骤都等我确认
- 我们一步一步来，每完成一步等我确认再继续
- 我们一个一个问题解决

### 锁定范围（DEV、DEBUG）

- 只改这一个文件
- 只改当前模块，不要碰其他地方
- 改动越小越好，用最少的代码解决这个问题
- 不要引入任何新的依赖

### 控制深度（DEV）

- 先做最简单的实现，跑通了再考虑优化
- 这是临时方案，不需要考虑扩展性
- 这是长期基础设施，要考虑后续的扩展
- 不需要处理所有边界情况，先把主流程跑通

### 排查定位（DEBUG、TEST 发现问题时）

- 先不要修，先定位根因
- 用排除法，逐个关掉可能的原因
- 从数据流的角度把整个链路走一遍
- 对比正常情况和异常情况的日志差异
- 检查最近的改动，二分法定位是哪个提交引入的

### 审查验证（REVIEW、TEST）

- 审查所有改动，按正确性、边界、耦合、性能四个维度
- 检查有没有影响到其他模块
- 假设这个改动有 bug，最可能在哪里出问题
- 列出所有可能受影响的场景，逐个验证

### 纠偏（任何阶段）

- 方向不对，换一个思路
- 太复杂了，给一个更简单的方案
- 改动范围太大了，只改核心问题
- 不要自作主张加我没有要求的东西

### 回退（任何阶段）

- 刚才的改动全部撤掉，重新开始
- 那个方向放弃，换一个方向重新分析

### 提交（COMMIT）

- 自查一遍：有没有遗留的调试代码、写死的测试值
- 只提交本次改动的文件
- 不要 push
- 用中文写 commit message
- 不要带 AI 的账号信息

### 收尾（FINISH、DOCS）

- 总结这次改了什么、为什么这么改、还有什么没做的
- 更新相关文档，确保文档和代码同步

### UI 稿（涉及 Figma 时）

- Implement this design from Figma. @
- UI稿已更新，先对比和上一版的差异点，再逐个修改
- 参考现有组件的代码风格和目录结构来实现

### 决策（PLAN、遇到阻塞时）

- 给我两个方案，一个激进一个保守，说说代价
- 如果时间只有一半，你会砍掉哪些
- 这个问题的最大风险是什么

## 二、阶段生成规则

每个阶段分两步：**先分析上下文做决策，再按顺序组装**。

### DEV

| 判断条件 | 从字典选 |
|----------|----------|
| task.deps 非空 | [进入状态]：「先阅读相关代码」 |
| 从 DEBUG 回来 | [设定模式]：「你自主推进」 |
| task 复杂、多文件 | [设定模式]：「一步一步来」 |
| task 简单、明确 | [设定模式]：「快速迭代」 |
| 提到具体文件名 | [锁定范围]：「只改这一个文件」 |
| 提到模块/目录 | [锁定范围]：「只改当前模块」 |
| 有"首期""简化" | [控制深度]：「最简单的实现」 |
| 有"基础设施""长期" | [控制深度]：「考虑后续扩展」 |
| 有 Figma 链接 | [UI 稿]：选 1 条 |
| 都不命中 | 默认：「先复述需求」+「改动越小越好」+「主流程跑通」 |

### DEBUG

| 判断条件 | 从字典选 |
|----------|----------|
| 错误含"报错""crash" | [排查定位]：「先定位根因」+「二分法定位提交」 |
| 错误含"不生效""没反应" | [排查定位]：「走链路」+「用排除法」 |
| 错误含"偶发""有时" | [排查定位]：「先确认复现条件」+「对比日志差异」 |
| 无控制台输出 | [排查定位]：「先加日志」 |
| exec.files 1-2 个 | [锁定范围]：「只改引起问题的代码」 |
| exec.files 3+ 个 | [锁定范围]：「不要顺手改其他」 |

### REVIEW

| 判断条件 | 从字典选 |
|----------|----------|
| exec.files 5+ 个 | [审查验证]：「按四个维度全面审查」 |
| exec.files 1-4 个 | [审查验证]：「假设有 bug 最可能在哪」 |
| 任何情况 | [审查验证]：「检查是否影响其他模块」 |

### TEST

1. [审查验证]：「列出所有场景逐个验证」
2. 验证点：正常路径、边界条件、异常路径各至少 1 条
3. 额外检查：控制台、打点、关联功能
4. 发现缺陷 → 追加 [排查定位] 1 条

### COMMIT

无决策分支，固定组装：
1. 自查
2. 约束全选（不 push、中文 message、不署名）
3. 提交范围 {exec.files}
4. 标记 done

### FINISH

| 判断条件 | 从字典选 |
|----------|----------|
| 里程碑 10+ 个 task | [收尾]：「总结改了什么、为什么、还有什么」 |
| 里程碑 <10 个 task | [收尾]：「检查任务 done、文档同步、Issue 清点」 |
| 任何情况 | 遍历 tasks、对比 docs、扫描 issues、lint 检查 |

### DOCS

固定组装：[收尾] 文档相关 + 任务上下文 + 文档范围

---

## 三、风格铁律

1. **场景 + 约束 + 参考** — 先说场景，再说限制，最后给参照
2. **具体不抽象** — 说文件路径不说"相关文件"
3. **先列边界** — 明确告诉 AI 哪些不能动
4. **一个 prompt 一个任务**
5. **互斥显式标注** — "A 和 B 互斥"
6. **调试类带排除项** — 告诉 AI 已排除了什么
7. **中文为主，技术名词保留英文**
8. **不废话** — 直接说事
9. **简洁不啰嗦（弱限制）** — 保留必要信息的前提下尽量短

## 四、上下文装配

| 来源 | 字段 | 用途 |
|------|------|------|
| task | prompt | DEV 核心指令 |
| task | desc | 各阶段描述锚点 |
| task | exec.result | DEBUG 了解改动、REVIEW 知道审什么 |
| task | exec.files | REVIEW/TEST/COMMIT 范围 |
| task | deps | DEV 提示依赖任务 |
| plan | wbs | 整体上下文 |
| milestones | status | FINISH 判断进度 |

## 五、状态更新模板

| 阶段 | 完成后更新 |
|------|-----------|
| DEV | task_status → active, task_result → 写入 exec |
| REVIEW | 通过 → phase → TEST; 不通过 → task_status → active, phase → DEV |
| TEST | 通过 → phase → COMMIT; 缺陷 → task_status → active, phase → DEV |
| COMMIT | task_commit + task_status → done |
| DEBUG | task_status → active, task_result 更新 |
| FINISH | milestone → done, phase → FINISH |
| DOCS | task_result 标注文档已同步 |
