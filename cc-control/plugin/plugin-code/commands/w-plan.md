# w-plan

主规划流程。从一句话需求到完整规划产出的全流程方法论。

## 关联 Skill

- **awf-plan-norm** — 需求规范化（目标/边界/场景/验收标准）
- **awf-plan-wbs** — 生成 WBS 空间树（任务拆分，广度/深度优先遍历）
- **awf-plan-tasks** — 生成任务列表（门禁任务插入）
- **awf-plan-prompt** — 提示词生成（填入任务中的执行提示词）
- **code-context-onboard** — 上下文交接协议（7 段快照格式，上下文不足时触发）

## 执行阶段

1. 需求归一化 → 目标、边界、场景、验收标准（**100% 范围敲定**）
2. 现状分析 → 探索代码库、识别影响范围
3. 自由讨论 → 方案对比、技术选型（**60-70% 技术敲定**）
4. 确定大概架构 → 顶层模块 + 依赖关系的初步草图，作为拆分 checkpoint
5. 逐级产出 WBS 碎片 → 广度/深度优先 loop，只落盘临时文件（**不写 state.json**）
6. 碎片合并 → 将所有碎片拼成完整 WBS 树（共享抽象、位置调整），用户确认
7. 生成 tasks → 基于最终 WBS 派生任务 + 门禁 + 任务层提示词
8. 最后写入 state.json → 整个 plan 阶段**只在最后调用 MCP 改写一次**

## 敲定标准

plan 阶段必须达成：**范围 100% 敲定 + 技术 60-70% 敲定**。

| 产出 | 敲定程度 | 判定 |
|------|---------|------|
| **范围**（inScope/outOfScope） | **100%** | 每个功能点归属明确，outOfScope 显式列出，无 openQuestions |
| **技术细节** | **60-70%** | 技术选型、架构方向、关键约束定，实现层细枝末节不强求 |
| **WBS** | 100% | 叶子节点能写出具体、可独立验证的 done 条件 |
| **tasks** | 100% | 每个任务有 wbsRef/deps/acceptance/prompt，门禁已插入 |

**结果导向**：不管具体技术如何实现，"做成什么样、有什么功能、做什么用、整体大方向"必须在 plan 阶段敲定。**三大核心产出 = 范围 + WBS + tasks**，三者齐备才进入下一阶段。

## 编号规范

WBS 节点与任务的 id 采用 `{前缀}{编号}-{序号}`：

| 前缀 | 含义 |
|------|------|
| `W` | WBS 节点 |
| `T` | 任务（含门禁/契约任务） |

- **编号 = 语义层级自下而上**（对应 awf-plan-level 的「级别↔编号」表）：任务=1、功能=2、模块=3、项目=4、系统=5、生态=6。创建节点时按语义直接定级，不随树深变化——最底下一层是 `W1`，一个需求过来直接定义好是 W 几
- **序号**：同级内 3 位补零递增（001、002…）
- **对齐**：dev 叶子任务 `T1-{序号}` 与其对应 WBS 叶子 `W1-{序号}` 序号一致，靠 `wbsRef` 直接溯源
- **门禁任务**：编号取被管辖节点编号（审查管功能=2、测试管模块=3、文档管项目=4），**序号与被管辖节点序号对齐**——从 ID 一眼溯源门禁管辖谁

示例（项目 → 模块 → 功能 → 任务）：

```
W4-001 图片hover项目
└─ W3-001 图片hover模块
   ├─ W2-001 对话能力（共享）
   ├─ W2-002 缓存能力（共享）
   └─ W2-003 意图识别按钮
      ├─ W1-004 按钮完整链路    → task T1-004（wbsRef=W1-004）
      ├─ W1-005 异常处理        → task T1-005（wbsRef=W1-005）
      └─ 功能级审查（门禁）     → T2-003（对齐功能 W2-003）
   └─ 模块级测试（门禁）        → T3-001（对齐模块 W3-001）
└─ 文档门禁                    → T4-001（对齐项目 W4-001）
```

## 逐级产出 WBS 碎片（loop）

核心机制。WBS 不是一次性拆完，而是多轮对话逐级产出**碎片**，每产出一个节点落盘到临时文件。

> **重要**：本阶段及其后的碎片合并、tasks 生成，都在 plan 对话内完成，**不调用任何 awf-state MCP 工具**。模型直接写 `.awf/plan/` 下的临时文件。state.json 只在最后阶段改写一次。

### 遍历策略（广度优先 + 深度优先）

**模块级及以上广度优先，功能级及以下深度优先。**

```
阶段 A — 广度展开（模块级及以上）：
  拆出全部顶层模块节点 → 形成架构图
  每拆一个节点落盘 checkpoint
  （先把这一层所有兄弟节点拆完，再下钻）

阶段 B — 深度探索（功能级及以下）：
  逐个模块深度优先 → 一路拆到叶子（任务级）
  拆完一个模块的整条分支 → 再进下一个模块
```

**架构图先行**：阶段 A 形成的架构图（顶层模块 + 依赖关系）先给用户确认，架构定再进入阶段 B 深拆。架构错了返工成本最高，必须先定死。

### 循环体（每轮一个节点）

```
while 存在未拆完节点:
  1. 拆当前节点        → awf-plan-wbs（定级→估量→定依赖→下拆一层）
  2. 落盘 WBS 碎片     → .awf/plan/wbs/<node-id>.md
  3. 讨论/决策过程落盘  → .awf/plan/discussion/<topic>.md
  4. 上下文评估         → 不足则触发交接协议（见下）
  5. 全部拆完           → 进入碎片合并
```

节点产出的是**碎片**，不是最终树——每个节点独立成文件，散落存放，不在此阶段做树结构整合。

## 碎片合并（拼图式整合）

所有节点拆分确认完毕后，将散落的碎片**整合成最终的 WBS 树**。这就像拼图、搭积木——最后把碎片合并在一起。

```
1. 收集全部碎片      → 读 .awf/plan/wbs/*.md
2. 拼合完整 WBS 树   → 按层级/依赖关系组装
3. 整合中处理变动     → 在合并时统一处理：
   - 通用功能抽象     → 共享逻辑上提为公共节点（awf-plan-wbs 共享上提规则）
   - 模块/功能位置调整 → 归属不合理的节点移到正确的父节点下
   - 跨模块契约确认   → 接口/数据模型边界在合并时敲定
4. 用户确认最终 WBS  → 确认后才进入 tasks 生成
```

**合并时机**：合并发生在所有碎片产出之后、tasks 生成之前。合并是结构性调整的最后窗口，之后不再大改。

## 生成 tasks

基于**最终 WBS 树**派生任务列表：

```
1. 遍历最终 WBS 叶子 → 每个叶子转为一个 task
2. 插入门禁任务       → awf-plan-tasks（功能级审查 / 模块级测试 / 全局文档更新）
3. 生成任务层提示词   → awf-plan-prompt（只写命令、task ID 和具体目标）
4. 设置依赖关系       → 按 WBS 层级 + 叶子间依赖
```

此时 tasks 仍是 plan 对话内的产出，**不写入 state.json**。

## 最后写入 state.json

整个 plan 阶段**只在最后调用一次 MCP 改写 state.json**：

```
1. 确认范围          → awf_plan_configure（summary/inScope/outOfScope/acceptanceCriteria）
2. 写入 WBS          → awf_wbs_create（逐节点）
3. 写入 tasks        → awf_task_create（逐任务）
4. 其他字段          → 按需更新（里程碑、版本号等）
```

**原则**：
- **前 7 步全部在 plan 对话内完成，不触碰 state.json**
- 最后一步集中写入，一次性落盘最终成果
- 写入顺序按依赖：范围 → WBS → tasks → 其他

## 落盘约定

| 位置 | 内容 | 清理时机 |
|------|------|---------|
| `.awf/context/` | 交接快照 handoff.md（7 段格式） | 下次 run 前 |
| `.awf/plan/discussion/` | 方案讨论、决策过程记录 | 下次 run 前 |
| `.awf/plan/wbs/` | WBS 拆分碎片 + 最终合并树（每节点一个 .md） | 下次 run 前 |

- 目录**运行时 `mkdir -p` 按需创建**，不写入模板骨架
- 碎片/checkpoint 用 markdown（AI 可读可续），完成后保留供 --resume / run 参考
- 临时阶段模型直接写这些文件（不调 MCP）；state.json 最后统一写入

## 交接协议

触发条件：剩余上下文不足以支撑下一个节点设计（对话轮数多 / 主观判断 / 后续可接入量化信号）。

```
1. 生成 7 段快照（Goal/State/Tried/Decisions/Evidence/Feedback/Next）
   → code-context-onboard 格式 → 写 .awf/context/handoff.md
2. 保存当前 WBS 碎片 checkpoint → .awf/plan/wbs/
3. 执行 clear / 重启会话：
   - 交互式会话 → 请求用户 /clear，或退出后用 awf plan --resume 续跑
   - tmux 托管会话 → 经 server /cmd 发 /clear（能力已具备）
4. 恢复：读 handoff.md + wbs 碎片 + discussion 记录（若已到最后写入阶段，再读 state.json），从快照 Next 段继续
```

**原则**：快照必须在 clear 之前完成落盘，否则进度丢失。交接机制的 MCP 化（如 awf-session 增加发命令/交接工具）为后续抽离项（TODO）。

## 产出物

- `.awf/state.json` — 更新 plan 元数据 + wbs + tasks（**最后一次写入**）
- `.awf/plan/wbs/` — WBS 碎片 + 最终合并树（临时，保留至下次 run 前）
- `.awf/plan/discussion/` — 讨论过程记录（临时，保留至下次 run 前）
- `docs/features/<需求名>/` — 需求文档、测试用例

## 门禁检查

每个产出步骤完成后，由 awf-plan-norm 定义的检查规则验证产出是否符合标准。最终 state.json 写入前做完整校验（plan-check 6 项）。
