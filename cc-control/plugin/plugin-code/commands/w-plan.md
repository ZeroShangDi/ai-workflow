# w-plan

将用户目标整理为结构化规划、WBS 和任务列表，并在最终审阅后写入 AWF 规划状态。命令负责阶段顺序、用户审阅与状态写入；各阶段的术语和生成方法由技能提供。

## 按阶段调用能力

| 阶段 | 按需加载 | 产出或决定 |
|---|---|---|
| 需求归一化 | `awf-plan-norm`、`awf-plan-level` | 目标、范围、场景、验收条件和统一术语 |
| 项目现状与方向 | `code-context-onboard`（需要交接时）；按信号加载 `code-tech-selection`、`code-design` | 现状约束、需比较的方案和初步结构 |
| WBS 生成与变更 | `awf-plan-wbs`、`awf-plan-level` | 按层级逐步生成或差分更新 WBS |
| 任务派生 | `awf-plan-tasks`、`awf-plan-prompt` | 依照最终 WBS 生成任务、门禁、依赖和精简提示词 |

按当前阶段加载必要能力；遇到技术选型、架构边界或其他领域问题时再加载相应领域技能，不为规划预加载全部技能。

## 规划流程

1. 将原始需求归一化，确认目标、范围、主要使用场景和可验证验收条件。关键歧义会改变范围或方案时先向用户澄清。
2. 探索理解规划所需的项目现状、技术约束和既有决策。根据实际信号形成技术建议或架构草图；存在会改变设计的未决选择时交由用户决定。
3. 使用 `awf-plan-wbs` 逐级形成 WBS。上下文不足以支撑后续拆分时，先保存可恢复的阶段进度，再按 `code-context-onboard` 交接。
4. 汇总并校验完整 WBS，向用户展示结构、边界和关键依赖；收到审阅意见后更新受影响部分，再进入任务派生。
5. 使用 `awf-plan-tasks` 和 `awf-plan-prompt` 生成任务列表及门禁。检查每项任务是否可独立执行和验收、依赖是否可解析、文件范围是否明确、提示词是否只描述本任务目标。
6. 规划确认且结构完整后，才集中写入 AWF state；前序讨论和 WBS 草稿不提前改写最终 `state.json`。写入时保留已有无关状态字段。

## 交付与状态边界

- 最终规划需包含规范化目标与边界、确认后的 WBS、任务列表及其依赖和验收条件。
- 编号、层级、门禁归属、任务字段和提示词格式遵循对应 `awf-plan-*` 技能；命令不复制其细则。
- 方案或范围改变时同步更新受影响的 WBS 子树和派生任务，不全量重写无关规划内容。
- 用户尚未确认会改变范围、架构或任务切分的关键选择时，暂停依赖该选择的规划和状态写入。
