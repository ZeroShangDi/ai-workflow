# w-dev

以满足目标和风险要求的最低成本路径完成开发任务。普通交互直接使用用户目标；只有输入能解析为 AWF task ID 时才进入 AWF 任务流程。

## 建立目标

1. 输入能解析为 task ID 时，加载 **awf-task-context**，读取目标、范围、约束、验收和必要依赖；读取不到则按普通交互处理。
2. 普通交互不读取 `.awf` 状态，不启动 AWF，也不要求补造 task ID。
3. 只探索理解目标和安全修改所需的代码、仓库说明与当前变更；信息不足且不同答案会实质改变结果时再询问。

## 实现前的必要判断

每个任务先结合现有实现回答下列问题，判断深度与风险相称；局部任务可简短完成，无需生成独立设计文档。

- **行为与失败**：什么必须始终成立？检查正常路径以外与任务有关的状态组合、空值、重复操作、异步乱序、取消/卸载、错误恢复和数据一致性。把最可能破坏约束的情形变成可执行验证；不要只照抄需求中的示例。缺少会改变行为的约定时先澄清。
- **职责与边界**：谁拥有状态和业务决策？组件负责什么，模块对外提供什么？优先复用现有权威实现，使展示、业务规则和副作用各有归属。抽象依据独立职责和已出现的变化，避免万能组件、布尔开关堆积、重复规则，也不为假想需求搭框架。
- **成熟解法**：从零搭建、新增独立子系统、复杂但常见的能力，或自研有明显协议、安全及维护负担时，先查项目已有能力；若不足，先选型再实现。复用对象包括架构方法、协议、脚手架、插件和组件，不只是依赖包。不要把沿用项目风格或询问语言偏好当作选型。局部修复、简单业务逻辑及已有合适方案不重复调研。
- **影响范围**：预计修改哪些位置，各自为何必要？查看已有未提交改动。明确用户文件预算；新增模块、依赖或公共接口要能解释收益。任务较大时向用户简要说明边界及主要风险，再开始实现。

以上判断用于发现路由信号，不因少加载 skill 而跳过。只有已确认沿现有模式即可满足行为、设计和质量要求时，才直接实现。

## 按判断结果选择能力

| 可观察信号 | 按需加载 | 用于决定 |
|---|---|---|
| 从零搭建、独立子系统或复杂常见能力缺少已确认适配的方案；自研负担明显，现有方案不适配，或用户明确要求选型 | **code-tech-selection** | 先形成成熟方案/必要自研的推荐及关键验证，再进入实现；不以用户主动提出选型为前提 |
| 新增或重组组件/模块，改变状态归属、公开契约，或变化跨越多个模块 | **code-design** | 规则归属、模块边界、变化路径及代码结构；仅此时读取相关架构地图 |
| 改动公共 API、共享基础设施、高回归影响区域，或自查发现复杂控制流及难以解释的职责 | **code-quality** | 质量目标、风险判断与验证证据；通用可读性基线始终适用 |
| 用户提出性能目标，或证据指向真实热点 | **code-performance** | 测量、瓶颈和优化方案 |
| 涉及外部输入、认证、授权、秘密或敏感数据边界 | **code-security** | 必须满足的安全约束 |
| 涉及旧调用方、旧数据、新旧实现共存或多端能力差异 | **code-compatibility** | 契约差异、切换/迁移路径及退役条件 |
| Vue 或 React 任务遇到框架特有的实现取舍 | 匹配的 **code-vue** 或 **code-react** | 框架内方案；两者不同时加载 |

不要因为某项能力“可能有用”就预加载。多个信号同时成立时组合职责互补的 skill；Vue/React 和安全技能不能替代职责设计或业务正确性分析。依赖顺序由决策决定：先确定职责和约束，再落实框架实现，最后验证风险。复用已有结论和已加载内容，避免重复探索。

选型信号成立时，在铺设项目骨架或自写通用能力前完成必要调研与关键验证；将推荐方案、接入边界和未验证项交给设计及实现。已有结论且约束未变时直接沿用，不因加载另一个技能而重新选型。

## 实现与调整

1. 沿现有权威边界做最小、可审查的修改，不夹带无关清理或假想扩展。
2. 优先完成能验证核心行为及关键失败路径的小步改动。每次影响面超出预测，先解释新增位置是否必要；发现同一规则散落或跨层耦合时重新选择设计/架构能力。扩大任务范围或突破用户文件预算前先取得确认，不能通过挤进一个大文件规避。
3. 执行中出现新的设计或风险信号时再升级能力；没有新证据时不要把简单任务升级成完整工作流。
4. 当前方案连续失败、修复不产生新信息或方向持续偏离时，才加载 **awf-run-reset**；其回撤行为服从当前是否处于 AWF run 模式及用户授权。

## 验证与完成

- 按实现前识别的约束和失败路径验证行为，补充实现过程中发现的风险。类型检查、lint 和构建不能代替行为验证；没有可运行验证时说明尚未证明的部分。
- 公共契约、跨模块传播、构建配置或高风险边界发生变化时，扩大到相关集成或全量验证。
- 检查本次实际 diff：每处改动是否必要、是否重复维护同一事实、是否夹带无关格式化或清理；保留用户已有改动。文件数用于发现异常传播，不能作为架构好坏的唯一指标。
- 以维护者视角复查：命名是否表达业务意图，控制流能否直接读懂，状态与副作用归属是否清楚，组件接口是否暴露了过多内部细节。用任务已存在的一种合理变化检验修改是否集中；发现问题就局部修正，避免顺手开展重构。
- 普通交互只报告实际结果、关键文件和验证结论，不生成固定格式报告。
- AWF task 只有在验收全部满足后才调用 `awf_task_complete`，原子记录结果、实际文件和必要的架构变化；加载 `code-design` 时将变化轴、权威边界、选择路径、边界是否变化及关键取舍写入 `exec.architecture`；未完成则继续处理或准确标记 blocked。
- 非 AWF 调用不得执行 AWF 状态落账。
