# w-review

对指定改动做有证据的代码审查。先界定审查目标与范围，再根据改动涉及的风险加载专项审查方法；不预加载全部技能，也不因发现风格偏好扩大审查范围。

## 建立范围

1. 输入含 task ID 时，加载 `awf-task-context`，读取目标、范围、约束和验收条件。
2. 按用户指定的范围审查；未指定时，以当前任务改动或当前 diff 为准。需要时查看相关调用方、测试和约束，避免孤立阅读单个文件。
3. 审查以发现问题为主；未经用户要求，不直接修改被审查代码。

## 按信号加载专项审查

| 可观察信号 | 按需加载 | 关注点 |
|---|---|---|
| 输入、身份、权限、敏感数据、网络或依赖供应链边界发生变化 | `code-review-security` | 可利用路径、影响、证据与防护缺口 |
| 安全审查需判断具体防护方式或修复控制 | `code-security` | 对应领域方法与匹配知识；不默认读取整库 |
| 改动触及已知关键路径、容量目标、资源热点，或用户要求性能审查 | `code-review-performance` | 真实负载下的性能风险和证据；不按固定阈值猜测 |
| AWF 审查任务；或普通审查中模块职责、依赖方向、公共边界、状态所有权发生变化，或用户要求核对架构地图 | `code-review-architecture` | 变化是否落在正确边界，目标项目的适用架构约束是否有实际证据 |
| 需要设计或检查测试场景 | `code-test-case` | 依据行为、状态和失败条件补齐有区分力的用例 |

其余改动直接依据目标、既有契约和相关验证检查正确性、失败路径、清晰度及范围。专项信号不存在时，不加载对应技能；不要为了维持技能清单而机械逐项检查。

## 结论

- 发现按影响排序；阻断发布的问题标为「阻塞」，会造成明显行为、安全或性能损害的标为「严重」，其他真实但非阻断的问题标为「建议」。不为风格偏好或纯假设创建发现。
- 每项发现给出严重程度、位置、可观察影响、证据和可执行的修复方向；区分已证实问题与待确认风险。
- 只报告能由代码、调用链、约束或验证结果支持的问题；不要把偏好的写法包装成缺陷。
- 没有发现问题时，说明审查范围及未覆盖的重要部分，不推断整个系统均无风险。
- 加载 `code-review-architecture` 时，按该技能要求提供架构结论；未加载时不强制输出架构专用 verdict。
- AWF 审查必须在 `RESULT` 中包含 `architecture`：`changeAxis` 为主要变化轴，`boundary` 为权威边界，`path` 为 `extend|refactor-then-change|split`，`boundaryChanged` 表示边界是否实际改变，`note` 记录审查证据与关键取舍；非 pass 时还须指出修复方向。普通审查无需固定 JSON 字段。
- 含 task ID 的任务按 AWF 流程记录审查结论；普通交互不写 AWF 状态。
