# 兼容与迁移

兼容判断变化是否破坏既有使用方依赖的行为；迁移设计系统如何从旧状态转到新状态。小到函数或组件替换，大到协议和数据升级，都可能涉及兼容；迁移只是其中需要处理状态转换的一类任务。

## 核心判断

- **先找依赖，再谈兼容。** 沿实际调用方、运行路径和数据流确认哪些行为被依赖；接口形状相同不代表默认值、时序、错误和副作用也兼容。
- **按契约差异选择切换方式。** 新旧实现满足同一契约时可直接替换；契约有差异时，判断是否用边界适配、分批迁移调用方或集中切换。不要默认保留双实现。
- **把差异限制在明确边界。** 适配器、兼容层、能力检测和版本协商都是手段；它们应转换可解释的差异，不应把不支持或语义不等价伪装成成功。
- **只为可达的过渡态承担运行正确性。** 开发中尚未交付、不会被调用的中间状态，无须满足生产契约。若新旧实现会并行可用，就明确各自适用范围、共享状态的归属、关键行为与退出条件；按风险决定是否分批，而不是按工作量决定。
- **兼容需要范围和终点。** 明确支持哪些调用方、版本、环境和期限；为临时适配设定观测方式与移除条件，避免兼容分支永久化。
- **迁移要处理状态转换。** 除目标结果外，判断中断、重试、并发访问、部分完成和恢复；代码回滚不一定能恢复已变更的数据。
- **验证结论不能超出证据。** 在真实消费者和入口验证旧行为、新行为及并行路径；类型、构建、替身或接口形状通过，都不能单独证明端到端兼容。

## 处理步骤

1. 找出真实使用方以及它们依赖的可观察行为、数据和运行条件。
2. 对比旧、新契约，标出相同点、差异点和必须保留的不变量。
3. 根据差异、共存风险和恢复能力选择直接替换、边界适配、分批迁移或集中切换，并明确支持范围。
4. 验证实际调用路径与关键反例；若新旧并行，额外验证路由、共享状态和收敛条件。
5. 说明未覆盖的使用方、不可逆影响及兼容机制何时退役。

当兼容目标、实际依赖或迁移约束不确定，且答案会改变方案时，先向用户追问。涉及破坏既有契约、不可逆数据变化、停机或支持范围改变时，不自行假设；迁移方案交由用户审阅后再定稿。

不必逐项汇报常规实现手段或模式名称。若方案会改变用户可见行为、支持范围、数据结果，或带来值得权衡的长期维护成本，应向用户说明影响与取舍；需要改变已确认的设计约束时先征求意见。
