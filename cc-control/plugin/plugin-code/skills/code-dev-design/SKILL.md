# 架构与模块设计

设计的核心是让每个业务决策有清晰归属，让变化沿合理边界传播。

## 设计判断

- **职责归属**：识别谁拥有状态、业务规则和副作用，避免同一决策由多个模块分别维护。
- **模块边界**：根据职责与变化原因划分模块，明确对外接口和依赖方向；调用方只依赖完成任务所需的契约。
- **变化落点**：判断需求能否由现有边界承载；若不能，确认需要调整的边界及其依据，避免平行机制和假设性扩展点。
- **抽象依据**：依据真实职责、共同变化原因和实际复用决定是否抽象或拆分，不以代码相似、文件规模或模式名称单独裁决。
- **影响范围**：检查变化对调用方、数据、公共契约、依赖方向和验证的影响，确保相关改动都能由当前目标解释。

设计判断以语义归属和变化传播为依据，不以文件数或代码行数代替。

## 设计过程与审阅

- 先理解目标、约束和已有结构。遇到不确定前提时向用户追问；尤其是可能改变职责边界、接口、依赖、交互时序或部署方式的事项，不要自行假设后定稿。
- 明确各部分的职责、状态归属、交互过程与失败情形，再决定模块边界和代码组织；目录结构应表达职责和变化边界，避免结构与实现细节混杂。
- 给出设计理由和大致代码结构，并交由用户审阅；根据反馈调整，用户认可后再视为定稿。
- AWF run 等无人值守模式下，先依据明确的用户授权和项目约定进行内部审查。若存在会改变设计的未决问题或缺少继续所需的授权，标记为 `needs_user_review` 并停止依赖该决定的工作；仅在方案明确、影响较小且可逆时，才可采用保守选择继续，并注明设计未经用户审阅。内部审查不得表述为用户已批准。

## 按需经验

需要具体实现经验时，根据任务关键词检索同级 `knowledge/`，只读匹配条目；没有匹配经验时按上述判断原则处理，不读取整库。
