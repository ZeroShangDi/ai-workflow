# 架构审查

从任务目标和完整 diff 出发审查变更传播，不逐文件孤立打分，也不因文件多而直接否决。

读取任务的 `exec.architecture` 与 `.awf/context/architecture.md`（存在时），但以实际代码和依赖关系为准。依次判断：

1. 需求的主要变化轴是否由明确的权威边界承载。
2. 同一业务判断是否被复制到多个模块，尤其是散落的类型/场景分支。
3. UI、存储、传输等细节是否越权决定领域行为，或产生反向/循环依赖。
4. 新抽象是否来自真实变化轴；共享实现是否因调用方差异不断增加特例。
5. 应重构时是否只做了补丁堆叠；不应重构时是否扩大了无关影响面。
6. 同类需求再增加一个实例时，预计修改是否能集中在当前扩展点。
7. 测试是否验证稳定行为，并允许内部结构安全演进。

## Verdict

- `pass`：变化沿合理边界发生；局部权衡不会显著增加下一次变更成本。
- `changes_requested`：方向可修复，但存在决策散落、依赖越界、错误抽象或应收敛而未收敛。
- `fail`：核心边界选择错误，继续局部修补会扩大结构损害，需要重新设计或拆分。

非 pass 时，结论必须指出：变化轴、被破坏的边界、证据位置、期望的权威归属和修复方向。不要只写“可维护性差”或“文件太多”。

在门禁 RESULT 中同时返回结构化架构审查信息：

```json
{"architecture":{"changeAxis":"变化轴","boundary":"期望边界","path":"refactor-then-change|split","boundaryChanged":true,"note":"证据与修复方向"}}
```

若审查确认了新的长期模块职责、依赖规则或扩展方式，修复并复审通过后再更新架构地图；失败轮次不写入未验证的设计。
