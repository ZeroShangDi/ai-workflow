# 上下文接力协议

> 参考：[REMvisual/claude-handoff](https://github.com/REMvisual/claude-handoff) — 7 段快照格式

当 AI session 断裂时（阶段切换、上下文压缩、冷启动），如何让下一个 AI 快速接手。

## 上下文传递格式（Handoff Snapshot）

每次上下文断裂前，生成 7 段接力快照：

| 段 | 内容 | 说明 |
|----|------|------|
| Goal | 当前要达成的目标 | 一句话 |
| State | 当前进度 | 完成了什么、正在进行什么 |
| Tried | 已尝试的方案 | 试过什么、为什么没继续 |
| Decisions | 已做的决策 | 技术选型、方案取舍、原因 |
| Evidence | 关键发现 | 探索结果、踩过的坑 |
| Feedback | 用户反馈要点 | 偏好、纠正、确认 |
| Next | 下一步行动 | 接手者应该做什么 |

## 三种上下文处理手段（按场景选）

| 手段 | 处理对象 | 场景 |
|------|----------|------|
| 压缩（Compaction） | 整个对话历史 → 摘要 | 对话快满窗口，整体浓缩 |
| 清除（Clearing） | 过期的大 tool 结果 | 结果可重新获取（文件、API 响应） |
| 记忆（Memory） | 跨 session 持久化 | 跨天/跨阶段的长期上下文 |

对应到 awf：阶段间用**快照**（压缩），大文件/长输出用**引用**（`file:line` 代替全文——可重新读取，不要复制），运行状态用 **state.json**，项目结构认知用 **`.awf/context/architecture.md`**。

## 项目架构上下文

开发任务冷启动时，在探索实现前读取 `.awf/context/architecture.md`。它只保存已确认的项目事实：核心概念、模块职责、依赖方向、真实变化轴与扩展方式。

- 文件仅有初始化注释、尚无项目事实时，从当前任务涉及的代码中补充足够支撑本任务的局部模型，不要求扫描全仓库。
- 只有实现或复审确认改变了模块职责、依赖方向或公共扩展方式时才更新。
- 不写通用原则、文件清单、临时实现细节和任务流水账；不确定的推测不落盘。
- 上下文压缩快照引用架构地图，不复制全文；接手者先读架构地图，再继续实现。

## 压缩规则

当对话历史过长需要压缩时：

1. **保留**：决策记录、错误信息和修复、用户明确确认的偏好、下一步计划
2. **丢弃**：探索过程中的死胡同、已解决的中间态讨论、纯过程性对话
3. **重写**：将散落的多个消息合并为结构化的快照

### 标识符必须原样保留

UUID、文件路径、URL、哈希、端口号等不透明标识符**逐字保留**——一旦被摘要改写，接手者就无法对应到真实资源。压缩时对这类内容不可意译。

### 缓存友好

压缩触发点别太早（频繁压缩本身耗上下文），也别太晚（临近上限时模型已失去早期决策的连贯性）。分阶段预留：到窗口 ~65-80% 时先写快照 + 落 state.json，再继续。

## 原则

- **快照是给 AI 读的**，写清楚"为什么"比"是什么"更重要
- 压缩不是丢失，是重新组织——决策和坑要留下，过程可以丢
- 宁可多保留一条决策，不少保留一个坑
- 大体积可重新获取的内容（文件内容、长日志）用路径/引用代替全文
- 接手者先读 Goal → Decisions → Evidence，再读 State → Next，避免从零摸索

## 快照质量检查

- [ ] Goal 一句话能说清吗？
- [ ] 已做的决策都有"为什么"吗？
- [ ] 踩过的坑（Evidence）记录了吗？
- [ ] 标识符（路径/ID/URL）是原样还是被意译了？
- [ ] Next 是具体行动，不是"继续推进"这种空话吗？

## awf 接入：CLI 任务前上下文检查（自动触发）

`awf run` 在每个任务执行前（跳过第一个任务）做上下文压缩检查，分两层：

- **第一层（CLI，免打扰）**：读 statusline 实测占用，低于过滤阈值（默认 80%）→ 直接发任务，不触发本技能
- **第二层（AI，仅占用 ≥ 阈值或无实测时触发）**：发 context-check prompt，本技能做一次**纯判断轮**。执行协议：

1. **确定上下文占用** — 优先用 prompt 里的 statusline 实测值（`已用约 X%（statusline 实测）`）；若无实测（`未知`，statusline 未配置），再按对话轮数与体积估算（不必精确）。
2. **判断是否需要压缩**（结合下个任务体量）：
   - 占用明显充足（明显低于窗口 ~65%），或虽接近阈值但下个任务轻量、可安全完成 → 只需回复 `AWF_CONTEXT_OK`。不做任何任务工作、不修改任何文件。
   - 占用已接近/超过窗口 ~65%，且下个任务仍需较多上下文 → 执行压缩准备，四步：

   ```
   a. 生成 7 段交接快照（上面的格式，标识符原样保留）
   b. 写入 .awf/context/handoff.md（目录不存在则创建）
   c. 调用 awf_context_ready 通知 CLI 快照已就绪
   d. 回复 AWF_CONTEXT_READY，结束本轮
   ```

4. **CLI 收到通知后**执行 `/clear` 清空对话，把 handoff.md 内容前缀注入下一个任务 prompt —— 接手者从快照拿到 Goal/Decisions/Evidence，再从 State/Next 起步，无需从零摸索。

关键点：

- **这是纯判断轮**：无论判断结果如何，本轮都不开始执行任务、不调任务相关工具。判断完就停。
- **压缩触发后上下文会归零**：所以快照必须写全决策和坑（对应"宁可多保留一条决策"），标识符原样保留，否则接手者无法对应真实资源。
- **大体积内容用引用**：快照里不要粘贴大段文件/日志全文，用 `file:line` 引用，接手者可重新读取。
