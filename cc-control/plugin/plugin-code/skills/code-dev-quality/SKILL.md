# 高质量代码最佳实践

行为准则见 code-dev-rule，这里是"好代码长什么样"的质量标准。

## 质量维度

代码质量不是单一指标，是五维度的合力：

| 维度 | 定义 | 判断方法 |
|------|------|---------|
| 正确性 | 逻辑对不对、边界/错误路径是否覆盖 | 测试 + 审查 |
| 可读性 | 没写代码的人多快能看懂 | 人审（命名、结构、意图） |
| 可维护性 | 改一个功能不炸另一处 | 复杂度指标 + 结构审查 |
| 可测试性 | 多容易写自动化测试 | 耦合度、接口清晰度 |
| 效率 | 资源消耗是否合理 | 测量（见 code-dev-performance） |

## 正确性

- 边界条件有处理（空值、极值、并发）
- 错误路径有覆盖（网络失败、超时、权限不足）
- 状态转换有明确的触发条件和目标状态

## 可读性

- 代码自解释：好的命名 > 注释；代码要"讲故事"
- 注释只解释"为什么"，不解释"是什么"；需要解释"是什么"时改命名
- 函数长度：能在一屏内看完（目标 20 行内，上限 50）
- 嵌套深度：不超过 3 层，多用早退守卫
- 文件长度：100-300 行健康，>400 行考虑拆分

## 可维护性

- 一个修改只影响一个地方（DRY）
- 相似代码到第 3 次才抽象（Rule of Three），避免仓促抽象（AHA）
- 硬编码值提取为常量或配置
- 魔法数字命名；枚举替代魔法字符串
- 圈复杂度 ≤10，超了拆分
- 继承深度控制在 1-3 层；耦合越低越好

## 可测试性

- 纯逻辑与副作用分离，纯函数易测
- 依赖注入优于全局状态——测试能换实现
- 接口清晰、松耦合——一个改动只动一处测试
- 行为驱动测试，AAA 结构（Arrange-Act-Assert）

## 防御性

- 外部数据不信任（API 响应、用户输入）
- 类型系统充分利用（TypeScript 严格模式）
- 断言和类型守卫在边界处
- 深度安全实践见 code-dev-security

## 量化检查（选 3-5 个持续跟踪）

| 指标 | 阈值 | 说明 |
|------|------|------|
| 圈复杂度 | ≤10 | >20 易藏 bug |
| 维护指数 | ≥85 | 趋势比绝对值重要 |
| 测试覆盖率 | 关键路径 100% 优先 | 覆盖行为不追百分比 |
| 重复代码 | 趋零 | 重复 = 重复的 bug |
| 代码churn | 观察 | 高 churn = 不稳定或需求不清 |

指标单独看会骗人：覆盖率 90% 但圈复杂度失控，代码照样烂。趋势比单点值重要。

## 持续保障

- 每次提交跑 lint + 测试，用 CI 兜底
- review 时对照本 skill 的维度逐项检查
- 技术债要可见：`// TODO(username): <要改什么> <日期>`，进 backlog
