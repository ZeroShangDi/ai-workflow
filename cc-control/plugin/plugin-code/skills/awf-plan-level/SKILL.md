# 术语与级别规范

全项目描述用词和层级划分遵循本规范，禁止混用「需求/功能/模块」等近义词。

## 级别定义（决定深度）

```
生态，系统，项目，模块，功能，任务。
```

**级别是种类，不是大小。** 每个级别对应一种边界，判一个东西的级别 = 看它顶在哪种边界上：

| 级别 | 边界类型 | 判据（问一个问题） |
|------|---------|------------------|
| 任务 | 提交边界 | 一次 commit 能完成且能验证吗？ |
| 功能 | 验收边界（锚点） | 能独立说「做成/没做成」吗？ |
| 模块 | 内聚/演化边界 | 这一坨是不是「一起改、一起懂、一起交付」？ |
| 项目 | 交付边界 | 是不是一个仓库 / 一次交付目标？ |
| 系统 | 部署边界 | 能独立部署、独立运行吗？ |
| 生态 | 集成边界 | 多个系统如何交互？ |

- **功能是锚点**（验收边界，客观可判）；向上都是「聚合」，向下都是「执行」
- 功能 = 默认任务单位；简单可收成模块级任务，复杂向下拆出任务级
- 叶子在「模块 ~ 任务」级按任务量浮动（粒度经济）
- 大多数单仓库项目从「项目」级起步，生态/系统仅多系统集成时用到

### 级别 ↔ 编号（绑定）

级别直接烙进 ID，创建时定级即编号，不需二次判断。**编号从任务级向上数**，与「级别是种类」一一对应：

| 级别 | 编号 | WBS 节点 | 任务（含门禁） |
|------|------|---------|---------------|
| 任务 | **1** | `W1-{序号}` | dev 叶子任务 `T1-{序号}` |
| 功能 | **2** | `W2-{序号}` | 审查门禁 `T2-{序号}`（管辖功能子树） |
| 模块 | **3** | `W3-{序号}` | 测试门禁 `T3-{序号}`（管辖模块子树） |
| 项目 | **4** | `W4-{序号}` | 文档门禁 `T4-{序号}`（管辖整树） |
| 系统 | 5 | `W5-{序号}` | 系统级门禁 `T5-{序号}` |
| 生态 | 6 | `W6-{序号}` | 生态级门禁 `T6-{序号}` |

- ID 格式：`{前缀}{编号}-{序号}`，前缀 `W`=WBS 节点、`T`=任务
- **门禁任务级别 = 被管辖节点级别**（审查管功能=2、测试管模块=3、文档管项目=4），**序号 = 被管辖节点序号对齐**（审查 `T2-003` 对应功能 `W2-003`），从 ID 一眼溯源门禁管辖谁
- dev 叶子任务 `T1-{序号}` 与其对应 WBS 叶子 `W1-{序号}` 序号一致，靠 `wbsRef` 溯源

## 模块与功能（判据）

**模块 ≠ 功能：模块是容器，功能是叶子。** 判据是「可独立验收性」：

- **功能** = 模块内可独立验收的最小逻辑单元 = WBS 叶子。拆到拆不动、每个都能单独验收的粒度就是功能。
- **模块** = 功能的聚合域。本身不可单独验收，只是把若干「一起演化」的功能装起来的容器。

判定一个东西是模块还是功能，问两句：

1. 它能不能继续拆出多个「可独立验收」的单元？（能 → 模块）
2. 它本身能不能单独验收？（不能 → 模块）

**模块身份由「是否独立成域」决定，不由大小决定。** 字典、日志很小，但独立成域（各有自己一套功能），所以是模块；任务小是执行粒度，与模块无关。

## 拆分轴（决定切法）

级别是「这算什么种类」，拆是「怎么切」。**拆分轴不由固定规则决定，由项目主要复杂度来源决定：**

| 项目性质 | 主要复杂度来源 | 模块轴 | 例子 |
|---------|--------------|--------|------|
| 业务产品 | 业务领域 | 业务能力轴 | 用户/权限/字典/日志 |
| 基础设施/工具 | 运行时架构 | 架构组件轴 | cli / server / plugin |
| 框架/引擎 | 技术原理 | 技术子系统轴 | 响应式 / 运行时 / 编译器 |
| 复用库 | 复用单元 | 复用单元轴 | 组件族 / 单组件 |
| 内容站 | 信息结构 | 内容域轴 | 产品 / 文档 / 定价 |

判定方法（三步）：

1. **听语言**：项目里的人怎么称呼「它的部分」？这些词就是模块（领域语言）。
2. **验证轴**：一次典型功能改动，是否被限制在单模块内？
3. **命名即判据**：模块名必须是领域语言里的自然词；禁止 lib / shared / common / util 这类位置词。

## 跨轴原则

- **每级一个主导轴，换轴只发生在降级时**（跨级交叉，健康）。例：模块层用架构轴（cli/server/plugin），功能层换功能轴（state/run/gate-fix）。
- **同级别混轴 = 反模式**（N×M 网格：责任碎片化、归属模糊、依赖失控）。
- 例外：组织/Conway 轴与架构轴同层刻意对齐（团队边界 = 模块边界）合法。

## 级别与拆分的关系

- 两个**正交维度**：级别是空间分类（跨级别），SPIDR 是时间演化（级别内，由简到繁）。SPIDR 拆出的仍是功能，不跨级别。
- 拆分轴决定「候选分组长什么样」，级别定义决定「这个分组算什么种类」。
- **先定主拆分轴，再谈级别**：轴不定，级别定义是空谈；级别不定义，拆分是任意切。

## 术语表

| 术语 | 定义 | 对应 |
|------|------|------|
| 模块 module | 功能聚合域，按内聚/演化边界切；本身不可单独验收 | `docs/features/<module>.md` |
| 功能 feature | 模块内可独立验收的最小逻辑单元 = WBS 一个叶子节点 | `docs/features/<module>/<req-id>.md` |
| 任务 task | awf run 执行单元；通常 1 功能 = 1 任务，复杂功能可拆多任务 | state.json tasks |
| req-id | 功能唯一标识（如 `req-003`） | 功能级文档命名 |
| 需求 requirement | 规划期原始诉求，规范化后即「功能」 | 只出现在规划期，落地统一写「功能」 |
