# 架构决策

目标是让同一原因的变化集中发生、不同原因的变化彼此隔离。判断语义影响面，不以修改文件数或代码行数代替架构判断。

## 开始实现前

结合任务、相关代码和 `.awf/context/architecture.md`（存在时）形成局部系统模型：

1. 用一句话指出本次需求的主要变化轴。
2. 找到该概念的数据定义、决策点、执行入口和副作用边界。
3. 确认拥有该决策权的模块，以及已有的策略、注册表、适配器或稳定接口。
4. 预测变化会传播到哪里，并确认每处修改都源自当前目标。

选择且只选择一条实现路径：

- `extend`：现有权威边界能够自然承载需求，沿它局部扩展，不创建平行机制。
- `refactor-then-change`：同一业务决策已经散落，当前需求会继续复制分支；先做有测试保护、行为不变的小步收敛，再实现新行为。两部分保持可分离审查。
- `split`：需要改变公共契约、跨越多个业务边界，或行为不变重构明显超出当前任务。停止实现并用 `NEEDS_INPUT` 说明结构缺口和建议的前置任务。

不要为未经证实的未来需求预埋通用扩展点。只有变化轴已经出现、存在多个真实实例，或当前需求明确需要时才引入抽象。

## 首个纵向切片后

完成能贯通入口、核心行为和结果的最小切片后，重新检查实现路径。出现以下信号时不要继续复制代码：

- 同一业务条件开始出现在第二个不相关模块。
- 新类型要求连续修改多处 `switch` 或 `if` 链。
- UI、传输或存储层开始决定领域行为。
- 共享抽象按调用方增加特例参数或条件分流。
- 局部行为的测试必须 mock 大量无关内部细节。

若信号可在当前目标内小步收敛，切换到 `refactor-then-change`；否则切换到 `split`。文件数量增加本身不是切换理由。

## 完成检查

- 每个生产代码变更都能由任务目标或必要的结构收敛解释。
- 同一业务决策只有一个权威位置。
- 依赖仍指向拥有决策权的边界。
- 再增加一个同类实例时，主要是新增实现或配置，而不是再次遍历散落分支。
- 测试保护稳定行为，不锁死可变的内部组织。
- 没有夹带无关清理或为了展示设计而增加的抽象。

在任务结果中返回简短架构记录，不生成单独报告：

```json
{"changeAxis":"变化轴","boundary":"权威边界","path":"extend|refactor-then-change","boundaryChanged":false,"note":"关键取舍或无"}
```

只有真正改变模块职责、依赖方向或公共扩展方式时，才更新 `.awf/context/architecture.md`；不要把任务流水账写入架构地图。
