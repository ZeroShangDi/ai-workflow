# 质量实践参考

来源：原技能中的可读性、可维护性及量化检查经验。以下是待真实任务验证的启发式建议，不是已经通过实验的结论。

# 代码长度或复杂度达到什么程度才应该拆分？
关键词：代码复杂度、可读性、职责拆分
答案：长度、嵌套和复杂度只用于发现理解负担，不直接决定拆分。先定位负担来自职责混杂、隐藏状态、重复分支，还是需要频繁跳转；再选择命名、守卫语句或职责拆分。单一职责的解析表可能很长却清楚，大量单行转发也可能更难理解。检查主要与失败路径是否更容易读懂、行为是否保持。固定行数、嵌套层数或圈复杂度不能单独作为拆分门槛。状态：待真实任务验证。

# 常量、配置与业务语义应该如何组织？
关键词：常量、配置、权威定义
答案：值的业务含义不清时使用语义命名；同一政策值需统一调整时建立权威定义；只有确需外部调整时才配置化。局部且含义明确的字面量无需提取，不相关的值相同也不代表应共享常量。配置化还会增加校验、默认值及兼容成本。检查读者能否理解含义，改变政策时能否只改权威定义，以及无效配置的行为是否明确。状态：待真实任务验证。

# 如何判断覆盖率、复杂度等质量指标是否有意义？
关键词：质量指标、测试有效性、完成证据
答案：先将指标关联到具体风险，再查看异常或趋势并验证行为。测试能否识别关键错误，比单纯执行代码更重要；覆盖率高仍可能缺少有效断言，降低重复率也可能引入耦合。可在隔离验证中改变关键条件或构造反例，确认测试会失败，并检查指标改善是否保留清晰职责。指标达标不能替代验收，也不以统一维护指数或覆盖率百分比判定完成。状态：待真实任务验证。

# 异步请求乱序时，如何避免旧结果覆盖新状态？
关键词：异步乱序、状态隔离、回归测试
答案：先确定界面状态代表“最新发起请求”还是“最后成功结果”，再据此约束写回。若最新请求优先，可为每次请求分配递增身份，仅允许当前身份更新共享可见状态；各请求仍返回自己的结果或错误。状态应放在匹配其生命周期的实例中，不必为了隔离而禁止闭包，也不要把取消请求当作唯一正确性保障。验证同词重搜、旧请求晚到、最新请求失败、不同实例交错等会区分实现的顺序。2026-09-24 的合成案例以 6 项执行测试和 9 项验收用例验证；验收用例在修改前失败 4 项、修改后全部通过。该结果不是生产项目验证，未覆盖真实界面、取消和销毁场景，也不适用于结果累加型请求。
