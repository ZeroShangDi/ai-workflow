# 改动范围

用于发现多个落点、考虑自动生成或准备扩大重构时。以下为待项目实测的决策经验，不把未经核实的文件数和历史故事当证据。

## 多处修改先分类，不先合并

- **情境**：一个需求看起来必须改很多文件。
- **做法**：区分真正的不同消费者、同一事实的手写副本、生成产物，以及无关整理。消费者各自有真实契约时，多处修改可以是完整实现；同一事实反复手填时，再评估单一来源或生成；产物遵循仓库构建方式，不逐份手修。
- **原因**：文件数量描述规模，却不说明职责是否错误。把前后端校验、迁移和测试强行合成一处，并不能减少真实影响面。
- **代价与反例**：生成器会增加构建和排错成本。仅为省一次填写而建设系统未必合算；重复频繁、格式确定且有验证时才更有价值。若优化超出当前任务，给出局部完成与后续收敛的选择，不擅自迁移。
- **验证**：检查来源到产物是否一致、缺失与重复项是否能被发现、输出是否稳定，以及既有消费入口是否仍有效。不能只看文件变少。

## 必要整理与顺手整理

- **情境**：实现前需要整理一段已有代码。
- **做法**：说明不整理会如何妨碍本次正确实现或验证。能说明的局部整理用现状行为测试保护，再实现新行为；无关命名、全量格式化和框架升级另议。
- **原因**：区分整理与新行为，便于定位回归；这是逻辑和验证上的分离，不天然要求两个提交。
- **代价与反例**：完全禁止整理可能留下危险补丁；为了“干净”拆出大量单次使用模块也会扩大理解成本。提交需有授权，仓库要求原子交付时应一并包含必要代码和测试。
- **验证**：整理阶段原有行为仍成立，新行为测试能在修改前暴露差异；最终 diff 中每个落点都能关联本次需求或关键风险。
