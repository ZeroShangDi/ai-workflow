# 边界与护栏

用于跨模块引用、共享状态或修改接口时。以下为方法应用与待项目实测的例子；当前项目是否存在架构测试，必须现场确认。

## 引用方便不等于职责合适

- **情境**：一个页面想直接引用另一个页面的内部组件。
- **做法**：先读当前依赖约定和相关测试。真正独立于页面的能力可放入双方允许依赖的位置；带有页面业务策略、权限和状态的组件，不宜直接搬到 shared。也可通过组合或传入所需能力维持边界。
- **原因**：公共目录不会自动消除业务耦合；应隐藏变化决定，避免共享层反向依赖具体页面。
- **代价与反例**：抽取会增加导航和接口成本，仅一个消费者且边界清晰时不必搬。护栏测试失败先查是否触及真实约束，不能为通过测试而取消护栏。
- **验证**：检查依赖方向及共享模块是否混入消费者特例；运行实际存在的架构测试和受影响行为测试。

## 状态需要明确归属，不需要禁用闭包

- **情境**：工厂函数或组件内部持有缓存、请求状态或计数器。
- **做法**：确认每个实例是否独立、谁更新状态、何时释放、异步结果能否越过生命周期。实例闭包可以是正确封装；模块级可变单例则需要确认是否真的允许跨用户或跨实例共享。
- **代价与反例**：把所有状态和依赖都通过参数层层传递会污染接口；把所有状态隐藏起来也会失去可控性。按真实生命周期与测试需求选择，不因语法形式重写。
- **验证**：两个实例交错操作是否互相影响，重试或销毁后旧结果是否还能写回；只选择当前代码实际涉及的情况。

## 可替换性不只适用于继承

- **情境**：用新适配器、函数或测试替身替换现有实现。
- **做法**：核对输入前提、返回值、错误语义和可见副作用是否仍满足消费者契约。不能因为项目没有类继承就排除可替换性问题。
- **代价与反例**：遵守契约不等于把所有实现行为做成完全相同；需要先区分调用方可依赖的保证与内部细节，也不能无依据推翻消费者已实际依赖的行为。
- **验证**：以相同契约用例运行可替换实现；不要只验证方法名存在或类型检查通过。

## 隔离验证记录：搜索乱序与实例状态

- **证据状态**：2026-09-24，合成案例实测，非生产项目验证。独立执行代理读取本技能后修改一个闭包搜索工厂；各次调用须返回自身结果或错误，保存状态只接受最新发起请求。
- **实际做法**：保留实例闭包，用实例内请求序号控制写回，没有抽取状态框架。同期订单期限变更保留了相似但独立的邀请规则；共修改两个实现文件并新增一个测试文件。
- **结果**：执行代理的六项测试通过；另设九项验收在原始实现上失败四项，在修改后全部通过，包括同词重搜、最新请求失败、旧请求失败和实例隔离。
- **可复用结论与限制**：请求身份与查询字符串不是一回事；完成调用与更新共享可见状态也不是一回事。该方案适用于“最新请求优先”，不适用于结果累加。未验证真实界面、取消与销毁，也未作新旧技能对照，不能据此归因全部收益或声称普遍降本。
