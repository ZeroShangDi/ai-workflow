# 抽象时机

用于重复代码、预留扩展点或公共层越来越难理解时。以下为文献建议及应用推导，不代表已在目标项目实测。

## 相似实现不一定拥有同一规则

- **情境**：两个流程写法相似，正在考虑合并。
- **判断**：问它们是否受同一政策约束、未来是否必须同步变化，而不是数重复次数。例如订单撤销期限与邀请过期时间即使都是七天，也可能属于两个独立契约。
- **做法**：不同变化原因保留独立表达；共同规则已有明确归属时复用该归属。公共函数不断增加调用方标志和特殊分支时，重新检查抽象是否错误，必要时先还原独立实现再观察真正共性。
- **代价与反例**：保留重复有同步遗漏成本；权限、计价等同一规则不能仅以“避免抽象”为由散落复制。反过来，也不能为了统一而让无关领域绑定发布与依赖。
- **依据**：[Sandi Metz：The Wrong Abstraction](https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction)；业务规则判据是本技能的应用推导。三次法则可提醒重新审视，不能作为“第三次必须抽、第一次不能抽”的门槛。

## 扩展点也有持有成本

- **情境**：当前只有一种实现，但可能以后支持更多。
- **做法**：先画出未来真要支持时需要改哪里。若只是一个内部函数，可推迟策略层；若现在就有多个实现或依赖替换需求，接口可能立即有用。整理命名、消除隐式共享状态、隔离外部副作用，也可能直接改善当前代码。
- **代价与反例**：“只换个位置写”仍可能改变依赖方向、生命周期和公共 API，不保证免费；多一层间接也并非必然过度设计。已发布格式、外部消费者所依赖的行为需要先考虑兼容，但无需预建所有未来版本。
- **依据**：[Martin Fowler：Yagni](https://martinfowler.com/bliki/Yagni.html)。它针对推测性能力，不是否定可修改性；这里的接口与迁移判断是应用推导。
