# 性能差异审查

从用户可感知路径、系统负载和本次差异出发，判断改动是否可能增加时间、内存、网络、存储或构建成本。优化方法由 `code-performance` 承载；本技能只负责审查风险和证据。

## 检查方法

1. 找出受影响的关键路径和代表性输入规模；优先使用现有性能目标、追踪记录、基准或生产观测。没有负载依据时，不把理论上的复杂度增长直接写成用户影响。
2. 沿实际调用路径检查重复数据库/网络请求、数据量增长、同步主线程工作、重复渲染与计算、资源创建/释放、缓存和并发行为。清单项只是调查线索，不是缺陷结论。
3. 将本次差异与基线或可计算的工作量对照。没有测量时，明确标注为代码路径支持的潜在风险，不编造延迟、请求数或容量数据。
4. 只在存在具体负载和影响证据时提出修复方向；建议修复后用相同场景复测，并检查收益是否以正确性、内存、新鲜度或运行成本为代价。

## 不作为通用结论的做法

- 不用固定列表项数、循环层数或代码行数决定是否优化。
- 不因看到 `map`、内联函数、数据库访问或缺少缓存就直接报告性能问题。
- 不把虚拟列表、memo、缓存、并行化、批量查询当作默认修复；先证明瓶颈与该措施相匹配。
- 不要求每个审查都生成基准或做全量性能测试；验证强度与已观察风险和用户目标相称。

审查发现的严重程度、证据位置和报告字段遵循 `w-review`；测量与修复方案需要深入分析时，读取 `code-performance` 中对应方法和经验。
