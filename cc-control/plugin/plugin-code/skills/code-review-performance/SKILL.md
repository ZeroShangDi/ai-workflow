# 性能分析审查

缺陷清单见 code-dev-performance（反模式与基线），这里是审查方法和报告格式。

## 审查方法

### 1. 定位关键路径

- 先找到用户可感知的路径：首屏渲染、核心交互、列表加载、主流程 API
- 对每个关键路径问：这条路径每次执行做了什么、会随着数据量怎么增长

### 2. 逐项检查清单

**数据访问**
- [ ] N+1 查询：循环里发查询 → 应批量/join/预加载
- [ ] 查询取多余字段/全表扫描 → 只取需要的列和行
- [ ] 深度分页（大 offset）→ 用游标

**渲染/前端**
- [ ] 状态放的位置导致不必要重渲染（父状态驱动子全部重渲染）
- [ ] 列表无 key / 用 index key
- [ ] 大列表未虚拟化（100+ 项）
- [ ] 内联对象/函数 props 破坏 memo
- [ ] 图片无尺寸占位（CLS）、LCP 元素被 lazy-load
- [ ] 长同步任务阻塞主线程（大循环、同步处理）

**内存**
- [ ] 定时器/监听器/订阅/observer 无清理 → 内存泄漏
- [ ] 闭包持有大对象 / 全局缓存无限增长
- [ ] 重复创建大对象/数组（如每次渲染都 new）

**算法**
- [ ] 明显低效算法（嵌套循环、O(n²) 在可预期大输入上）
- [ ] 热路径上重复计算 → 应缓存/memo/预计算

### 3. 复杂度判断

- 单点修改是否有数量级风险：`for` 套 `for` 是否数据量可控
- 新代码是否引入对既有热路径的额外开销（每条记录多一次调用）

### 4. 证据要求

- 每条发现必须有 `file:line` + 具体风险，禁止猜测
- 能给出量化的更好："列表 1000 条时每次渲染执行 1000 次查询"

## 严重度分级

| 级别 | 含义 | 处理 |
|------|------|------|
| 阻塞 | 明显性能崩溃：O(n²) 在现实数据量下不可用、内存泄漏导致卡死 | 合入前必修 |
| 严重 | 可感知退化：关键路径明显变慢、大列表卡顿 | 应修 |
| 建议 | 潜在风险：现在不痛但随规模恶化 | 建议修 |
| 参考 | 微优化、风格性 | 可选 |

## 报告格式

```
## 性能审查

**结论**：APPROVE / APPROVE WITH COMMENTS / REQUEST CHANGES

### 关键路径评估
- 首屏/核心交互路径：<基线评估>

### 发现（按严重度）

**[严重] `src/user/list.ts:42`** N+1 查询
- 问题：循环内查询用户详情，1000 条记录产生 1000 次查询
- 修复：join 或批量 `WHERE id IN (...)`，预加载

**[建议] `src/App.tsx:10`** 状态位置
- 问题：过滤状态放根组件，每次输入全树重渲染
- 修复：状态下沉到列表组件

### 做得好的
- 图片均带尺寸占位，无 CLS 风险
```
