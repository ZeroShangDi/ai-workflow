# 渐进增强与优雅降级

## 两个方向

| 策略 | 方向 | 思路 |
|------|------|------|
| 渐进增强 | 自下而上 | 先保证基础体验人人可用，再为高能力环境叠加增强 |
| 优雅降级 | 自上而下 | 先做完整功能，再为低能力环境准备回落方案 |

**2025 共识**：不是二选一。以渐进增强为底座，用优雅降级处理现代特性的失效——内容优先，从 HTML 出发，不从 JS 出发。

## 渐进增强：从基础体验逐层增强

三层模型：

```
Layer 1  语义 HTML     → 无 CSS/JS 也能读内容、提交表单
Layer 2  CSS           → 增强呈现，可读性、布局
Layer 3  JavaScript    → 高级交互，为可用则加，不可用则退
```

落地要点：

- 核心内容不依赖 JS：服务端/SSG 出完整 HTML，浏览器再水合交互
- 表单原生可提交（无 JS 时正常提交），有 JS 时用 Ajax 增强
- 导航用标准链接；禁用 JS 时核心流程仍可完成
- 关键路径考虑 SSR/SSG（Nuxt/Next），首屏不等 JS 才可见

## 优雅降级：高级特性不可用时如何回落

### 功能检测（特性检测）优先，浏览器检测弃用

- 用能力检测而非 UA 判断：`'fetch' in window` 而不是 `navigator.userAgent`
- CSS 用 `@supports`：`@supports (display: grid) { ... }`
- 检测到再启用，检测不到给基础实现

### 分级方案

| 特性层级 | 不可用时 | 示例 |
|----------|----------|------|
| 关键功能 | 必须保证可用 | 表单、支付、登录 |
| 增强交互 | 回落到基础交互 | 拖拽 → 按钮选择；Ajax → 原生提交 |
| 视觉增强 | 降级布局 | Grid → Flex → 块级；不支持则元素垂直堆叠 |
| 锦上添花 | 可舍弃 | 动效、WebGL、剪贴板 |

### 交互降级案例

- 表单：无 JS 时原生提交（页面刷新）；有 JS 时 Ajax + 局部校验
- 上传：无 File API 时回落到普通 `<input type="file">`
- 实时推送：无 WebSocket 时轮询，或提供"刷新"按钮
- 剪贴板：无 Clipboard API 时提供手动复制文本

## 功能检测 vs 浏览器检测

| | 功能检测 | 浏览器检测 |
|--|---------|-----------|
| 判断对象 | 能力是否存在 | 浏览器品牌/版本 |
| 可靠性 | 高（能力与行为直接相关） | 低（UA 可伪造、版本≠能力） |
| 维护 | 能力增加即扩展 | 每次发版要更新列表 |
| 结论 | **优先使用** | 仅极少数兜底场景 |

## 降级决策标准

一个特性要不要花成本做降级，按以下判断：

1. **它是关键功能吗？** 是 → 必须降级（支付、登录、核心数据）
2. **目标环境能覆盖多少人？** 覆盖率高 → 可接受简化降级；受众未知 → 按渐进增强做
3. **不可用时损失多大？** 损失轻微 → 优雅降级即可；损失严重 → 直接保证基础路径
4. **降级成本 vs 受众** — 内部工具受众窄，可只做完整路径 + 简单降级；公网产品按渐进增强

## 尊重用户偏好

- `prefers-reduced-motion`：减少动画
- `prefers-color-scheme`：暗色主题
- `prefers-contrast` / `forced-colors`：高对比

## 测试策略

- 禁用 JS 验证核心功能仍可用
- 节流网络模拟弱网，验证内容先于增强加载
- 旧浏览器/禁用 CSS 特性：DevTools 开关逐个验证
- 屏幕阅读器跑通关键流程
