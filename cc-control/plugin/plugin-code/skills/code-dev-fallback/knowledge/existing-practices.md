# 新组件要替换旧组件，应该直接替换还是分批迁移？
关键词：组件替换、契约差异、并行迁移
答案：比较真实调用方依赖的参数、默认值、事件、状态控制、校验和错误行为，再选切换方式：

| 旧新契约关系 | 做法 | 主要检查 |
|---|---|---|
| 对调用方完全一致 | 直接替换 | 关键调用点的行为回归；无需为了兼容保留双实现 |
| 存在差异，但旧调用方可逐步修改 | 平行变更，按调用方逐步切换 | 哪些调用方仍走旧实现；新旧实现是否争用状态或产生不同结果 |
| 存在差异，调用方暂时不能修改 | 在边界放适配器或兼容包装器 | 映射是否保留语义；兼容层由谁维护、何时移除 |
| 并行运行会造成更大风险 | 集中切换，或先统一契约再切换 | 切换窗口、失败恢复和真实使用路径验证 |

分批切换的价值是限制单次变更影响范围，不是减少工作量，也不天然更安全。开发过程中未交付、不可达的中间状态无需满足生产契约；一旦新旧实现同时可用，就要明确调用方路由、状态归属和结束并行的条件。

# CSS 跨浏览器差异出现时，如何选择回退方法？
关键词：CSS兼容、渐进增强、优雅降级、特性检测
答案：先确定受支持的浏览器范围以及差异对内容、操作和视觉的影响，再选择处理层次：

1. **语法不支持，但有等价基础样式**：先写基础声明，再用新语法增强；必要时用 `@supports` 限定增强样式。
2. **增强效果不可用，但核心内容仍可工作**：采用渐进增强或优雅降级，让布局退回可读、可操作的形式。
3. **必需能力缺失**：评估 polyfill 或针对性修复，并明确目标环境与退出条件。
4. **能力存在但行为有差异**：按实际浏览器行为验证并针对差异修正；仅检测 API 存在不够。

不必为每条 CSS 都准备多层回退。只覆盖声明支持的环境和会影响用户任务的差异。

# 页面要适配不同视口，Flexbox、Grid、断点和相对单位怎么选？
关键词：响应式布局、视口适配、Flexbox、Grid
答案：按布局关系和变化条件组合使用：

| 需求 | 常用方案 |
|---|---|
| 一维排列、对齐、换行、剩余空间分配 | Flexbox |
| 二维行列、区域布局、行列对齐 | Grid |
| 内容或容器到一定宽度后需要改变布局 | 媒体查询；组件由自身容器决定时用容器查询 |
| 尺寸需要随字体、容器或视口伸缩 | `%`、`rem`、`vw` 等相对单位；需要时用 `min()`、`max()`、`clamp()` 限定范围 |
| 窄屏需改变信息层级或操作方式 | 响应式重排，而不只是缩小原布局 |

Flexbox、Grid 是布局工具，媒体/容器查询决定何时改变规则，相对单位表达尺寸关系；它们不是互斥方案。断点由内容何时变得拥挤或难用决定，需用真实内容、缩放和窄宽视口验证。

# 适配器、策略和代理模式在兼容改动中分别何时有用？
关键词：适配器模式、策略模式、代理模式、设计模式
答案：按变化种类判断，不因“兼容”二字而套模式：

- **适配器**：调用方契约需要保持，但新旧接口或平台 API 不同；在边界转换参数、结果或错误语义。
- **策略**：存在多种真实可选的行为实现，且系统有明确依据选择其中之一，例如按运行能力选择实现。只有一个实现时，先用直接调用。
- **代理**：需要控制访问、延迟加载、缓存或拦截调用。代理本身不负责把不兼容契约变兼容，除非它明确承担了转换边界。

若只是新旧组件契约相同，直接替换比增加模式层更合适。

# 函数签名或行为要改变，怎么让旧调用方逐步迁移？
关键词：函数契约、包装器、弃用
答案：先盘点调用方依赖的参数、默认值、返回值、异步时序和错误行为。语义相同而签名变化时，可用旧签名包装新实现；语义不同则提供可区分的新入口，避免用可选参数悄悄改变旧调用行为。标记弃用、迁移调用方并验证后，再移除旧入口。若调用方都可同时修改且没有外部消费者，通常直接改完更简单。

# 升级依赖包时，怎样判断是否需要兼容层？
关键词：依赖升级、API变化、兼容层
答案：先核对项目实际使用的 API、默认行为、错误语义、运行时要求和构建产物。局部 API 变化且多个调用点都受影响时，可在项目自己的边界封装依赖，避免差异散落；若升级没有破坏已依赖行为，就不必为了抽象增加封装。升级后验证真实功能路径、打包结果和受影响环境，不把类型检查或构建通过视为完整兼容证据。

# 两端无法同步发布时，接口或消息协议如何演进？
关键词：接口演进、协议版本、能力协商
答案：先列出部署期间可能出现的新旧版本组合，并约定共同契约。常见做法是新增可选字段并定义默认值、忽略未知字段、增加版本标记或协商双方能力；字段含义、必填性、消息顺序和握手变化都属于行为变化，不能只测序列化结果。等旧端不再出现并确认使用情况后，再删除旧字段或旧分支。

# 数据结构或数据库格式变化时，何时采用分阶段迁移？
关键词：数据迁移、扩展迁移收缩、恢复
答案：当生产者、消费者或实例不能同时升级，或数据量/服务连续性不适合一次切换时，考虑“扩展—迁移—收缩”：先让新旧结构共存，再迁移并校验，最后删除旧结构。对长任务采用分批回填、检查点和幂等操作；双读/双写只在确实需要并行服务时采用，并预先定义一致性、对账与退出方法。集中切换若更简单且恢复可控，则不必人为分阶段。

# 多平台模块加了适配器，怎样确认所有调用都经过兼容边界？
关键词：多平台适配、调用路径、适配器
答案：定义共同契约与各平台实现后，沿生产入口追踪调用链，检查是否仍有代码直接依赖某个平台。测试至少覆盖每个声明支持的平台和真实入口；仅测试适配器本身不能证明系统实际使用了它。DSH 接入中曾出现适配边界已建立、生产代码仍直接引用旧平台的情况，因此边界测试要与调用路径检查配合。

# 兼容改动应该验证哪些组合？
关键词：兼容矩阵、契约测试、真实路径
答案：从声明支持的使用方、版本和环境中选出会影响行为的组合，不追求机械穷举。至少覆盖：

- 必须保留的旧行为。
- 新行为及关键边界。
- 新旧并行或协商的路径（若存在）。
- 真实生产入口，而不只是适配器、替身或序列化结构。

矩阵用于暴露未覆盖的支持组合；风险较高时优先验证真实消费者和失败路径。测试结果只能支持已覆盖的组合，不能自动推广到全部环境。
