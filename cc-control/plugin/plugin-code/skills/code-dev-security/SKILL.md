# 安全处理

## 核心判断

- **从威胁和边界出发。** 确认保护什么、谁可能滥用什么入口、可触达哪些资源，以及失败会造成什么影响；攻击面由数据流和权限决定，不由代码位置或“前后端”标签决定。
- **信任需逐边界建立。** 外部输入、客户端状态、第三方响应和持久化数据都要按来源与用途验证；验证、授权和输出编码解决不同问题，不能相互替代。
- **授权绑定主体、资源和动作。** 访问控制应在可信服务端根据当前主体与具体资源/操作判断；隐藏界面、不可猜测 ID 或前端校验都不能替代授权。
- **拒绝应安全且可恢复。** 认证、授权或校验无法确定时，不以放行兜底；同时避免错误路径泄露敏感信息、留下半完成状态或造成不必要拒绝服务。
- **保护贯穿数据生命周期。** 收集最少必要数据，限制访问与留存；密钥、令牌和个人数据不应进入代码、日志或不必要的传输路径。
- **防护落在真实执行路径。** 识别机制在哪一层执行、能否被绕过，并覆盖攻击者可控输入、越权对象、异常顺序和依赖失败等关键反例。
- **安全取舍需要显式。** 降低安全控制、扩大信任范围或接受高影响风险，会改变产品承诺；不得静默降级，应说明风险并取得相应决策。

## 处理步骤

1. 从本次变更识别资产、主体、入口、信任边界和可能到达的敏感操作。
2. 推演最相关的滥用路径：攻击者控制什么、如何绕过现有判断、能够造成什么影响。
3. 在最靠近可信决策或敏感资源的边界实施最小权限防护；需要多层控制时说明每层阻断的路径。
4. 验证控制确实覆盖生产入口，并用针对性反例证明拒绝、隔离和错误处理有效。
5. 检查敏感数据、日志、密钥和新增依赖的处理；说明尚未覆盖的风险与证据边界。

若攻击面、主体权限或数据敏感等级不清且会改变设计，先向用户追问。发生疑似漏洞、影响范围未知或修复会改变访问行为时，说明已知事实、风险和可选处理，避免自行扩大范围或静默改变授权语义。

## 按需经验

根据具体问题检索同级 `knowledge/` 中匹配的输入处理、注入、授权、会话、敏感数据或依赖供应链条目。具体技术和标准需按当前技术栈与目标环境核实；不把旧案例中的数字、算法或配置无条件套用。
