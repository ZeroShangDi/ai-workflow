# 性能优化

## 核心判断

- **先定义目标，再谈快慢。** 指标必须对应用户任务或系统容量，并注明测量对象、负载和环境；没有目标的“优化”容易把资源消耗转移到别处。
- **先测量定位，再改代码。** 从基线识别端到端关键路径和主要瓶颈；凭直觉、代码行数或单个微基准不能证明用户侧变快。
- **优化受瓶颈约束。** 改善非瓶颈部分对整体收益有限；缓存、并发、预计算、懒加载等手段也会引入一致性、延迟、复杂度或资源代价。
- **性能不能破坏语义。** 结果正确性、错误处理、安全、可访问性与兼容行为是约束；性能收益要与这些约束及运行成本一起衡量。
- **用可比证据验证并设停止点。** 在相同或可解释的负载下比较前后数据，同时检查尾延迟、内存、网络、主线程等可能转移的成本；收益不显著或代价不合算时停止。

## 处理步骤

1. 明确性能问题对应的用户任务、系统指标、目标范围和代表性负载。
2. 建立基线，沿端到端路径定位主要时间或资源消耗点。
3. 针对瓶颈比较候选做法及其代价，优先选择能验证、影响范围明确的改动。
4. 用相同场景复测，确认目标指标改善且关键约束未退化；记录环境和未覆盖条件。

用户要求性能目标或资源预算时按其目标判断；若选择会改变正确性、数据新鲜度、服务质量或成本，应先说明取舍。没有可靠测量条件时，不把推测写成已证实的优化效果。

## 按需经验

根据问题读取同级 `knowledge/` 中匹配的前端渲染、网络加载、数据库、缓存、并发或内存条目；只读取相关经验，不把工具清单或固定阈值当作通用结论。
