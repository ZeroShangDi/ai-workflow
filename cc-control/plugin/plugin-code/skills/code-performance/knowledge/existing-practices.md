# 如何判断一个性能问题值得优化？
关键词：性能目标、基线、测量
答案：先对应到用户任务或系统容量，明确测量对象、负载、环境和可接受目标，再建立基线并定位端到端的主要耗时或资源消耗。先查证据指向的瓶颈，不根据代码看起来复杂、文件较大或某条微基准直接推断用户受影响。优化后在可比较条件下复测，并检查成本是否转移到内存、网络、尾延迟或维护复杂度。

# 如何判断一次查询或循环是否形成真实的性能瓶颈？
关键词：数据库查询、N加一、复杂度
答案：沿真实数据路径观察调用次数及其随输入规模的增长。列表内逐项查询可能形成 N+1；此时比较批量加载、关联查询或预取，但要同时检查返回数据量、索引、事务和一致性。用查询计划或追踪确认扫描与等待；深分页、全字段读取、嵌套循环等只有在实际数据规模和使用方式下造成成本时才是优化目标，不套统一行数或复杂度门槛。

# 什么时候应该缓存，缓存设计要先回答什么？
关键词：缓存、一致性、失效策略
答案：先确认重复计算/读取确实占据成本，并识别允许的数据陈旧程度、权威来源、缓存键和更新时机。选择旁路、直写或其他方案时，明确失效、并发写、重试和缓存不可用时的行为；只有观测到并发回源压力时才引入互斥或防击穿机制。缓存能减少重复工作，也会增加一致性和排障成本，收益未证明或新鲜度要求严格时不缓存。

# 前端渲染或长列表变慢时，应先看什么？
关键词：前端渲染、长列表、Profiler
答案：在代表性页面和数据量下定位用户感知的卡顿，区分 JavaScript 计算、组件更新、DOM 数量、布局绘制和网络等待。针对证据选择状态下沉、减少重复计算、分批工作或列表虚拟化；虚拟化只在渲染规模确实成为瓶颈时引入，并检查键盘访问、焦点、搜索和测量需求。不要用固定条目数决定是否虚拟化，也不要把 memo 当默认修复。

# 页面加载慢时，资源加载优化如何选择？
关键词：首屏加载、资源优先级、代码分割
答案：用真实用户或浏览器性能记录区分服务器响应、关键资源发现、下载、解析执行和渲染瓶颈。按结果考虑减少首屏 JavaScript、按路由拆分非关键代码、优化图片尺寸与格式、为会造成布局位移的媒体预留尺寸，或调整确实阻塞关键路径的字体和脚本。预加载、内联或延迟每种策略都有副作用，应针对关键资源使用并在目标设备复测，不把特定工具清单当固定方案。

# 如何避免异步任务、内存和资源使用随时间失控？
关键词：并发、内存泄漏、资源清理
答案：先确定工作量、并发上限、取消/重试和生命周期，再用批处理、队列、限流或并发控制保护系统；数据库事务尽量保持在满足一致性的必要范围。监听器、订阅、计时器和大型缓存需有清理或淘汰策略。用长时间运行、代表性并发和失败恢复场景观察积累趋势；不为尚未出现的负载预先引入复杂队列或锁。

# 性能优化完成后需要怎样证明收益？
关键词：性能回归、基准测试、收益验证
答案：让优化前后使用同一关键路径、可比环境和代表性数据，记录目标指标及相关副作用。避免只测单次微基准而忽略端到端体验；开发模式、缓存暖机、设备差异和数据分布可能改变结果。若改善小于波动、目标未达成或正确性/资源成本退化，调整方案或撤回，不把“代码更少”写成性能提升。
