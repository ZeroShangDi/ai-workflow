# 项目复盘

复盘不是追责，是提炼经验。核心是产出**可执行的行动项**，不是记录感想。

## 默认格式：Stable + Improve + Experiment

### Stable（保持）

哪些做法效果好，值得继续保持。

### Improve（改进）

哪些地方可以做得更好。

### Experiment（尝试）

下次想尝试什么新做法。

## 复盘格式菜单（按场景换）

固定格式用久了会疲劳，每 2-3 个里程碑换一种，保持视角新鲜：

| 格式 | 维度 | 适合 |
|------|------|------|
| Stable/Improve/Experiment | 保持/改进/尝试 | 默认，通用 |
| Start/Stop/Continue | 开始/停止/继续 | 轻量快速复盘 |
| 4Ls（Liked/Learned/Lacked/Longed For） | 喜欢/学到/缺失/渴望 | 中期复盘，捕捉未说出口的诉求 |
| Mad/Sad/Glad | 愤怒/失望/开心 | 艰难冲刺后，先认可情绪再找根因 |
| Starfish | Keep/More/Less/Stop/Start | 需要精细反馈时 |
| 时间线 | 把事件铺在时间线上 | 长周期复盘 |

## 复盘流程

1. **回顾上次行动项** — 上次的改进项完成了吗？未完成的说明原因
2. **收集** — 各成员按当前格式写，静默书写避免被带节奏
3. **归类讨论** — 按主题归并，找出模式，不止于单条现象
4. **选行动项** — 全团队投票选出最重要的 1-3 条
5. **定负责人和期限** — 每条行动项有 owner 和截止时间

## 复盘原则

- **每项写具体，不写空话**："沟通需要加强" → "需求变更时应该先更新 issue 再动手写代码"
- **最多 3+3+3 条** — 一次复盘产出太多等于没有产出
- **行动项 1-3 条，各配 owner 和期限** — 无 owner 的行动项完成率低于 20%
- **下轮先查上轮行动项** — 复盘本身要被复盘
- **心理安全** — 团队负责人先承认自己的失误，成员才敢说真话
- 复盘记录存入 `docs/discuss/` 保留

## 反模式

- 追责会——复盘变成批斗会，成员开始自我保护
- 感想大会——只说感受不产出行动项
- 清单式堆砌——10 条改进 = 0 条执行
- 复盘的复盘被跳过——上轮行动项无人跟进
