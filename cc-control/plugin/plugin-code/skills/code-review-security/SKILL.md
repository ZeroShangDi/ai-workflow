# 安全漏洞检查

防御方法与漏洞详解见 code-dev-security，这里是审查方法论和报告格式。

## 审查方法

### 1. 高危入口优先

安全审查按"攻击面"而非文件顺序：用户输入、认证/授权、数据传输、动态执行、密钥处理是优先检查点。

### 2. 检查清单

**输入与注入**
- [ ] 用户输入/API 响应是否校验（类型、长度、白名单）
- [ ] SQL/NoSQL 是否参数化，有无字符串拼接
- [ ] 命令执行是否用参数数组，有无拼 shell
- [ ] XSS：`innerHTML`/`v-html`/`dangerouslySetInnerHTML` 是否有净化；`eval`/`new Function` 是否禁用
- [ ] 文件操作有无路径穿越（`path.resolve` + 前缀校验）

**访问控制**
- [ ] 敏感资源访问是否服务端鉴权（不信任前端状态）
- [ ] 对象 ID 是否可枚举（IDOR）——资源归属校验
- [ ] CORS 白名单是否过宽
- [ ] SSRF：用户提供 URL 有无 host 白名单

**认证与会话**
- [ ] 密码哈希是否 bcrypt/Argon2id
- [ ] cookie 是否 `HttpOnly` + `Secure` + `SameSite`
- [ ] 登录失败有无限速/锁定

**敏感数据**
- [ ] 有无硬编码密钥/token/连接串
- [ ] 日志/错误信息是否泄露敏感数据或堆栈
- [ ] 传输是否强制 HTTPS

**依赖**
- [ ] 新依赖是否 `npm audit` 无高危
- [ ] 版本是否锁定

### 3. 置信度评分

每条发现标注置信度，只把高置信度当结论：

| 置信度 | 含义 | 处理 |
|--------|------|------|
| HIGH | 可复现/逻辑明确可证 | 进报告，按严重度 |
| MEDIUM | 存在风险路径但需确认上下文 | 标注"疑似"，附验证方法 |
| LOW | 仅凭代码片段推测 | 不进报告，或列"参考" |

**宁可漏报也不误报**：报告里的每一条都要经得起"为什么这是漏洞"的追问。

### 4. 验证

- 高置信度漏洞给出可复现的触发输入（如 `' OR 1=1 --`）
- 不确定的分支去查调用方上下文再定论

## 严重度分级

| 级别 | 含义 | 处理 |
|------|------|------|
| 阻塞 | 可直接利用：注入、未授权访问、密钥泄露 | 合入前必修 |
| 严重 | 可被利用但需条件/组合：宽松 CORS、缺限速 | 应修 |
| 建议 | 纵深防御缺口：单点防线存在 | 建议修 |
| 参考 | 非关键但值得改进 | 可选 |

## 报告格式

```
## 安全审查

**结论**：REQUEST CHANGES（存在 1 个阻塞项）

### 发现（按严重度 + 置信度）

**[阻塞·HIGH] `api/user.ts:23`** 未授权访问
- 问题：查询用户详情仅校验登录，未校验资源归属（IDOR）
- 触发：`GET /api/user/123` 任意登录用户可读他人资料
- 修复：`if (userId !== req.user.id) return 403`

**[严重·HIGH] `auth.ts:15`** cookie 缺少 Secure 标志
- 问题：登录 cookie 未设 `Secure`，HTTP 下可被嗅探
- 修复：`cookie('token', t, { httpOnly: true, secure: true, sameSite: 'strict' })`

### 做得好的
- 所有 SQL 均使用参数化查询，无注入风险
```
