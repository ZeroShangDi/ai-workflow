# 架构与模块设计

设计的目标是让每个业务决策有清晰归属，使同一原因的变化沿合适边界传播。目录、组件和模式服务于这个目标，不是设计结果本身。

## 核心判断

- **先找规则所有者。** 明确谁拥有状态、业务决策和副作用；同一规则应有权威位置，调用方通过契约协作。
- **按职责与变化原因划边界。** 高内聚、低耦合意味着相关规则共同演进、不同规则保持可独立变化，不等于文件越少或抽象层越多越好。
- **按功能组织相关代码。** 页面骨架应能看出组成，状态、规则、组件和测试按共同变化原因聚拢；跨功能共享能力才单独上提。
- **抽象由真实变化驱动。** 共同语义、独立变化或真实替换需求可以支持抽象；语法相似、模式名称和假想扩展点本身不构成理由。
- **接口表达稳定契约。** 暴露调用方需要的能力及必要语义，不泄漏可变实现细节；同时检查数据、错误、时序和依赖方向。

## 选择变化路径

先结合目标、约束、调用方和现有架构约定（如 `.awf/context/architecture.md`），找出主要变化轴、规则所有者、数据/副作用流以及必须保持的契约。若不确定前提会改变职责、接口、依赖或交互时序，先向用户澄清。

| 路径 | 适用判断 | 做法 |
|---|---|---|
| `extend` | 现有权威边界能够自然承载需求 | 沿该边界局部扩展，不建立平行机制 |
| `refactor-then-change` | 决策已散落，本次继续实现会复制规则或破坏不变量 | 先做行为不变、可单独验证的局部收敛，再实现新行为 |
| `split` | 需要跨越多个业务边界、改变公共契约，或超出当前任务可安全完成的范围 | 给出边界问题与前置方案，暂停依赖该决定的实现并交由用户审阅 |

不要为了未经证实的未来需求预埋通用扩展点。若小步实现出现新分支散落、共享抽象不断增加调用方特例、或上层开始决定下层业务规则，重新判断变化路径。

## 形成并验证设计

给出足以审阅的设计草图，至少说明模块/组件职责、关键输入输出、状态归属、协作关系及重要失败路径。设计应能解释为什么采用当前边界，以及下一项已知同类变化会落在哪里。

设计草图和大致代码结构交由用户审阅，根据反馈调整后再定稿。AWF 无人值守时，仅在约束明确、影响较小且可逆时作保守选择并注明未获用户审阅；若存在改变设计的未决事项，标记 `needs_user_review` 并停止依赖该决定的工作。

实现首个纵向切片后重新检查：是否仍只有一个规则所有者、依赖是否指向正确边界、测试是否保护行为而非锁死内部组织。仅当职责、依赖方向或长期扩展方式发生变化时更新 `.awf/context/architecture.md`；任务流水账不进入架构地图。
