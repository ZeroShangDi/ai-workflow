# 架构与模块设计有哪些基础知识？（置顶）
关键词：设计基础、设计原则、编程范式、架构模式
答案：
- 高内聚、低耦合。
- 面向对象与 SOLID 五大原则。
- 面向过程。
- 函数式编程。
- 命令式与声明式编程。
- 设计模式。
- 常用数据结构与算法。
- 分层架构、端口与适配器等架构风格。
- 领域建模与边界划分。
- 依赖方向与依赖倒置。
- 状态与数据所有权。
- 抽象与封装。
- 按功能组织代码与功能内聚。
- 组件组合与页面骨架式组织。

# 新建模块时，业务概念和术语的边界如何确定？
关键词：领域建模、业务术语、概念边界
答案：先收集该概念参与的业务规则、状态变化、生命周期和决策责任，再看这些规则是否总由同一方维护、是否因相同需求一起变化。术语相同不代表概念相同：例如两个“用户”在权限、身份来源或生命周期不同的子域中，可能应建模为不同角色并通过明确映射协作。名称应来自业务语境；若团队对名称的定义不一致，先澄清语义再决定模块边界，避免用技术类名替代业务概念。

# 新建模块时，模块应该按什么职责和粒度划分？
关键词：模块职责、模块粒度、内聚
答案：从模块需要负责的决策、数据和规则出发，检查它们是否属于同一业务目的、是否通常一起变化，以及模块能否在不窥探其他模块内部状态的情况下完成职责。过大常表现为内部有多个独立变化原因、需要频繁跨职责修改；过小常表现为模块没有自己的规则，只转发调用或迫使调用方拼装内部细节。目标不是最少文件或最小模块，而是让变更落点、所有者和接口容易说清。

# 新增代码时，应该按业务功能、技术类型还是变化原因组织目录和文件？
关键词：代码组织、功能内聚、目录结构
答案：以“改一个功能时，需要理解和改哪些内容”为依据：若状态、规则、界面和测试常一起变化，把它们按功能聚拢能减少跨目录跳转；真正跨功能共享的基础设施才适合集中按技术类型组织。文件树应让常见改动的相关代码相邻，同时避免把所有内容塞进一个功能目录。页面可用组件组合显露整体骨架，各组件内部保留实现细节；骨架解决可辨认和定位问题，按功能聚拢解决相关状态与行为分散问题，两者可以并用。

# 新建功能时，状态、业务规则和副作用分别由谁拥有？
关键词：状态所有权、副作用、职责归属
答案：逐项标出状态的创建者、合法修改者、规则判断者和副作用执行者；通常应尽量让它们靠近同一业务职责，但不必强塞进同一个函数或对象。跨模块操作通过明确命令、查询或事件完成，并说明谁能写、谁只读。把网络、文件、时钟等不可控交互留在可替换边界，使核心规则能独立推理；若任何调用方都能随意改状态，或同一规则被多处重复判断，所有权就不清楚。

# 新建功能时，面向对象、过程式或函数式组织各适合什么问题？
关键词：编程范式、对象、函数
答案：看代码最需要表达什么，而不是给项目选一个范式标签。对象适合有身份、生命周期和需持续维护的不变量；过程式适合输入输出明确、按步骤完成的流程；函数式适合把数据转换拆成可组合、易验证的纯计算，并将副作用安排在边界。混合使用很常见：用对象或模块管理状态，内部用函数表达规则，外层用过程串联步骤。若采用某种范式后需要大量样板或读者必须绕行才能看懂，说明它未贴合问题。

# 新建系统或子系统时，分层、端口与适配器等架构风格如何选择？
关键词：架构风格、分层、依赖方向
答案：先识别系统有哪些独立变化源、哪些规则必须保持、哪些部分需要单独测试或替换，再选能以最低结构成本隔离这些变化的风格。分层适合职责顺序清楚、依赖方向简单的应用；端口与适配器适合业务规则需要脱离数据库、框架或多个外部服务独立运行、测试或替换的系统。架构风格不是目录模板：若引入后仍到处穿透层次，或小改动要维护大量空接口和转发器，应缩减结构。

# 增加业务行为时，应该放入现有模块还是建立新的职责边界？
关键词：职责边界、功能归属、模块拆分
答案：先问新行为由谁决定、它读写谁的数据、与哪些既有规则必须保持一致，以及将来是否可能独立变化。若它扩展现有职责并与其规则共同演进，放在现有模块内通常更直接；若它有独立规则或生命周期，需要不同权限/依赖，或变化时不应牵动现有模块，则考虑新边界，并定义协作接口。不要只看代码长度、文件数量或“看起来能复用”来拆分。

# 同一业务规则被多个功能使用时，应该共享还是各自维护？
关键词：业务规则复用、共同变化、重复逻辑
答案：先比较输入含义、边界条件、例外规则和变更历史，确认这是同一条业务约束，而不只是公式或代码相似。若使用方必须对规则保持一致，应指定唯一所有者并提供稳定接口；避免复制后各自漂移。若不同场景预期独立演进，分别维护更安全，即使短期代码重复；确有共同部分时只抽取共同且稳定的语义，不把差异藏进难懂的参数开关。

# 新增行为分支时，如何判断是普通条件变化还是独立变化策略？
关键词：条件分支、策略、变化点
答案：先看条件表达的是同一规则里的少数例外，还是几套可独立说明、独立变化的行为。前者用清晰的条件分支即可；后者若频繁扩展、各有依赖或需单独验证，再考虑策略、分派表或组合。抽象前应明确新变体从哪里来、由谁选择、哪些行为真正不同；若只有一个调用点且条件易读，过早建策略对象通常只会增加跳转。

# 修改组件时，组件职责、状态所有权和对外接口是否仍然清楚？
关键词：组件职责、组件状态、组件接口
答案：检查组件做什么、哪些状态由它维护、调用方能通过什么输入影响它、结果如何输出，以及它是否自行触发外部副作用。状态通常放在能够保证相关规则一致且生命周期匹配的位置：局部交互状态可留在组件，多个视图共享或由业务流程控制的状态应由更高层/领域模块拥有。若组件承担多个无关用途、父子双方都能改同一状态，或调用方依赖其内部结构，应收紧接口或拆分职责；拆分后仍要让页面骨架保持易读。

# 多个页面需要相似能力时，应该复用组件、组合子组件还是保持独立？
关键词：组件复用、组件组合、页面结构
答案：复用依据是共同语义和共同演进，不是外观相似。多个页面若共享稳定的交互、状态约束和变化原因，可提取组件；页面内部复杂但部分只服务该页面，可拆成局部/私有子组件以显出结构，不必提升为全局复用；规则不同的相似外观应分别实现，必要时只复用低层视觉原语。提取后若出现大量布尔参数、插槽分支或调用方理解成本上升，说明通用组件吞并了不同职责。

# 修改一个样式时，全局样式、组件局部样式和设计令牌应该如何组织？
关键词：样式组织、样式作用域、设计令牌
答案：先判断样式的影响范围与变化责任：重置、字体基线等应用级约定放全局；组件自己的布局和状态样式尽量局部作用域；多个组件共同遵守且需统一调整的颜色、间距等值用令牌集中管理。避免通过宽泛选择器偶然修改其他区域，也避免把每个单次值都提升为令牌。修改后应核对响应式、交互状态和主题等依赖同一规则的场景。

# 设计接口时，如何避免暴露实现细节或让调用方依赖过多能力？
关键词：接口设计、封装、依赖
答案：从调用方的实际用例反推最小契约：它需要发起什么操作、提供什么信息、得到什么结果，以及错误如何表达。用稳定的领域语义表达契约，避免暴露数据库模型、内部组件树或可随时重排的实现细节。一个接口若混合无关用例、需要大量可选参数，或调用方必须先了解内部状态才能正确使用，应拆清职责或改成更有约束的输入输出；接口也不必抽象到隐藏所有实现信息，目标是限制不必要的依赖。

# 多个模块共同完成一项业务时，直接调用、共享状态或事件消息各适合什么情况？
关键词：模块协作、直接调用、事件
答案：先确定协作的时序和业务语义。需要明确请求、立即得到结果并由调用方处理失败时用直接调用；多个参与者确实围绕同一权威状态协作时可共享受控状态，但须指定写入者并避免任意读写；发布方只需声明已发生的事实、接收者可异步处理时用事件。事件会带来顺序、重复投递、失败重试和追踪成本；共享状态会带来隐式耦合。不要只为降低表面上的直接依赖就改用事件。

# 多个模块共同读写数据时，数据归属和一致性边界如何确定？
关键词：数据所有权、一致性、共享状态
答案：对每份关键数据标明权威来源、允许的写入操作、校验规则和读取方；尽量只有一个模块负责维持其不变量。跨模块流程先识别必须原子成立的业务条件，再决定事务边界；无法跨系统原子提交时，明确最终一致、补偿或冲突解决方式。缓存和投影可以有多个副本，但必须说明如何更新、允许多大延迟及失效时怎么恢复，不能把副本误当权威状态。

# 外部模块或技术的语义渗入业务边界时，是否需要隔离接口？
关键词：外部依赖、适配器、业务边界
答案：看外部依赖是否把业务规则绑到特定供应商、协议、框架模型或难以替换的副作用上，以及业务代码是否必须理解外部术语才能工作。若依赖易变、转换有实际语义或测试需替身，则在边界用适配器把外部输入输出翻译成内部契约；若依赖稳定、轻量且没有语义泄漏，直接使用往往更清楚。适配层应集中转换、错误映射和版本差异，避免只增加同名转发类。

# 重构时，如何发现职责混杂、变化原因不一致或边界放错的位置？
关键词：重构、职责混杂、变化原因
答案：从具体变更证据开始，而非先套“高内聚低耦合”标签：对照近期需求与改动文件，找出同一模块因哪些互不相关的原因修改、同一规则在哪些位置实现、哪些变更总需同步多个模块。再画出数据所有权、调用方向和实际责任人，判断问题是职责混杂、接口泄漏、重复真值还是需求本身跨领域。一次只调整一个可验证边界，观察后续类似变更是否更集中；不要为了理想图形大规模重排。

# 一处需求变化要修改多个模块时，变化传播是否暴露了边界问题？
关键词：变化传播、耦合、影响范围
答案：多模块改动本身不是坏事，关键看每个改动是否表达需求所需的独立责任。先列出文件及其必要性：业务规则变化、接口适配、调用方迁移、测试/生成物更新分别标明；再找是否存在同一事实多处维护、无关模块因内部细节变更而被迫同步、或单一规则缺少负责人。需求确实横跨多个边界时，协调改动合理；若长期同类需求都扩散到无关模块，才是调整边界或契约的证据。

# AI 为局部功能修改十几个文件时，如何判断必要传播还是结构性扩散？
关键词：AI改动范围、多文件修改、变更扩散
答案：先列出每个文件的改动理由，并区分直接实现、真实消费者及调用方、测试、配置、生成产物和无关整理。多个消费者各自承担契约时，多处修改可能是完整实现；同一事实被手工维护多份时，才评估权威来源或生成；生成产物应按仓库流程重建并核对一致性。再检查是否存在职责混杂、接口泄漏或规则无主等结构原因。不要机械设文件数上限；每个落点都应能对应需求或风险。无法解释的改动应收窄、复核或撤回。

# 模块之间形成循环依赖或依赖内部细节时，依赖方向哪里不合理？
关键词：循环依赖、依赖方向、封装
答案：沿依赖环逐条问谁拥有共享规则和数据，双方是否互相调用对方内部实现，或一个概念被放在了错误模块。若依赖方向违反业务层级，可由稳定的高层契约定义接口、低层实现适配；若双方只是共享同一小段概念，应把其真实所有者明确出来。不要把接口随意塞进“common”模块以打断静态环，却保留运行时循环或模糊归属；解环后需确认控制流和数据所有权仍清楚。

# 多处代码相似时，如何判断它们代表共同规则还是表面相似？
关键词：重复代码、共同规则、复用判断
答案：对比相同输入下的业务含义、边界条件、错误处理和预期演进方向。只有语义与不变量一致、修正规则时所有使用方都应同步，才有理由集中为共享实现；若只是样子相像或规则将独立变化，保留局部重复更能防止误耦合。共享后若出现调用方专属参数、条件分支越来越多，说明抽象跨越了不同语义，应拆回共同部分与各自规则。

# 同一技能的名称、数量或定义散落在多个文件时，如何找到唯一真值？
关键词：唯一真值、重复定义、维护扩散
答案：先确定哪份定义是权威源、其他副本是引用还是派生结果，并选择机制消除手工同步：能运行时读取就读取，能由源生成就生成；确实需重复展示时注明来源并自动校验。若工具链无法自动引用，应减少重复字段或把事实改为由一个清单维护。关键检验是修改一个事实时需要改几处：若多处手工编辑，AI 和人工都会遗漏，维护扩散问题仍未解决。

# 什么时候抽象能集中变化，什么时候会增加额外间接层？
关键词：抽象、变化集中、间接层
答案：抽象成立需指出具体收益：集中一条共同规则、隔离已知变化源、缩小调用方依赖，或让多个实现遵守同一契约。再比较它新增的概念、文件、跳转和配置成本；若仅一个直观用例、变化点是假设、调用方仍要理解全部内部机制，直接实现通常更容易维护。可先保留局部实现，在第二个真实用例出现时验证共同语义后提取，不以“以后可能复用”作为充分理由。

# 为新行为先整理旧代码时，如何区分必要重构和顺手清理？
关键词：必要重构、行为保持、改动范围
答案：先说明不整理会怎样妨碍本次正确实现或验证。若整理是必要前置，先用现有行为或针对性测试保护旧行为，再做局部收敛并验证行为不变，之后实现新行为并验证新增契约；这表示推理和验证分段，不要求机械拆成多个提交。无关命名、全量格式化、框架升级或跨模块迁移应单独提出。完全禁止必要整理可能留下错误补丁；以“代码更干净”为由大范围清理也会扩大回归面。

# 模块应该拆分还是合并，如何判断拆分后的独立职责是否真实存在？
关键词：模块拆分、模块合并、独立职责
答案：用实际改动和协作来判断：若模块内部有不同规则所有者、不同变化原因或可独立替换/测试的部分，且它们之间能形成稳定接口，拆分可能降低牵连；如果拆后仍需频繁共同修改、跨模块访问内部状态、接口只是转发，边界成本超过收益。合并也要满足语义和责任相近，不能仅因模块数量多就合。评估时同时看理解路径、依赖方向、发布/测试独立性及改动范围。

# 新增变体时，应该使用配置、组合、独立实现还是扩展点？
关键词：变体设计、配置、组合
答案：先列出变体之间哪些规则相同、哪些真正不同，以及谁负责选择变体。只是名称、阈值或展示值不同且执行逻辑一致时用配置；变化可拆成少数稳定能力时组合；规则、依赖或生命周期差异明显时分开实现。扩展点适用于已有外部扩展者或明确产品需求，并且契约、版本和失败行为都可定义；不要为未知未来预先开放插件机制。

# 设计模式何时解决了重复出现的问题，何时只是增加了结构？
关键词：设计模式、重复问题、过度设计
答案：不要从“这里能用某模式”开始，而从反复出现的具体困难开始：例如创建规则散落、算法需替换、对象协作导致耦合。确认模式的参与角色能对应实际职责，再比较它是否减少重复决策、收敛依赖或让变化局部化。若只是命名好听、增加工厂/接口/对象层，却没有真实替换点或协作收益，就用直接结构；模式应帮助团队沟通与演进，不是完成设计任务的清单。

# 列表、映射、集合、队列、栈或树，如何按数据关系和主要操作选择？
关键词：数据结构、查找、顺序
答案：先看数据天然关系和最常见操作：需要位置与顺序遍历用列表；按键定位用映射；强调唯一性和成员判断用集合；按到达顺序处理用队列；嵌套调用、撤销或回退用栈；父子层级用树。随后考虑查找、插入、删除的频率与数据规模，确认语言库实现和迭代顺序约定。不要只凭理论复杂度选结构；语义清楚、标准库支持且规模适中的结构通常优先。

# 算法与数据结构选择何时属于设计问题，何时应交由性能分析判断？
关键词：算法选择、性能分析、复杂度
答案：若数据规模和操作模式已知会使某种算法超出时延/内存约束，或选择决定系统是否能完成需求，需在设计阶段处理并估算复杂度；这不是等到上线才看指标的问题。若几种方案都满足约束，而差异大小不确定，就先选清楚、可维护的方案，再用代表性数据剖析热点、测量时间与内存后优化。基准应反映真实数据分布和关键路径，避免凭小样本或微基准过度优化。

# 业务概念相似但规则不同，如何避免错误复用或边界混淆？
关键词：领域概念、业务规则、错误复用
答案：将两个概念的身份、状态转换、不变量、权限、生命周期和语言定义并排列出，找出相同与不同。核心规则不同就用不同名称/类型/模块表达，必要时在边界显式转换；这避免把某处的例外塞入共享模型并破坏另一场景。若语义确实相同但流程不同，可以共享模型而让用例流程分别编排。不要为追求复用把领域差异压成一个带大量可选字段的“万能实体”。

# 模块边界与团队责任、独立交付或并行开发方式冲突时，问题应如何定位？
关键词：团队边界、并行开发、模块归属
答案：先调查冲突的具体表现：变更需多团队排队、接口频繁协商、故障责任不清，还是同一业务规则被不同团队重复实现。再比较业务内聚、共同变化、数据所有权与团队的决策/运维责任。若团队确实独立交付且职责稳定，可把模块契约和数据边界设计为可独立演进；若一个业务能力天然需要紧密协作，生硬按团队拆分会增加协调，应考虑调整责任归属或协作流程。组织图只能提供线索，不能单独决定代码边界。
