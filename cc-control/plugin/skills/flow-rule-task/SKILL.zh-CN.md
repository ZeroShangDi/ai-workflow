# 任务粒度 — 如何拆分工作

## 核心原则

**不了解实现方案就不能拆。** 拆分的质量取决于对实现步骤和工作量的认知深度。先拆再理解 → 边界错误。

> 所有的拆分都需要先考虑好实现方案，实现步骤，每个步骤的工作量才好想怎么拆分。

## 任务层级（自上而下定位）

```
生态级 → 系统级 → 里程碑级 → 项目级 → 模块/需求级 → 功能级 → 任务级 → (动作级) → (原子级)
                                                              ↑
                                                        最小使用单位
```

| 层级 | 范围 | 示例 |
|------|------|------|
| 生态级 | 多产品多项目商业版图 | 微信生态（小程序 + 公众号 + 支付 + 小商店） |
| 系统级 | 多项目共同实现一个目标 | 后端 API + 用户 App + 后台管理 |
| 里程碑级 | 版本化迭代 | v0.1 MVP → v0.2 → v1.0 |
| 项目级 | 一个完整可部署的单元 | 前端项目、后端服务、CLI 插件 |
| 模块/需求级 | 自包含的子系统 | 认证模块、支付模块 |
| 功能级 | 用户可感知的能力 | 暗黑模式、导出 PDF、搜索筛选 |
| **任务级** | **Claude Code 一次能解决** | 实现 StateParser、添加缓存拦截器 |
| 动作级 | 3-8 个原子操作，不作为任务使用 | 重命名函数、添加配置项 |
| 原子级 | 单个函数/行/命令，几乎不使用 | 一个 `const` 声明 |

**任务级是实践中使用的最小单位。** 动作级和原子级只存在于概念中，不应出现在 WBS 或任务清单中。

## 任务定义

任务是 **Claude Code 一次会话能解决** 的颗粒度。锚点：1-5 个文件，50-300 行变更，有明确、可独立验证的完成条件。

**任务是弹性容器** — 简单功能可以是一个任务，复杂需求也可以是一个任务。粒度跟着实际复杂度走，不按公式套。

## 通用流程

每次拆分都遵循这个 5 阶段结构：

```
理解/探索 → 方案/规则 → 分治实现 → 组装/整合 → 验证/复盘
```

不是每个阶段都需要子任务。只有复杂到需要时才拆分。

### 各阶段说明

| 阶段 | 目的 | 何时拆分子任务 |
|------|------|---------------|
| **理解/探索** | 探索未知，界定问题范围 | 多个独立未知项需分别调查 |
| **方案/规则** | 定义规则、接口、约定 | 跨模块耦合需前置对齐 |
| **分治实现** | 构建交付物 | 核心复杂度所在 — 按独立性拆分 |
| **组装/整合** | 串联模块，联调 | 始终至少有一个组装任务 |
| **验证/复盘** | 端到端验证、回归、复盘 | 始终至少有一个验证任务 |

## 拆分规则

### 什么时候拆

| 信号 | 行动 |
|------|------|
| **独立可验证** | 拆 — A 的正确性不需要等 B 就能确认，就是独立任务 |
| **复杂度高** | 拆 — 把复杂部分单独拎出来 |
| **数据源独立** | 拆 — 不同输入、不同验证 |
| **需要前置规则** | 拆 — 多模块耦合时，先拆"定义规则"的任务 |
| **存在依赖链** | 拆并排序 — 按依赖关系确定先后 |

### 什么时候不拆

| 信号 | 行动 |
|------|------|
| **逻辑同构** | 合并 — 同一模式、同一套代码、同一个任务 |
| **薄层/胶水代码** | 合并 — 路由、组装、透传逻辑 |
| **还不够了解** | 不拆 — 先探索，再决定 |
| **没必要** | 不拆 — 拆分是工具，不是目的 |
| **验证耦合** | 合并 — 如果正确性只能一起验证，就放一起 |

## 核心判断标准

**第一标准 — 独立可验证：**
> A 做完了不需要等 B 就能确认 A 是否正确？能 → 拆。不能 → 合并。

**第二标准 — 自上而下定位：**
> 从对应的层级开始往下拆分，深入时发现复杂再继续拆。不要提前一次性拆完所有层级。

**第三标准 — 渐进式拆分：**
> 先按功能切大块，深入实现时发现复杂再往下拆。边做边拆，不是一次性的。

## 场景适配

不同场景对基础模式的变形：

| 场景 | 策略 |
|------|------|
| **不确定** | 先探索，不等全搞懂就先拆一个探索任务，基于结论再拆 |
| **紧急** | 止血优先于根治，并行排查后快速收敛 |
| **有基础** | 在现有框架上增量叠加，按新增功能拆分 |
| **无基础** | 先各自独立实现 → 发现共性 → 重构抽取。或：先定规则再各自实现 |
| **纯调研** | 知己 → 知彼 → 维度对比 → 综合评估。按维度拆分 |
| **迁移类** | 探索 → 工具脚本 → 独立表先迁 → 依赖表后迁 → 数据校验 → 全量回归 |

## 非实现类任务

以下都是正经任务，不是附加项：

- **调研/探索**：在设计前降低不确定性
- **方案/规则定义**：多模块耦合时前置定规则
- **工具/脚本**：为主线工作建辅助工具
- **组装/联调**：串起各自独立构建的模块
- **测试/验证/回归**：确认正确性
- **问题排查/调试**：诊断和修复
- **运维保障**：断点恢复、数据校验、回滚方案
- **复盘/总结**：从事中学习
- **非功能性**：打包、预览、文档

## 渐进式拆分

拆分不是一次性提前完成的活动：

1. 将工作在层级中定位（是哪一级？）
2. 在当前层级按功能拆分
3. 对每个功能块：复杂？→ 往下拆。不复杂？→ 停。
4. 实现过程中：发现复杂度？→ 继续拆。没有复杂度？→ 继续。
5. 始终以组装 + 验证任务收尾

## 示例

### 功能开发（有基础）：给 REST API 加 Redis 缓存

```
1. [探索] 了解现有中间件、可缓存点
2. [实现] MVP：TTL 缓存读写 → 验证可行性
3. [实现] 拦截器集成
4. [实现] 缓存失效策略
5. [组装] 全量集成 + 回归测试
```

### 功能开发（无基础）：跨平台 Button 组件（React/Vue/Web Component）

```
1. [方案] 定义跨平台接口规范（props、events、slots）
2. [方案] 主题 token 定义、样式配置
3. [实现] 通用样式引擎
4. [实现] React 实现
5. [实现] Vue 实现
6. [实现] Web Component 实现
7. [实现] size 变体、loading 状态
8. [组装] 构建管线 + 预览
```

不知道共性时的 fallback：
```
1. [实现] React Button 独立实现
2. [实现] Vue Button 独立实现
3. [实现] Web Component 独立实现
4. [重构] 抽取共享逻辑
5. [组装] 统一构建 + 预览
```

### 紧急修复：支付回调成功率骤降

```
1. [止血] 并行排查：近期部署、第三方状态、数据库指标
2. [响应] 代码问题 → 回滚。第三方问题 → 联系 + 备用方案。都不是 → 公告 + 安抚。
3. [根因] 深度排查
4. [修复] 实施方案
5. [复盘] 复盘文档
```

### 纯调研：React vs Vue 技术选型

```
1. [知己] 团队技术储备、现有资产、招聘难度、项目需求
2. [知彼-项目] 做什么项目、可能有什么功能
3. [知彼-框架] 框架区别、特性对比
4. [知彼-生态] 插件/库可用性、项目契合度
5. [评估] 长期演化成本、维护负担
6. [综合] 综合建议 — 不是最好，而是最合适、综合成本最低、风险最小
```

## 与 WBS 的关系

WBS 项是**交付物**，任务是**可执行工作单元**。一个 WBS 项复杂时可包含多个任务，简单时多个 WBS 项可合并为一个任务。

```
WBS: "数据采集模块"   →  Tasks: StateParser、GitExtractor、FileExtractor
WBS: "配置模块"       →  Tasks: config（简单，1:1）
```
