# Command 管理

命令是用户显式选择的执行入口。优质命令表达目标、按需路由能力并判断何时完成；它不是固定流程模板，也不是可能相关的 skill 清单。

## 判断是否值得创建

创建前先回答：

1. 用户是否需要一个可记忆、可显式调用的入口？不是则优先使用 skill。
2. 入口是否对应稳定目标、工作模式或状态转换？一次性提示词不必固化成命令。
3. 内容是否会被多个入口复用？会则把知识放进 skill，命令只保留选择和协作方式。
4. 目标平台如何发现命令？先读取仓库约定与相邻命令，不凭经验猜目录或字段。

命令与 skill 同时需要时，先稳定 skill 的职责和名称，再编写命令入口。

## 从真实场景设计

不要从章节模板开始。先用目标命令覆盖的真实请求建立行为边界：

- 最轻场景：模型能否直接完成，哪些额外流程应被跳过；
- 常规场景：通常存在哪个决定性难点，需要什么能力；
- 复杂或高风险场景：什么证据出现后才升级分析、验证或协作；
- 邻近反例：什么请求不应调用该命令或其中的专项能力。

场景用于发现分支，不要求把“简单/常规/复杂”写成用户可见模式。只有用户确实需要控制执行强度时才暴露模式参数。

## 设计最小契约

每条命令都要让执行者能够确定：

- **目标**：最终要促成什么可观察结果；
- **入口行为**：如何解释调用上下文，缺少关键信息时如何继续；
- **路由依据**：什么事实触发、跳过或组合某项能力；
- **完成条件**：何种结果与验证足以结束。

其余内容按需生成：只有存在真实参数时才写参数契约；只有消费方依赖固定形状时才规定输出；只有命令新增特殊风险时才写权限或失败规则。不要为了形式补齐空章节。

## 设计 Skill 协作

先为命令定义不可跳过的质量基线，再设计专项路由。基线须来自该任务的典型失败方式：如何发现隐含约束、确定职责和影响范围、检查失败路径，以及用什么证据判断结果可交付。简单任务可以简短完成这些判断，但不能因未加载 skill 而免除它们。

路由必须说明如何发现信号，不能仅写“存在设计问题时加载设计能力”。例如开发命令先检查状态归属、调用方契约、异步顺序和变更传播，再据此选择能力；框架或安全标签不能代替这些判断。

先定位任务中的决策点，再寻找能改变这些决策的 skill。对每个候选 skill 明确：

| 设计项 | 必须回答的问题 |
|---|---|
| 触发信号 | 哪个可观察事实出现后才需要加载 |
| 决策贡献 | 它会改变哪个选择或降低什么具体风险 |
| 使用成本 | 会增加多少上下文、探索、工具调用或流程步骤 |
| 组合关系 | 与哪些能力互斥、依赖或需要先后执行 |
| 退出条件 | 何时已经得到足够指导，不再扩展流程 |

无法说明决策贡献的 skill 不应进入命令。命令正文写“条件 → 能力 → 用途”，不要写没有触发条件的“关联 Skill”目录。

遵守以下路由原则：

- 默认走能够满足目标与风险要求的最低成本路径；模型已有能力足够时允许不加载 skill。
- 发现真实信号后再加载专项能力，不为“可能用到”而预加载。
- 优先一次只解决当前决定性问题；多个 skill 只有在职责互补且任务确实同时需要时组合。
- 互斥能力只选择匹配当前技术或场景的一项。
- 通用方法不得无条件拉起重型工作流；状态管理、子代理、全量审查和恢复机制都需要单独触发理由。
- 执行中出现新证据可以升级路径；已满足完成条件时停止继续路由。
- 组合能力时明确交接结果：前一项形成的约束、接口或风险交给后一项落实和验证，避免各自重复探索。skill 中的继续引用也需判断是否为真实依赖，不能递归加载整套目录。

## 平衡速度、质量与成本

先满足用户验收以及不可降低的正确性、安全性和权限边界；在满足该质量底线的候选路径中，选择上下文、工具调用、等待和协作成本最低的路径。成本接近时选择更快、更可逆的实现。

成本包含返工、漏检和维护代价；少加载 skill、少写测试或少修改文件本身不证明成本更低。设计与可读性属于交付质量。新增流程必须能防住具体失败，不能靠增加检查口号证明改进。

涉及修改既有产物时，要求执行前预测必要影响范围，执行中对新增影响点重新判断，完成前检查实际差异。优先收敛权威修改点；尊重用户明确的文件预算，但不得靠堆进单文件、删除必要测试或隐藏生成物规避预算。范围外工作需要另行授权。

不要把三者换算成虚假的固定分数。通过执行策略体现平衡：

- 简单、局部、可逆的任务直接处理并做针对性验证；
- 出现设计取舍、专项风险或跨边界影响时，只增加对应能力；
- 高风险、长周期、多任务依赖或确需追踪时，才进入完整工作流；
- 验证范围随影响面和失败代价扩大，不默认运行所有检查；
- 失败没有带来新信息或方向持续偏离时，才启用复盘、回撤或重新规划。

## 编写命令

1. 找到唯一手写源、生成目录和注册清单；禁止直接修改构造产物。
2. 搜索同名、同义和相邻命令。能扩展既有入口时不新建第二个入口。
3. 从真实场景提炼最小契约和最低成本主路径，再定义有证据的升级分支。
4. 按目标仓库现有格式写 frontmatter 与正文。跨平台源采用字段超集时保留各平台字段，不自行互相推导。
5. 只固定具有真实依赖的顺序；其余步骤写目标、判断条件与不变量，允许执行者按上下文调整。
6. 把专业知识留在 skill；命令只说明何时需要它、用它决定什么以及如何回到主任务。
7. 同步实际需要的注册、索引和验证；不因为新增命令顺手改无关配置。

## 质量规则

- description 说明结果和适用场景；参数提示只描述真实输入；正文表达自适应编排。
- 命令名短、稳定、无同义重复；是否带命名空间由宿主决定。
- 正常路径短且可直接执行，复杂分支不能成为所有调用的固定税。
- 不用固定步骤掩盖决策；不以文件数、skill 数或流程长度冒充质量。
- 不把实现路径、生成目录或单一平台工具名写成跨平台事实。
- 不静默扩大权限；写文件、联网、发布等动作仍服从调用任务的授权边界。
- 不保留 TODO、示例占位符或不存在的 skill/工具引用。

## 验证

先验证结构与发现，再用代表性场景验证行为：

- 最轻场景不会加载无关 skill、读取无关状态或启动重型流程；
- 常规场景能选择真正改变关键决策的能力；
- 未显式提示风险的场景也会主动检查隐含约束和失败路径；不能只在用户点名问题时才启动质量分析；
- 产物的职责、可读性与变更范围符合任务，必要的扩展能沿明确边界完成；未调用专项 skill 也必须满足这些基线；
- 高风险场景会升级到必要的保护与验证，而不是为了节省成本牺牲质量；
- 邻近反例不会误触发；互斥能力不会同时加载；
- 非工作流调用不会执行工作流落账，未满足完成条件不会报告成功；
- 宿主能发现命令，frontmatter 可解析，引用真实存在，生成链路不丢字段或留下旧文件。

修改既有命令时保留仍然成立的合法调用，但不要为兼容旧流程保留已证明造成无效成本的行为。优先运行相关构建和测试；行为测试同时观察结果质量以及不必要的 skill、工具和流程是否被省略。

区分静态校验和真实行为评估：格式、引用与构建通过只能证明可加载。比较质量、耗时和用量需在相同模型、任务与初始状态下运行；只有加载日志时，不把调用数量当成成功或失败的根因，也不声称已验证节省比例。
