# Skill 管理

好 skill 提供模型原本不稳定掌握、且能重复复用的判断力。删除后任务仍能同样可靠完成的内容，不应写进 skill。

## 创建前判断

1. 读取目标仓库的代理说明、技能规范和相邻 skill；确认唯一手写源，避开构造产物。
2. 搜索同名、同义和同职责 skill。优先增强既有 skill；只有职责可独立描述、触发条件可区分时才新建。
3. 判断它是否真是 skill：
   - 自动发现、可复用的知识或方法 → skill；
   - 用户显式调用的稳定入口与编排 → command；
   - 确定性、重复性的机械操作 → skill 内脚本；
   - 仅某一模式需要的大段规则 → reference。

## 设计规则

### 命名

- 使用小写 kebab-case，简短、面向能力；有领域时采用 `{domain}-{capability}`。
- 文件夹名与 frontmatter 的 `name` 一致。
- `common-*` 只用于跨领域基础能力，不能把领域规则放进 common。

### Description

description 是发现入口，应同时写清：

- 能力：它完成什么；
- 触发：什么请求、症状或文件形态应加载；
- 边界：最容易混淆的相邻任务何时不应加载。

不要把完整流程塞进 description，也不要用“处理各种任务”一类宽泛表述。

### 正文与资源

- 只写会改变决策或显著提高可靠性的内容，不重复模型常识与上位规则。
- 固定顺序只用于有真实依赖的步骤；开放任务写目标、判断标准和不变量。
- `SKILL.md` 固化道（理念、判断原则、取舍）与法（分析和执行方法、完成条件）。以结果指导方法，不为每项任务强制复制章节模板。
- 术（框架用法、陷阱、案例、操作经验）放入与 `SKILL.md` 同级的 `knowledge/` 目录，由入口按场景链接。理念必须能指导取舍，方法必须能导出行动，经验必须带条件和证据。
- 静态规范或外部协议放 `references/`，可演进经验放 `knowledge/`，重复且确定的操作放 `scripts/`，生成物素材放 `assets/`。避免同一知识维护多份。
- 后续 AI 可维护知识库，但不能借经验积累自动修改理念、方法或发现描述。具体写入边界见下方维护规则。
- 每个 reference 都必须从 `SKILL.md` 说明何时读取；不建立没有用途的空目录。
- 默认保持用户范围和权限，不把“完成任务”解释为允许发布、删除、安装或修改外部系统。

## 生命周期

- 修改：先理解当前调用者和资源用途，只改由真实问题支持的部分。
- 聚合：两个 skill 触发条件和主体知识相同，合并后保留一个权威入口。
- 拆分：只有不同模式各自内容足够独立、按需加载能明显降噪时才拆。
- 审计：检查误触发、漏触发、职责重叠、失效引用、重复规则、过时例子和未完成占位符。
- 删除：先搜索引用方和路由项；确认能力已迁移或废弃后再移除。

## 验证

1. 运行目标平台或仓库已有的 skill 校验器，确认 frontmatter、命名和资源引用有效。
2. 对复杂或高风险 skill 做行为测试：选一个真实请求，比较无 skill 与加载 skill 后的结果，验证它确实改变了关键决策。
3. 对路由类问题分别测试正例、近邻反例和组合请求，避免 description 抢占其他技能。
4. 新增脚本必须执行一次真实样例；只匹配标题或固定措辞的测试不算行为验证。

交付时说明新增、迁移或删除了哪些职责，以及验证结果；不把脚手架占位符留给下一次运行。

## 经验维护规则

任务执行中不能自动修改 SKILL.md 的道与法；只有用户授权技能设计变更时才能调整。AI 可在已授权的可写技能源 knowledge/ 中积累经验：先检索再补充或合并，记录适用条件、方法、原因、代价与反例、证据和验证状态。假设不能标为已验证，经验不能覆盖用户要求或稳定原则。不保存敏感数据或任务流水账，不写插件缓存及构建产物；无法定位可写源时只提出建议。

有实际经验再创建文件；条目少时由 SKILL.md 直接链接，多到需要检索时才添加索引。不要创建空目录、占位经验或重复的维护说明。
